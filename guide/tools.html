Herramientas: generadores de la solución

Referencia operativa para acelerar trabajo repetible: un generador prepara artefactos base de Extension y otro convierte especificaciones de APIs externas en contratos HTTP consumibles por Gateway. Surface tiene un comando separado para generar firmas TypeScript visibles al navegador. Esta página muestra qué crean, cuándo usarlos y dónde termina la automatización.

Overview

Las herramientas del workspace aceleran trabajo repetible, pero no deciden arquitectura por el dev. Escriben esqueletos, contratos y conexiones convencionales; la intención de aplicación sigue siendo una decisión humana.

Para alguien que recién entra al proyecto, conviene leer esta página como un manual de asistentes de código. Un comando Robo puede crear archivos con nombres, namespaces y ubicaciones correctas, pero no sabe si la feature necesita un use case simple, un service con varias fuentes, un connector opcional o un fragment HTML. Esa decisión se toma con las reglas de Gateway, Surface y Bridge; el comando solo evita trabajo mecánico cuando la decisión ya está clara.

Mapa rápido Cada herramienta cubre una parte distinta del flujo.
  • Artefactos de Extension tools/ExtensionScaffolder Genera controllers, routes, use cases, services, connectors, middleware e integraciones Surface base.
  • Contratos HTTP externos tools/HttpContractGenerator/Gateway Convierte Swagger/OpenAPI en PHP para llamadas outbound desde Gateway.
  • Contratos Surface tools/HttpContractGenerator/Surface Genera firmas TypeScript visibles para el navegador dentro de una integración.
  • Piezas compartidas tools/HttpContractGenerator/Shared Centraliza lectura OpenAPI, rutas, reportes y normalización común.

La regla práctica es simple: se debe usar un comando cuando el nombre, la carpeta y el wiring ya tienen una convención fuerte. El diseño manual corresponde cuando la decisión expresa comportamiento de aplicación, composición de datos, degradación parcial o conversación con un proveedor externo.

Regla central Primero se actualiza la configuración, luego se ejecuta el comando.

robo-configurations.json define rutas físicas, namespaces, defaults, destinos Surface y configuración de generadores. Cambia ese archivo antes de generar si la convención del workspace cambió.

Surface Los comandos crean el puente, no la lógica de negocio.
  • Page make:integration-page Puente mínimo SSR + Surface.
  • Fragment make:fragment Binding dentro de una integración existente.
  • API make:integration-api-data/json/html api.ts, ruta y action Gateway coordinadas.
  • Tipos surface:contract Contratos TypeScript visibles para una integración concreta.

Ninguno de estos comandos crea use cases, services, connectors ni clients outbound automáticamente.

Mapa de herramientas

Este mapa sirve para elegir una herramienta por el resultado que se necesita, no por ensayo y error entre comandos. Primero se identifica si el trabajo consiste en crear estructura de solución, traducir un contrato externo o generar tipos para Surface; después se consulta el comando y sus límites.

Capacidad Comando Robo Responsabilidad No decide
Generador de artefactos de la solución composer robo -- make:... Crea controllers, routes, use cases, services, ports, connectors, service clients, providers outbound, middleware, páginas SSR conectadas a Surface, bindings de fragment y endpoints consumidos desde integraciones UI, según el comando elegido. No decide si un service aporta valor, no inyecta clients dentro de connectors y solo toca Surface en los comandos explícitos make:integration-page, make:fragment y make:integration-api-*.
Generador de contratos HTTP externos composer robo http:contract ... Genera un archivo de request y un archivo de response por endpoint detectado en Swagger/OpenAPI. No crea el service client, no implementa connector y no registra servicios en services.json.
Generador de contratos Surface composer robo -- surface:contract ... Genera clases TypeScript dentro de workspace/integrations/<feature>/contracts.ts para payloads y data visibles desde Gateway. No crea api.ts, no crea actions.ts y no reemplaza el contrato PHP outbound.
Listar comandos disponibles 
/raiz-del-proyecto/app-gateway> composer robo list
Antes de ejecutar Pregunta correcta Dónde profundizar
Ruta o endpoint ¿Ya existe el path en el árbol cargado desde ExtensionRouteRegister.php? ¿La salida será JSON, página, fragment o redirect? Routing y controllers.
Use case ¿La intención ya tiene nombre propio? ¿Existe otro use case con el mismo nombre corto en otra carpeta? Use cases.
Service ¿Coordina varias fuentes, fallback o parcialidad, o solo delegaría una llamada? Services y connectors.
Contrato HTTP externo ¿El Swagger/OpenAPI describe el request y la response reales del proveedor? API HTTP clients externos.
Contrato Surface ¿El navegador necesita tipos para el contrato Gateway visible, no para el DTO interno del proveedor? Consumo Gateway en Surface.
Composer + Robo Se debe usar el separador -- cuando el comando recibe opciones.
  • Forma composer robo -- <command> [argumentos] [opciones]
  • Ejemplo composer robo -- make:use-case Demo --action=index

Sin ese separador, Composer puede consumir opciones como --config o --use-case-folder antes de que lleguen a Robo. Si Robo no está disponible, se debe revisar qué se instala y por qué importa.

Configuración en robo-configurations.json

Los generadores necesitan conocer dónde vive cada tipo de archivo y qué namespace corresponde a esa ruta. Esta configuración central evita que cada comando repita o adivine la estructura del workspace.

Las herramientas leen robo-configurations.json desde la raíz del workspace. También aceptan --config=<ruta> cuando se quiera probar una configuración alternativa, pero la convención viva del proyecto debe mantenerse en el archivo raíz.

Generador de artefactos de la solución

Este generador prepara archivos iniciales para los artefactos más habituales de una solución en Extension: rutas, controllers, casos de uso, services, connectors, service clients, providers outbound, middleware, el puente SSR + Surface de una página de integración, bindings de fragment y endpoints que una integración Surface consume desde Gateway. Acelera la parte repetible, pero no decide si un artefacto debe existir ni qué responsabilidad debe tener.

La ejecución sale de app-gateway/RoboFile.php y usa la configuración del workspace para elegir rutas físicas, namespaces y defaults. Internamente resuelve qué artefacto crear, renderiza PHP/TypeScript, escribe archivos y aplica ediciones pequeñas en rutas, classes, AppProvider.php, registry Surface y menú principal cuando corresponde.

# Comando Crea Integración opcional
1 make:route-controller Ruta + controller. Ninguna
2 make:route-use-case Ruta + controller + use case. Carpeta del use case.
3 make:use-case Use case. Controller existente, carpeta del use case y action.
4 make:service Service. Use case existente.
5 make:connector Port + connector. Ninguna
6 make:service-client ServiceClient + provider + import en AppProvider. Ninguna
7 make:integration-page Página SSR + integración Surface. Menú principal si el layout es control.
8 make:fragment Binding de fragment Surface. Registro dentro de la integración propietaria.
9 make:integration-api-data Función api.ts + ruta + action JSON. Usa serverClient.data y exige feature Surface existente.
10 make:integration-api-json Función api.ts + ruta + action JSON. Usa serverClient.json y conserva el envelope.
11 make:integration-api-html Función api.ts + ruta + action + fragment SSR. Usa serverClient.html.
12 make:middleware Middleware HTTP. Ninguna
Regla de uso Se debe crear solo el artefacto necesario y conectar manualmente la intención.
  • Rutas ExtensionRouteRegister.php Los comandos con HTTP escriben en el registro central.
  • Verificación load(...) / group(...) El árbol cargado también cuenta para detectar paths repetidos.
  • Decisión El scaffolder no inventa lógica de aplicación.
Protección Qué evita Cómo actuar
Ruta existente por path Duplicar una URL aunque el verbo HTTP sea distinto. Cambiar el path.
Controller inexistente en make:use-case Crear un use case que pretendía integrarse a un controller que no existe. Crear primero la ruta/controller o ejecutar make:use-case sin controller.
Duplicado de action Sobrescribir métodos existentes como index. El scaffolder usa index1, index2 y así sucesivamente cuando debe crear una action nueva.
Integración page ya existente Duplicar una integración Surface ya registrada o una page que ya tiene page.ts / integration.ts. Si ya existe page.ts, integration.ts, el feature en registry.ts o la ruta base, el comando no modifica nada. Si solo chocan vista, action, ruta candidata o menú, se utiliza un sufijo compartido index1, index2, etc.
Feature Surface faltante Crear APIs o fragments huérfanos fuera de una integración UI real. make:fragment exige carpeta de feature e integration.ts. Los make:integration-api-* exigen la carpeta workspace/integrations/<feature>.
Fragment duplicado Registrar dos loaders con el mismo data-surface-fragment o pisar un archivo existente. El comando alinea el sufijo del archivo y del id: detail1.ts con items-detail1, por ejemplo.

Punto HTTP mínimo

Este comando se elige cuando la necesidad inmediata es abrir una entrada HTTP y todavía no existe una operación de aplicación que merezca una clase propia. Permite comenzar por ruta y controller sin inventar capas futuras.

make:route-controller crea esa entrada sin asumir todavía una intención de aplicación compleja: registra la ruta, crea el controller y apunta a una action. Se debe usar cuando primero sea necesario abrir la superficie HTTP y después decidir si la lógica merece un use case.

Ruta + controller 
/raiz-del-proyecto/app-gateway> composer robo -- make:route-controller <method> <path> <controllerName>
/raiz-del-proyecto/app-gateway> composer robo -- make:route-controller get /demo Demo
Protección de rutas El path normalizado manda, incluso si cambia el verbo HTTP.
  • Entrada <path> Se normaliza antes de buscar duplicados.
  • Registro ExtensionRouteRegister.php Se revisa el árbol de rutas cargado.
  • Ejemplo GET /demo -> POST /demo Se considera duplicado por compartir el mismo path.
  • Resultado --force No crea controller ni ruta cuando esta protección se activa.
Argumento Significado Ejemplo
<method> Verbo HTTP aceptado por el router. get, post
<path> Ruta que se registra. Se normaliza con / inicial. /demo
<controllerName> Nombre base del controller. Demo genera DemoController
--action Método del controller. Si se omite, se usa extensionScaffolder.defaults.action. --action=show
--middlewares Lista separada por comas para la ruta generada. RequireAuthentication

Endpoint con intención

Se usa cuando la entrada HTTP ya representa una operación de aplicación reconocible y reutilizable. En ese caso conviene crear desde el principio la frontera entre controller y use case.

make:route-use-case crea la estructura base de una acción de aplicación: ruta, controller y use case. Es el flujo cómodo para endpoints JSON donde la intención ya está clara, pero todavía no hace falta componer services, connectors o dependencias externas.

Ruta + controller + use case 
/raiz-del-proyecto/app-gateway> composer robo -- make:route-use-case <method> <path> <controllerName> <useCaseName> --use-case-folder=<folder> --action=<action>
/raiz-del-proyecto/app-gateway> composer robo -- make:route-use-case post /auth/demo Demo CreateDemo --use-case-folder=Demo --action=create
  • El controller generado responde con respondJson(...) y llama a execute() del use case.
  • El use case generado extiende AppUseCase y usa run(...).
  • Si el endpoint requiere composición externa después, se deben crear service, connector y service client con comandos separados.
Validación Resultado
La ruta ya existe, incluso con otro method. El comando termina sin crear controller, use case ni ruta. La ruta se compara ya normalizada contra el árbol cargado desde ExtensionRouteRegister.php.
Ya existe un use case con el mismo nombre. El comando termina sin tocar nada aunque el archivo esté en otra carpeta bajo Application/UseCase. La regla protege el nombre corto de clase para evitar dos archivos visualmente iguales en namespaces distintos.
El controller no existe. Crea el controller completo, crea el use case y registra la ruta hacia la action resuelta.
El controller ya existe. No reemplaza el archivo: inyecta el use case, agrega una action JSON nueva y registra la ruta hacia esa action.
La action solicitada ya existe. El comando usa el primer nombre libre con sufijo numérico: index, index1, index2, etc.
--use-case-folder Nombra la carpeta bajo Application/UseCase. Si la carpeta ya existe, se reutiliza; si falta, se crea solo para alojar el use case.

Intención de aplicación

Este comando sirve cuando primero debe existir la operación y la entrada HTTP puede conectarse después, o incluso no existir. La decisión se modela fuera del transporte para conservar su significado desde cualquier invocador.

make:use-case crea una intención ejecutable sin depender de una ruta específica. Sirve para aislar una decisión de aplicación, validar input y devolver un resultado normalizado. Si se pasa un controller como segundo argumento, el comando lo inyecta ahí; si además se pasa --action, agrega una action JSON que lo llama.

Use case 
/raiz-del-proyecto/app-gateway> composer robo -- make:use-case <useCaseName> --use-case-folder=<folder>
/raiz-del-proyecto/app-gateway> composer robo -- make:use-case ListItems --use-case-folder=Demo

/raiz-del-proyecto/app-gateway> composer robo -- make:use-case <useCaseName> <controllerName> --use-case-folder=<folder> --action=<action>
/raiz-del-proyecto/app-gateway> composer robo -- make:use-case ListItems ExternalItem --use-case-folder=Demo --action=list
Forma Resultado
make:use-case <useCaseName> Solo crea el use case.
make:use-case <useCaseName> [controllerName] Crea el use case e inyecta la dependencia en el controller.
make:use-case <useCaseName> [controllerName] --action=list Además agrega una action JSON que llama al use case.
Use case Permite agregar intención de aplicación sin abrir rutas nuevas.
  • No crea controllers / rutas El controller opcional debe existir antes.
  • Unicidad Application/UseCase Si el nombre corto ya existe, se detiene sin tocar el controller.
  • Action index / index1 / index2 El comando usa correlativo cuando el método destino ya está ocupado.
  • Carpeta --use-case-folder La opción --feature queda solo como alias heredado.

Composición de aplicación

Un service se justifica cuando coordinar varias fuentes, transformar resultados o distinguir datos obligatorios y opcionales agrega una decisión real. No se crea únicamente para añadir otra llamada entre el use case y una dependencia.

make:service crea un artefacto para coordinar trabajo que el use case no debería cargar directamente: transformación, varias fuentes, fallback o parcialidad. Si se pasa --use-case=<UseCase>, lo inyecta en ese use case. La regla de arquitectura sigue aplicando: no se debe crear un service si solo va a delegar una única llamada sin agregar significado.

El use case destino se busca recursivamente bajo Application/UseCase. Ya no se pasa carpeta para make:service: si existe un único archivo con ese nombre, se edita; si hay varios, el comando aborta porque el filesystem ya está ambiguo y sería peligroso elegir de forma automática.

Service 
/raiz-del-proyecto/app-gateway> composer robo -- make:service <serviceName>
/raiz-del-proyecto/app-gateway> composer robo -- make:service ExternalItem

/raiz-del-proyecto/app-gateway> composer robo -- make:service <serviceName> --use-case=<useCaseName>
/raiz-del-proyecto/app-gateway> composer robo -- make:service ExternalItem --use-case=ListItems

La decisión de usar service se explica en Services y connectors. Se debe usar para composición, transformación, varias fuentes, fallback o parcialidad; no para delegación vacía.

Situación Comportamiento
Solo se pasa <serviceName>. Crea el service y no modifica ningún use case.
Se pasa --use-case=<useCaseName>. Crea el service si falta y lo vincula al constructor del use case existente.
El service ya existe. No lo reemplaza sin --force, pero igual intenta vincularlo al use case indicado.
El use case indicado no existe. Conserva el service creado y muestra un aviso; no inventa un use case.
Hay varios use cases con el mismo nombre. No crea ni modifica nada. El duplicado debe corregirse antes de vincular el service para evitar elegir un archivo equivocado.

Salida hacia una dependencia externa

Este comando abre una frontera para que la aplicación pueda pedir una capacidad externa sin depender del proveedor, del cliente HTTP ni de sus errores técnicos.

make:connector crea el contrato que consume la aplicación y el adapter outbound que lo implementa. Es la frontera para traducir payloads, errores técnicos y respuestas externas a ConnectorResult. El connector generado no recibe un ServiceClient por constructor: puede usar uno, varios o ningún client HTTP, y esa decisión pertenece a quien implementa el adapter.

Port + connector 
/raiz-del-proyecto/app-gateway> composer robo -- make:connector <connectorName>
/raiz-del-proyecto/app-gateway> composer robo -- make:connector ExternalItem
Artefacto Ubicación Responsabilidad
Port Application/Port/<Name>ConnectorInterface.php Contrato que consume la aplicación.
Connector Infrastructure/Outbound/Connector/<Name>Connector.php Adapter outbound concreto que devuelve ConnectorResult.
Ubicación Connector y service client viven en familias distintas.
  • Clients Infrastructure/Outbound/Client/<Service>/... Transporte técnico hacia una API externa.
  • Connectors Infrastructure/Outbound/Connector/... Adapter que traduce hacia el contrato de la aplicación.

Cliente HTTP externo

Se usa cuando ya se sabe que una integración necesita un cliente HTTP propio, con configuración y registro independientes de otros proveedores. El comando prepara transporte y DI; no modela todavía la operación de aplicación.

make:service-client prepara el transporte técnico para hablar con una API externa: crea el client HTTP concreto, su provider outbound y el import de ese provider en Extension/Bootstrap/Container/AppProvider.php. Este comando sí toca DI porque el service client necesita recibir un ServiceDefinition desde el contenedor.

Service client + provider + AppProvider 
/raiz-del-proyecto/app-gateway> composer robo -- make:service-client <serviceClientName>
/raiz-del-proyecto/app-gateway> composer robo -- make:service-client ExternalApi
  • Genera Infrastructure/Outbound/Client/ExternalApi/ExternalApiServiceClient.php.
  • Genera Bootstrap/Container/Outbound/ExternalApiProvider.php.
  • Importa el provider outbound desde Bootstrap/Container/AppProvider.php.
  • No crea requests ni responses de endpoints. Para eso se debe usar http:contract.

Puente SSR + Surface

Este comando se elige cuando una nueva página debe existir como HTML usable desde Gateway y además necesita comportamiento TypeScript en Surface. Crea ambos extremos del acuerdo sin inventar la lógica que la página representará.

make:integration-page crea la base mínima para una página SSR servida por Gateway y activada por una integración UI de Surface. Es el único scaffolding actual que cruza esa frontera: no crea lógica de negocio, use cases, services, connectors, service clients ni middleware automático.

Página SSR + Surface 
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-page <feature> --id=<data-surface-page> --layout=control|access
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-page items --id=items-page --layout=control
Crea o actualiza Detalle
workspace/integrations/<feature>/page.ts Binding inicial de la página Surface.
workspace/integrations/<feature>/integration.ts Integración UI con id, layout y page load.
workspace/integrations/registry.ts Registro de la integración para que runtime la monte.
resources/views/<feature>/index.page.php Vista SSR con data-surface-page.
<Feature>Controller.php Controller con action index y render del layout elegido.
GET /<feature>/index Ruta escrita en ExtensionRouteRegister.php.
MainMenuItems.php Solo se actualiza cuando --layout=control.
Regla Comportamiento exacto
--id Es el valor base de data-surface-page. Debe usar letras, números, guiones o guiones bajos. El comando lo necesita para crear integration.ts y la vista SSR.
Cancelación completa No escribe nada si ya existe page.ts, si el feature ya aparece en registry.ts, si ya existe integration.ts o si la ruta base /<feature>/index ya existe en el árbol de rutas.
Sufijo compartido Si chocan index.page.php, el action index, una ruta candidata o el item de menú, el scaffolder prueba index1, index2, etc. El mismo sufijo se usa para id Surface, vista, action, ruta y label de menú.
Menú Con layout control agrega un MainMenuItem de nivel 1 con path igual a la ruta generada y activePrefixes apuntando al feature. Con layout access no toca el menú principal.
--force Puede sobrescribir archivos que el writer cree, pero no anula las reglas de cancelación por page, registry, integración o ruta base existentes.
Layout El layout decide si aparece un acceso en el menú principal.
  • Control --layout=control Crea puente SSR + Surface y agrega item de menú.
  • Access --layout=access Crea el puente, pero no toca el menú principal.

Binding de fragment Surface

Se usa cuando un fragment SSR ya pertenece a una integración y necesita comportamiento propio al aparecer en el DOM. El resultado debe limitarse al binding y su registro; producir el HTML o abrir una ruta sigue siendo otro trabajo.

make:fragment agrega comportamiento frontend a un fragment SSR dentro de una integración Surface existente. Es un comando pequeño: crea el archivo del binding, registra el loader en integration.ts y se detiene ahí. No crea rutas, controllers, vistas SSR ni registro global.

Fragment Surface 
/raiz-del-proyecto/app-gateway> composer robo -- make:fragment <feature> <fragment> --id=<data-surface-fragment>
/raiz-del-proyecto/app-gateway> composer robo -- make:fragment items detail --id=items-detail
Punto Detalle
<feature> Carpeta existente bajo app-surface/workspace/integrations. También debe existir su integration.ts; si falta cualquiera de los dos, el comando no modifica nada.
<fragment> Nombre base del archivo. detail crea fragments/detail.ts y una clase ItemsDetailBinding extends UiBinding.
--id Valor de data-surface-fragment. Es opcional: si se omite, se usa <feature>-<fragment>.
Carpeta fragments/ Se crea si no existe dentro de la integración.
Sufijo compartido Si ya existe el archivo base o el id en integration.ts, se utiliza el siguiente correlativo para ambos lados: detail1.ts y items-detail1, luego detail2.ts y items-detail2.
Montaje El id del HTML y el registro de Surface deben coincidir.
  • HTML Gateway data-surface-fragment Debe tener el mismo id que quedó registrado.
  • Modal o toast contentMount Permite montar y desmontar fragments insertados dinámicamente.

Endpoint consumido como data

Este modo se elige cuando la UI solo necesita los datos útiles de una respuesta exitosa y no debe interpretar mensajes, errores o estados parciales del envelope completo.

make:integration-api-data agrega una función asíncrona en api.ts que llama a Gateway con serverClient.data. Este modo es para endpoints JSON donde la integración necesita la propiedad data ya validada y no el envelope completo.

API data 
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-api-data <feature> <nameFunction> <method> <path> --controller-name=<ControllerName>
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-api-data items searchItems post /items/search --controller-name=Item
Parte Qué ocurre
Precondición Debe existir workspace/integrations/<feature>. Si no existe, el comando aborta sin tocar archivos.
api.ts Si falta, lo crea con import de serverClient y export interface CustomResponse {}. Luego agrega una función async lowerCamelCase que retorna Promise<CustomResponse>.
Contrato TS La función incluye un comentario que recuerda crear en contracts.ts los tipos de params, body y data. El scaffold deja CustomResponse como marcador explícito para reemplazarlo por un tipo de la integración.
Ruta y controller Registra el método y path normalizados en ExtensionRouteRegister.php. El controller es --controller-name o, si se omite, el nombre del feature. Si no existe, lo crea; si existe, agrega la action.
Action PHP Usa el mismo nombre lowerCamelCase de la función TS y devuelve return $this->respondJson(fn(): array => []);.
Cancelación Si el path ya existe en el árbol de rutas, no modifica nada, aunque el verbo HTTP sea distinto.

Endpoint consumido como envelope JSON

Este modo se elige cuando la integración necesita tomar una decisión con la respuesta completa, por ejemplo mostrar un mensaje, conservar errores o distinguir un resultado parcial.

make:integration-api-json sigue el mismo flujo que make:integration-api-data, pero la función de Surface usa serverClient.json y retorna el envelope tipado. Se debe usar cuando la UI necesita revisar success, message, errors o estados parciales.

API JSON 
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-api-json <feature> <nameFunction> <method> <path> --controller-name=<ControllerName>
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-api-json items inspectItems get /items/inspect --controller-name=Items
Envelope JSON Este modo conserva la respuesta completa del Gateway.
  • Surface Promise<ApiResponse<CustomResponse>> Importa ApiResponse cuando la firma lo necesita.
  • Gateway respondJson(fn(): array => []) La action base queda lista para devolver JSON.
  • Cancelación Aborta si falta el feature o si el path ya existe.

Endpoint consumido como HTML embebible

Este modo se elige cuando Gateway debe devolver estructura HTML lista para insertar, como un panel o fragment dinámico, en vez de datos que Surface tendría que convertir en marcado.

make:integration-api-html crea la base para que una integración Surface pida HTML remoto con serverClient.html. Además de la función api.ts, registra ruta, crea o completa controller y escribe un fragment SSR base.

API HTML 
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-api-html <feature> <nameFunction> <method> <path> --controller-name=<ControllerName>
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-api-html items fetchPanel get /items/panel --controller-name=Items
Salida Detalle
api.ts Agrega una función async lowerCamelCase que retorna Promise<string> y llama serverClient.html con método y path normalizados.
Controller Crea o completa el controller con una action que llama renderFragmentView('<feature>/<nameFunction>.fragment').
Vista SSR Crea resources/views/<feature>/<nameFunction>.fragment.php como partial embebible base.
Montaje Surface Si ese HTML debe activar comportamiento Surface, después se debe agregar un binding con make:fragment y declarar expect: { kind: "fragment", fragmentId: "..." } en la llamada real.
Cancelación Igual que data/json: aborta si falta la carpeta del feature o si el path ya existe en rutas.

Regla transversal de request

Un middleware se crea cuando varias rutas deben compartir una comprobación anterior al controller. Si la regla solo tiene sentido para una operación, corresponde al controller o al use case y no a este generador.

make:middleware crea un artefacto para evaluar o enriquecer el request antes de que llegue al controller. Es útil para reglas transversales de presentación HTTP, no para lógica de negocio. El comando no lo conecta a rutas existentes; después debe aplicarse en routing o usarse --middlewares cuando se genere una ruta nueva.

Middleware 
/raiz-del-proyecto/app-gateway> composer robo -- make:middleware <middlewareName>
/raiz-del-proyecto/app-gateway> composer robo -- make:middleware RequireDemoContext

Generador de contratos HTTP externos

Este generador toma la especificación publicada por una API externa y la convierte en código PHP que Gateway puede usar para describir cómo llamar esa API y cómo leer su respuesta. Sirve para que el outbound trabaje con contratos explícitos en lugar de payloads sueltos o mapeos improvisados.

El comando recibe una request signature, una response signature y un archivo Swagger/OpenAPI JSON. Con eso busca la operación que conecta ambas formas y escribe una request outbound con #[Endpoint] y una response DTO con sus dependencias internas.

Generar contrato HTTP 
/raiz-del-proyecto/app-gateway> composer robo http:contract <RequestSignature> <ResponseSignature> <swaggerPath>
/raiz-del-proyecto/app-gateway> composer robo http:contract CreateItemRequest CreateItemResponse ../tools/HttpContractGenerator/Specs/external-api.json
Argumento Detalle
<RequestSignature> Schema de request que debe aparecer en requestBody o coincidir con query parameters cuando la operación no tiene request body.
<ResponseSignature> Schema de response esperado en una respuesta HTTP 2xx. Si la response es array, la request implementa EndpointListRequest.
<swaggerPath> Archivo JSON de Swagger/OpenAPI. Se resuelve desde la raíz del workspace o desde el current working directory.
--force Sobrescribe archivos existentes. Sin --force, el writer omite archivos ya creados.

Cómo detecta el endpoint

  • Recorre paths y métodos HTTP válidos.
  • Busca la request en $ref dentro del requestBody.
  • Si no hay request body, compara query parameters con las propiedades del schema de request.
  • Busca la response en schemas de respuestas HTTP 2xx, incluyendo arrays y refs internos.

Qué genera

  • Request con #[Endpoint(method, path, responseClass)].
  • EndpointRequest o EndpointListRequest según la response.
  • DTOs internos marcados como @internal y prefijados con el contrato principal.
  • CustomPayloadRequestInterface cuando hay fechas que deben normalizarse.
Fechas y payload El generador normaliza fechas sin exponer propiedades crudas.
  • Tipos OpenAPI date / date-time Se generan como DateTimeImmutable con valor default.
  • Serialización Y-m-d / DateTimeInterface::ATOM Define cómo salen las fechas en payloads outbound.
  • Escape CustomPayloadRequestInterface Permite usar payload() cuando no conviene serializar propiedades públicas.
  • Fallback get_object_vars(...) Se usa cuando la request no declara payload propio.
Estructura PHP La clase principal conserva PSR-4 y los auxiliares quedan agrupados.
  • Archivo principal PSR-4 Una request por archivo y una response por archivo.
  • Auxiliares @internal Se incluyen en el mismo archivo si ayudan a mantener el contrato unido.
  • API pública Las clases internas no forman parte del contrato visible de la aplicación.

Generador de contratos Surface

Este generador evita volver a escribir a mano en TypeScript una forma que ya está descrita por una especificación. El resultado se nombra como contrato visible de Gateway para Surface, no como acceso directo de la UI al proveedor externo.

surface:contract usa el mismo Swagger/OpenAPI como fuente, pero escribe TypeScript local para Surface. El contrato se trata como shape visible de una ruta Gateway, aunque coincida con un DTO externo por passthrough.

Generar contrato Surface 
/raiz-del-proyecto/app-gateway> composer robo -- surface:contract <feature> <RequestSignature> <ResponseSignature> <swaggerPath>
/raiz-del-proyecto/app-gateway> composer robo -- surface:contract items CreateItemRequest CreateItemResponse ../tools/HttpContractGenerator/Specs/external-api.json
Argumento Detalle
<feature> Carpeta bajo app-surface/workspace/integrations. El comando crea la carpeta si no existe y escribe en su contracts.ts.
<RequestSignature> Schema que representa params o body enviados por Surface.
<ResponseSignature> Schema que representa data JSON visible desde Gateway. Si la operación devuelve array, el contrato se tipa localmente sin crear un alias final <ResponseSignature>Data.
--force Reemplaza el bloque generado para esa pareja request / response. Sin --force, no pisa un bloque ya generado.
Contrato Surface Genera tipos locales, no llamadas HTTP ni lógica de serialización.
  • Uso posterior api.ts / actions.ts Api tipa serverClient; actions arma el request desde valores de UI.
  • Formato export class + Partial<T> Clases con defaults y constructor parcial.
  • No genera interfaces / toJSON() / normalizeDate(...) La integración resuelve cualquier serialización especial.
  • Fechas string | Date | null Los campos date y date-time quedan como contrato visible de Surface.

Preparar la implementación guiada

La implementación guiada de Gateway, Bridge y Surface usa items y SearchItems como nombres didácticos. Se puede preparar con varios comandos pequeños. Cada comando cubre una convención concreta; ninguno decide por sí solo la arquitectura completa ni escribe la lógica final de la feature real.

El resultado esperado se explica desde Gateway: ruta, controller y use case, Bridge: envelope JSON y Surface: contracts.ts, api.ts, actions.ts y page.ts.

Scaffolding compuesto para SearchItems 
/raiz-del-proyecto/app-gateway> composer robo -- make:integration-page items --id=demo-items --layout=control

/raiz-del-proyecto/app-gateway> composer robo -- make:integration-api-data items searchItems post /items/search --controller-name=Item

/raiz-del-proyecto/app-gateway> composer robo -- make:use-case SearchItems --use-case-folder=Items

/raiz-del-proyecto/app-gateway> composer robo -- make:service ItemSearch --use-case=SearchItems

/raiz-del-proyecto/app-gateway> composer robo -- make:connector ItemSearch
Comando Prepara Se completa manualmente
make:integration-page Vista SSR simple, ruta de página, controller, integration.ts, page.ts, registry y menú control cuando corresponde. Formulario de búsqueda, selectores y comportamiento real del binding.
make:integration-api-data POST /items/search, action searchItems y función base en api.ts con serverClient.data(...). Reemplazar CustomResponse por ItemSearchResponse, tipar SearchItemsRequest y conectar el action con SearchItems::execute(...).
make:use-case Archivo SearchItems.php bajo Application/UseCase/Items. Implementar execute(...), declarar SearchItemsInput e inyectar el use case desde el constructor del controller.
make:service Archivo ItemSearchService.php y dependencia convencional en el use case cuando se indica --use-case=SearchItems. Expresar qué llamadas son $flow->required(...) y cuáles son $flow->optional(...).
make:connector Port ItemSearchConnectorInterface y adapter outbound ItemSearchConnector. Agregar manualmente el client outbound requerido y traducir cada resultado a ConnectorResult.
Contrato TypeScript surface:contract es opcional y depende del origen de la firma.

Si el contrato visible para Surface nace de Swagger/OpenAPI, se puede generar el bloque inicial de contracts.ts. Si ItemSearchResponse compone varias fuentes internas del Gateway y no existe una firma OpenAPI equivalente, corresponde declararlo manualmente junto a la integración.

Firma Surface desde OpenAPI, cuando aplica 
/raiz-del-proyecto/app-gateway> composer robo -- surface:contract items SearchItemsRequest ItemSearchResponse <swaggerPath>
  • No existe un comando compuesto que genere route, controller, use case, service, connector y UI final en una sola operación.
  • make:integration-api-data crea el puente progresivo, pero no crea use cases, services, connectors ni clients outbound.
  • El controller debe terminar llamando $this->searchItems->execute($input) desde respondJson(...).
  • Si la UI necesita inspeccionar message, errors o code directamente, se debe usar make:integration-api-json en lugar del modo data.

Flujos recomendados

Los comandos están pensados para componerse. Esta secuencia evita que un scaffolder invente dependencias antes de que exista una intención clara.

  1. Ejecutar make:route-use-case para crear route, controller y use case.
  2. Implementar input, validación y execute() dentro del use case.
  3. Si Surface consume JSON, validar el envelope en Bridge JSON.

  1. Crear la página base con make:integration-page si aún no existe.
  2. Si el endpoint devuelve JSON utilizable directamente, usar make:integration-api-data. Si se necesita leer el envelope completo, usar make:integration-api-json.
  3. Si el endpoint devuelve HTML embebible, usar make:integration-api-html y registra un binding posterior con make:fragment solo cuando ese fragment necesite comportamiento.
  4. Sustituir CustomResponse por tipos de contracts.ts y completa la llamada con params, body o expect según corresponda.

  1. Ejecutar make:use-case <UseCase> <Controller>.
  2. Si se necesita una action nueva, agregar --action=<method>.
  3. Si la ruta ya existía, confirmar que apunte a la action correcta.

Límites

Los generadores reducen trabajo mecánico, pero deben detenerse antes de tomar decisiones que requieren contexto humano. Esta tabla marca esas fronteras para reconocer cuándo el archivo generado es un punto de partida y cuándo corresponde completar arquitectura, contratos o lógica manualmente.

Límite Motivo
El scaffolder solo toca Surface en comandos explícitos. make:integration-page crea una página SSR conectada con una integración UI. make:fragment crea bindings de fragment y make:integration-api-* agrega funciones en api.ts. Ningún comando crea actions.ts ni lógica de negocio frontend.
El connector no nace con service client. Un connector puede usar varios clients, uno solo o una fuente no HTTP. El constructor debe expresar una decisión real.
El service no nace con connector. Un service puede ser composición de aplicación o puede no necesitar integración externa.
http:contract no toca DI. Generar DTOs y requests no significa que exista un client configurado ni un adapter listo.
surface:contract no crea integración UI. Solo escribe firmas TS en contracts.ts. El binding, api.ts y actions.ts siguen siendo decisiones de la integración.

Diagnóstico

El diagnóstico comienza por el efecto visible del comando: no aparece, no encuentra configuración, omite un archivo o no identifica un endpoint. Cada grupo propone primero la comprobación más barata y después desciende a rutas, firmas o configuración interna.

Comando no aparece

  • Ejecutar composer robo list.
  • Confirmar que el método exista en app-gateway/RoboFile.php.
  • Tener presente que los comandos viejos compuestos ya no son API.

Configuración no carga

  • Archivo raíz robo-configurations.json Debe existir en la raíz del workspace.
  • Bloques esperados extensionScaffolder / httpContractGenerator / surfaceContractGenerator Dependen del comando que se esté ejecutando.
  • Configuración alternativa --config=... Se debe usar solo para pruebas puntuales.

Archivo omitido

  • El writer no sobrescribe por defecto.
  • Usar --force si se requiere regenerar.
  • Antes de forzar, revisar cambios manuales existentes.

Endpoint no detectado

  • Confirmar el nombre exacto de request y response en schemas.
  • Revisar que la response esté en un status HTTP 2xx.
  • Validar que el Swagger/OpenAPI sea JSON válido.
