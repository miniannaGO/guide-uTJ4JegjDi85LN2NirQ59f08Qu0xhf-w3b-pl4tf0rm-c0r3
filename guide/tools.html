Tools: generadores de la solución

Referencia operativa para acelerar trabajo repetible: un generador prepara artefactos base de Extension y otro convierte especificaciones de APIs externas en contratos HTTP consumibles por Gateway. Surface tiene un comando separado para generar firmas TypeScript visibles al navegador. La guía muestra qué crean, cuándo usarlos y dónde termina la automatización.

Overview

Los tools del workspace existen para acelerar trabajo repetible, pero no para decidir arquitectura por el dev. El generador de artefactos de la solución crea archivos base de `Extension` siguiendo rutas, namespaces y defaults definidos en `robo-configurations.json`. El generador de contratos HTTP externos convierte una descripción Swagger/OpenAPI en PHP que Gateway puede usar para llamar APIs externas de forma consistente. El generador Surface crea firmas TypeScript para el contrato Gateway visible desde `app-surface`.

Ambos generadores de firmas conviven en tools/HttpContractGenerator. La salida Gateway/PHP vive en tools/HttpContractGenerator/Gateway, la salida Surface/TypeScript vive en tools/HttpContractGenerator/Surface y las piezas comunes viven en tools/HttpContractGenerator/Shared. Comparten lectura OpenAPI, reportes de escritura, utilidades de rutas y normalización de nombres, pero mantienen renderers y writers separados.

La idea práctica es simple: el comando crea lo que tiene una convención fuerte; el dev conecta lo que tiene intención de negocio. Por eso el scaffolder no tiene comandos gigantes para route + controller + use case + service + connector. Ese flujo se arma por pasos y con decisión explícita en cada frontera.

Regla central: `robo-configurations.json` es la configuración de los tools. Si una ruta, namespace, route file o destino outbound cambia, primero se actualiza esa configuración y después se ejecuta el comando.

La guía conceptual de Gateway explica por qué existen controllers, use cases, services, connectors y clients externos. Esta página explica cuándo conviene pedirle al scaffolder que escriba la base mecánica y cuándo debes detenerte a decidir diseño. Como regla práctica: usa un comando cuando el nombre, la carpeta y el wiring son convencionales; escribe o ajusta a mano cuando la decisión expresa comportamiento de aplicación.

Surface usa los tools de forma distinta: no genera pantallas completas, sino contratos TypeScript visibles para una integración concreta. Por eso surface:contract se relaciona con consumir endpoints Gateway, no con crear una integración UI de cero.

Configuración en robo-configurations.json

Los tools leen `robo-configurations.json` desde la raíz del workspace. También aceptan `--config=<ruta>` cuando quieres probar una configuración alternativa, pero la convención viva del proyecto debe mantenerse en el archivo raíz.

Sección Qué controla Detalle importante
extensionScaffolder.paths Destino físico de cada componente generado. Las rutas se resuelven dentro del workspace. Si una ruta sale del workspace, el resolver la rechaza.
extensionScaffolder.namespaces Namespace PHP para templates generados. Debe quedar alineado con PSR-4 de `app-gateway` y con la carpeta de destino.
extensionScaffolder.routeFiles Claves usadas por --route-file. Permite elegir si una ruta va a públicas, autenticadas, fragments o sesión.
extensionScaffolder.defaults Action, route file y service outbound por defecto. `outboundService` se usa cuando `make:service-client` no recibe nombre.
httpContractGenerator Destino de requests y responses generadas. El ejemplo apunta a `ExternalApi`; si el client externo cambia, actualiza path y namespace antes de generar.
surfaceContractGenerator Destino de firmas TypeScript para Surface. integrationsBasePath apunta a las integraciones UI y contractsFileName define el archivo que recibirá los bloques generados.

Generador de artefactos de la solución

Este generador prepara archivos iniciales para los artefactos más habituales de una solución en `Extension`: rutas, controllers, casos de uso, services, connectors, service clients, providers outbound y middleware. Acelera la parte repetible, pero no decide si un artefacto debe existir ni qué responsabilidad debe tener.

La ejecución sale de `app-gateway/RoboFile.php` y usa la configuración del workspace para elegir rutas, namespaces y defaults. Internamente resuelve qué artefacto crear, renderiza PHP, escribe archivos y aplica ediciones pequeñas en rutas, classes y `AppProvider.php`.

# Comando Crea Integración opcional
1 make:route-controller Ruta + controller. Ninguna
2 make:route-use-case Ruta + controller + use case. Carpeta del use case.
3 make:use-case Use case. Controller existente, carpeta del use case. y action.
4 make:service Service. Use case existente.
5 make:connector Port + connector. Ninguna
6 make:service-client ServiceClient + provider + import en AppProvider. Ninguna
7 make:middleware Middleware HTTP. Ninguna
El orden recomendado es crear solo el artefacto necesario y conectar manualmente lo que expresa intención de aplicación.
Protección Qué evita Cómo actuar
Ruta existente por path Duplicar una URL aunque el verbo HTTP sea distinto. Cambia el path.
Controller inexistente en make:use-case Crear un use case que pretendía integrarse a un controller que no existe. Crea primero la ruta/controller o ejecuta make:use-case sin controller.
Duplicado de action Sobrescribir métodos existentes como index. El scaffolder usa index1, index2 y así sucesivamente cuando debe crear una action nueva.

Punto HTTP mínimo

`make:route-controller` crea una entrada HTTP sin asumir todavía una intención de aplicación compleja: registra la ruta, crea el controller y apunta a una action. Úsalo cuando primero necesitas abrir la superficie HTTP y luego decidir si la lógica merece un use case.

Ruta + controller 
composer robo -- make:route-controller get /demo Demo
Antes de escribir el controller, el comando normaliza <path> y lo busca en todos los archivos configurados en extensionScaffolder.routeFiles. La búsqueda ignora el verbo HTTP: si existe GET /demo, ejecutar luego POST /demo se considera duplicado. En ese caso no se crea controller, no se agrega ruta y --force tampoco pisa esa protección.
Argumento Significado Ejemplo
<method> Verbo HTTP aceptado por el router. get, post
<path> Ruta que se registra. Se normaliza con `/` inicial. /demo
<controllerName> Nombre base del controller. Demo genera DemoController
--action Método del controller. Si se omite, usa `extensionScaffolder.defaults.action`. --action=show
--route-file Clave de `extensionScaffolder.routeFiles`. public, auth
--middlewares Lista separada por comas para la ruta generada. RequireAuthentication

Endpoint con intención

`make:route-use-case` crea el recorrido base de una acción de aplicación: ruta, controller y use case. Es el flujo cómodo para endpoints JSON donde la intención ya está clara, pero todavía no hace falta componer services, connectors o dependencias externas.

Ruta + controller + use case 
composer robo -- make:route-use-case post /auth/demo Demo CreateDemo --use-case-folder=Demo --action=create
  • El controller generado responde con `respondJson(...)` y llama a `execute()` del use case.
  • El use case generado extiende `AppUseCase` y usa `run(...)`.
  • Si el endpoint luego requiere composición externa, crea service, connector y service client con comandos separados.
Validación Resultado
La ruta ya existe, incluso con otro method. El comando termina sin crear controller, use case ni ruta. La ruta se compara ya normalizada y contra todos los route files configurados.
Ya existe un use case con el mismo nombre. El comando termina sin tocar nada aunque el archivo esté en otra carpeta bajo Application/UseCase. La regla protege el nombre corto de clase para evitar dos archivos visualmente iguales en namespaces distintos.
El controller no existe. Crea el controller completo, crea el use case y registra la ruta hacia la action resuelta.
El controller ya existe. No reemplaza el archivo: inyecta el use case, agrega una action JSON nueva y registra la ruta hacia esa action.
La action solicitada ya existe. Usa el primer nombre libre con sufijo numérico: index, index1, index2, etc.
--use-case-folder Nombra la carpeta bajo Application/UseCase. Si la carpeta ya existe, se reutiliza; si falta, se crea solo para alojar el use case.

Intención de aplicación

`make:use-case` crea una intención ejecutable sin depender de una ruta específica. Sirve para aislar una decisión de aplicación, validar input y devolver un resultado normalizado. Si pasas un controller como segundo argumento, el comando lo inyecta ahí; si además pasas `--action`, agrega una action JSON que lo llama.

Use case 
composer robo -- make:use-case ListItems --use-case-folder=Demo

composer robo -- make:use-case ListItems ExternalItem --use-case-folder=Demo --action=list
Forma Resultado
make:use-case <useCaseName> Solo crea el use case.
make:use-case <useCaseName> [controllerName] Crea el use case e inyecta la dependencia en el controller.
make:use-case <useCaseName> [controllerName] --action=list Además agrega una action JSON que llama al use case.
make:use-case nunca crea controllers ni rutas. Si pasas [controllerName], ese controller debe existir antes de ejecutar el comando; si no existe, el scaffolder no crea el use case para evitar una integración incompleta. Si el use case destino ya existe en cualquier carpeta bajo Application/UseCase, también se detiene sin modificar el controller. Cuando se agrega una action y el nombre ya está ocupado, se usa la misma secuencia incremental: index, index1, index2. --use-case-folder es la opción descriptiva para indicar la carpeta bajo Application/UseCase; --feature solo queda como alias heredado.

Composición de aplicación

`make:service` crea un artefacto para coordinar trabajo que el use case no debería cargar directamente: transformación, varias fuentes, fallback o parcialidad. Si pasas el use case como segundo argumento, lo inyecta en ese use case. La regla de arquitectura sigue aplicando: no crees un service si solo va a delegar una única llamada sin agregar significado.

El use case destino se busca recursivamente bajo Application/UseCase. Ya no se pasa carpeta para make:service: si existe un único archivo con ese nombre, se edita; si hay varios, el comando aborta porque el filesystem ya está ambiguo y sería peligroso elegir por ti.

Service 
composer robo -- make:service ExternalItem

composer robo -- make:service ExternalItem ListItems

La decisión de usar service se explica en Services y connectors. Úsalo para composición, transformación, varias fuentes, fallback o parcialidad; no para delegación vacía.

Situación Comportamiento
Solo pasas <serviceName>. Crea el service y no modifica ningún use case.
Pasas [useCaseName] o --use-case. Crea el service si falta y lo vincula al constructor del use case existente.
El service ya existe. No lo reemplaza sin --force, pero igual intenta vincularlo al use case indicado.
El use case indicado no existe. Conserva el service creado y muestra un aviso; no inventa un use case.
Hay varios use cases con el mismo nombre. No crea ni modifica nada. Corrige el duplicado antes de vincular el service para evitar elegir un archivo equivocado.

Salida hacia una dependencia externa

`make:connector` crea el contrato que consume la aplicación y el adapter outbound que lo implementa. Es la frontera para traducir payloads, errores técnicos y respuestas externas a `ConnectorResult`. El connector generado no recibe un `ServiceClient` por constructor: puede usar uno, varios o ningún client HTTP, y esa decisión pertenece a quien implementa el adapter.

Port + connector 
composer robo -- make:connector ExternalItem
Artefacto Ubicación Responsabilidad
Port Application/Port/<Name>ConnectorInterface.php Contrato que consume la aplicación.
Connector Infrastructure/Outbound/Connector/<Name>Connector.php Adapter outbound concreto que devuelve `ConnectorResult`.
La carpeta del connector ya no depende del nombre del service client externo. Los clients viven bajo `Infrastructure/Outbound/Client/<Service>/...`; los connectors viven bajo `Infrastructure/Outbound/Connector/...`.

Cliente HTTP externo

`make:service-client` prepara el transporte técnico para hablar con una API externa: crea el client HTTP concreto, su provider outbound y el import de ese provider en `Extension/Bootstrap/Container/AppProvider.php`. Este comando sí toca DI porque el service client necesita recibir un `ServiceDefinition` desde el contenedor.

Service client + provider + AppProvider 
composer robo -- make:service-client ExternalApi
  • Genera Infrastructure/Outbound/Client/ExternalApi/ExternalApiServiceClient.php.
  • Genera Bootstrap/Container/Outbound/ExternalApiProvider.php.
  • Importa el provider outbound desde Bootstrap/Container/AppProvider.php.
  • No crea requests ni responses de endpoints. Para eso usa http:contract.

Regla transversal de request

`make:middleware` crea un artefacto para evaluar o enriquecer el request antes de que llegue al controller. Es útil para reglas transversales de presentación HTTP, no para lógica de negocio. El comando no lo conecta a rutas existentes; después debes aplicarlo en routing o usar `--middlewares` cuando generes una ruta nueva.

Middleware 
composer robo -- make:middleware RequireDemoContext

Generador de contratos HTTP externos

Este generador toma la especificación publicada por una API externa y la convierte en código PHP que Gateway puede usar para describir cómo llamar esa API y cómo leer su respuesta. Sirve para que el outbound trabaje con contratos explícitos en lugar de payloads sueltos o mapeos improvisados.

El comando recibe una request signature, una response signature y un archivo Swagger/OpenAPI JSON. Con eso busca la operación que conecta ambas formas y escribe una request outbound con `#[Endpoint]` y una response DTO con sus dependencias internas.

Generar contrato HTTP 
composer robo http:contract CreateItemRequest CreateItemResponse ../tools/HttpContractGenerator/Specs/external-api.json
Argumento Detalle
<RequestSignature> Schema de request que debe aparecer en `requestBody` o coincidir con query parameters cuando la operación no tiene request body.
<ResponseSignature> Schema de response esperado en una respuesta HTTP 2xx. Si la response es array, la request implementa `EndpointListRequest`.
<swaggerPath> Archivo JSON de Swagger/OpenAPI. Se resuelve desde la raíz del workspace o desde el current working directory.
--force Sobrescribe archivos existentes. Sin `--force`, el writer omite archivos ya creados.

Cómo detecta el endpoint

  • Recorre `paths` y métodos HTTP válidos.
  • Busca la request en `$ref` dentro del `requestBody`.
  • Si no hay request body, compara query parameters con las propiedades del schema de request.
  • Busca la response en schemas de respuestas HTTP 2xx, incluyendo arrays y refs internos.

Qué genera

  • Request con `#[Endpoint(method, path, responseClass)]`.
  • `EndpointRequest` o `EndpointListRequest` según la response.
  • DTOs internos marcados como `@internal` y prefijados con el contrato principal.
  • `CustomPayloadRequestInterface` cuando hay fechas que deben normalizarse.
Fechas OpenAPI `date` y `date-time` se generan como `DateTimeImmutable` con default `1900-01-01 00:00:00+00:00`. Para payloads, `date` se serializa como `Y-m-d` y `date-time` usa `DateTimeInterface::ATOM`.

Generador de contratos Surface

surface:contract usa el mismo Swagger/OpenAPI como fuente, pero escribe TypeScript local para Surface. El contrato se trata como shape visible de una ruta Gateway, aunque coincida con un DTO externo por passthrough.

Generar contrato Surface 
composer robo -- surface:contract items CreateItemRequest CreateItemResponse ../tools/HttpContractGenerator/Specs/external-api.json
Argumento Detalle
<feature> Carpeta bajo app-surface/workspace/integrations. El comando crea la carpeta si no existe y escribe en su contracts.ts.
<RequestSignature> Schema que representa params o body enviados por Surface.
<ResponseSignature> Schema que representa data JSON visible desde Gateway. Si la operación devuelve array, el contrato se tipa localmente sin crear un alias final <ResponseSignature>Data.
--force Reemplaza el bloque generado para esa pareja request / response. Sin --force, no pisa un bloque ya generado.
Este comando no genera llamadas HTTP. Después de crear las firmas, api.ts las importa para tipar serverClient y actions.ts arma el request desde valores de UI. Surface genera export class con defaults y constructor Partial<T>; no genera interfaces, comentarios de bloque, toJSON() ni normalizadores de fecha. Los campos OpenAPI date y date-time quedan como string | Date | null; si una integración necesita serialización especial, debe resolverla en su acción o request builder.

Flujos recomendados

Los comandos están pensados para componerse. Esta secuencia evita que un scaffolder invente dependencias antes de que exista una intención clara.

  1. Ejecuta make:route-use-case para crear route, controller y use case.
  2. Implementa input, validación y `execute()` dentro del use case.
  3. Si Surface consume JSON, valida el envelope en Bridge JSON.

  1. Ejecuta make:use-case <UseCase> <Controller>.
  2. Si necesitas una action nueva, agrega --action=<method>.
  3. Si la ruta ya existía, confirma que apunte a la action correcta.

Secuencia sugerida 
composer robo -- make:service-client ExternalApi
composer robo http:contract GetExternalItemRequest GetExternalItemResponse ../tools/HttpContractGenerator/Specs/external-api.json
composer robo -- surface:contract demo-items GetExternalItemRequest GetExternalItemResponse ../tools/HttpContractGenerator/Specs/external-api.json
composer robo -- make:connector ExternalItem
composer robo -- make:service ExternalItem GetExternalItem
  1. Valida `services.json` y variables `API_<SERVICIO>_*`.
  2. Implementa el connector a mano usando el service client que corresponda.
  3. Decide en el use case si usa `takeOrAbort(...)` o `runConnectorFlow(...)`.
  4. Si Surface consume la ruta Gateway, usa surface:contract para generar la firma TS y luego completa api.ts / actions.ts.

Límites

Límite Motivo
El scaffolder no crea Surface. Surface se activa por `data-surface-*` y registry UI. La página o fragment debe decidir explícitamente su bridge.
El connector no nace con service client. Un connector puede usar varios clients, uno solo o una fuente no HTTP. El constructor debe expresar una decisión real.
El service no nace con connector. Un service puede ser composición de aplicación o puede no necesitar integración externa.
`http:contract` no toca DI. Generar DTOs y requests no significa que exista un client configurado ni un adapter listo.
`surface:contract` no crea integración UI. Solo escribe firmas TS en contracts.ts. El binding, api.ts y actions.ts siguen siendo decisiones de la integración.

Diagnóstico

Comando no aparece

  • Ejecuta composer robo list.
  • Confirma que el método exista en app-gateway/RoboFile.php.
  • Recuerda que los comandos viejos compuestos ya no son API.

Configuración no carga

  • Verifica que `robo-configurations.json` esté en la raíz del workspace.
  • Revisa que existan `extensionScaffolder`, `httpContractGenerator` o `surfaceContractGenerator` según el comando.
  • Usa --config=... solo para pruebas.

Archivo omitido

  • El writer no sobrescribe por defecto.
  • Usa --force si quieres regenerar.
  • Antes de forzar, revisa cambios manuales existentes.

Endpoint no detectado

  • Confirma el nombre exacto de request y response en schemas.
  • Revisa que la response esté en un status HTTP 2xx.
  • Valida que el Swagger/OpenAPI sea JSON válido.
