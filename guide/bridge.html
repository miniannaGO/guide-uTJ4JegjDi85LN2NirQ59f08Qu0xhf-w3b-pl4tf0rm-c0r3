SSR + Progressive Enhancement

El gateway renderiza HTML usable. Surface llega después y activa comportamiento si encuentra atributos declarativos.

Para ver las piezas por separado, se recomienda abrir Views, JSON y assets y Runtime de pages y fragments.

Los ejemplos deben leerse como contratos, no como dominio. Lo importante es quién produce HTML/JSON, quién lo consume y cómo se propagan éxito, parcialidad, sesión, assets y errores.

Lectura guiada del bridge

El bridge es la parte que más confunde al principio porque no es una carpeta única. Es el acuerdo entre dos mundos: Gateway produce HTML/JSON/headers/assets; Surface los consume sin inventar negocio paralelo.

Por eso esta página no intenta volver a explicar todo Gateway ni todo Surface. Su especialidad es la frontera: qué formato cruza de un lado al otro, quién lo produce, quién lo valida y qué se considera contrato roto. Cuando leas una sección del bridge, pregúntate siempre: “¿qué lado promete esto?” y “¿qué lado lo consume?”.

Para seguir una interacción completa, léela como una entrega de responsabilidades: Gateway renderiza HTML SSR, Surface monta una integración, Surface pide datos o HTML con serverClient, Gateway pasa por ruta, controller y use case, y la respuesta vuelve como envelope JSON o fragment HTML validable.

Resumen Detalle que leerás después Sección
HTML SSR es la base. Gateway entrega una página o fragment usable. Surface solo activa lo declarado por atributos. Contratos HTML
data-surface-* es un contrato. El valor debe coincidir con integration id o fragment key. No es decoración. Mapa de contratos
JSON siempre viaja en envelope. Surface no acepta JSON libre: necesita success, data, errors y status coherente. JSON envelope
Parcialidad no es fallo total. Gateway puede devolver data usable con errores secundarios; Surface muestra advertencia. Errores HTTP
Sesión cruza por headers. X-TAB-SESSION va hacia Gateway; X-REMAINING vuelve hacia Surface. Headers de sesión
Assets se resuelven en Gateway. Surface compila; Gateway lee manifest y emite CSS/JS. Assets Vite

Orden sugerido dentro de esta página: HTML, JSON, flujo externo, sesión, seguridad, errores, assets, mapa de contratos, matriz E2E, ownership y flujo completo.

Contratos HTML

Cuando este HTML deba crearse desde cero, se debe consultar Crear una página SSR o Crear un fragment dinámico.

Page root 
<div data-surface-page="demo-items">
    ...
</div>
Fragment root 
<section data-surface-fragment="item-summary">
  ...
</section>
  • El atributo `data-surface-page` representa la integración UI de una página completa.
  • El atributo `data-surface-fragment` representa HTML SSR que puede aparecer después de una llamada `serverClient.html(...)` validada como HTML embebible; si se espera ese fragment concreto, Surface declara `expect`.
  • Surface puede activar, escuchar eventos y reemplazar HTML, pero no debería inventar una estructura que el gateway ya sabe renderizar.

Cómo leer los atributos como contrato

Atributo Significado Archivo que lo declara Archivo que lo cumple
data-surface-page="demo-items" Esta página tiene comportamiento UI propio. resources/views/items/index.page.php workspace/integrations/items/integration.ts
data-surface-fragment="item-summary" Este HTML puede tener binding propio. resources/views/items/summary.fragment.php workspace/integrations/items/fragments/summary.ts
id, data-* locales Selectores internos usados por un binding. View o fragment SSR. page.ts o fragment binding.

Envelope JSON

Surface espera un envelope compatible con `UseCaseResult`. Esto permite éxito limpio, parcialidad y fallos bloqueantes.

La forma interna del envelope pertenece al cliente HTTP de plataforma. La forma de data que una integración consume se declara en workspace/integrations/<feature>/contracts.ts como contrato Gateway visible para Surface. Si Gateway hace passthrough de un DTO externo, el shape puede coincidir, pero Surface no debe nombrarlo como contrato del proveedor externo.

El endpoint que produce este envelope se arma desde Controllers, Use cases y Crear un endpoint JSON.

Envelope conceptual 
{
  success: true,
  data: {},
  message: "Operación completada",
  errors: [],
  code: 200,
  errorMeta: null
}
Respuesta parcial 
{
  success: true,
  data: {
    id: 3021,
    displayName: "Cliente de ejemplo",
    total: 489.9,
    state: "issued"
  },
  message: "Recurso consultado con advertencias",
  errors: ["No se pudo cargar el detalle opcional"],
  code: 200,
  errorMeta: null
}
  • `success=true` y `errors=[]` es éxito completo.
  • `success=true` con errores permite mostrar datos usables y una advertencia de degradación.
  • `success=false` representa un fallo bloqueante; Surface no debe tratarlo como data válida.

Qué hace Surface con cada respuesta

Respuesta Gateway HTTP típico Surface debe
success=true, sin errores 200 Usar data o continuar flujo normal.
success=true, con errores 200 Usar data disponible y mostrar advertencia parcial.
success=false 400, 401, 403, 409, 422 o 500 Detener la acción y mostrar error normalizado.
HTML embebible válido 200 Insertarlo en el DOM; si es fragment montable, validar el data-surface-fragment esperado.
JSON, redirect, layout o page cuando se esperaba HTML Cualquiera Tratarlo como error de contrato, no como fragment.

Variables que conectan ambos lados

Variable Impacta en Contrato
BASE_URI Gateway base URL SSR y base de assets Vite. Surface no lo concatena en features; consume window.__BASE_URL__ para HTTP.
PUBLIC_PATH Salida de Vite y helpers de Gateway. Assets viven en app-gateway/{PUBLIC_PATH}/ui-assets.
IS_PRODUCTION Manifest, sourcemaps, cache y detalles de error. Producción debe ser estricta y no servir fallbacks viejos.
VERSION_DEPLOY Versionado/cache busting de assets. Ayuda a que navegador y despliegue no queden desalineados.
MENU_LAYOUT Startup de Surface. Solo afecta layout visual, no permisos ni rutas.
SPEED_UP_BUILD Build de Vite. No pertenece al runtime PHP ni se inyecta en __APP_ENV__.

Flujo externo completo

Cuando una pantalla necesita datos de una API HTTP externa, la frontera pública para Surface sigue siendo el gateway. El proveedor externo queda detrás de connector, service y use case.

Para implementar la parte externa, continúa en API HTTP clients externos o en Consumir un servicio externo.

Contrato visible para Surface

Límite del navegador Surface ve el contrato Gateway, no los detalles del proveedor.
  • No visible services.json También quedan fuera tokens, URLs y DTOs externos.
  • Tipos locales contracts.ts Clases con defaults y constructor `Partial<T>`.
  • Cliente api.ts / serverClient Tipa llamadas al Gateway visible desde Surface.
  • Acción UI actions.ts / page.ts Arma el request desde valores de la página o fragment.
Robo como ayuda Usa el esqueleto para apoyar el puente, no para definirlo.
  • Page SSR make:integration-page Crea la página base y la integración Surface.
  • Fragments make:fragment Registra bindings dentro de una integración existente.
  • API progresiva make:integration-api-data/json/html Agrega `api.ts`, ruta y action Gateway coordinadas.
  • Contrato final CustomResponse -> contracts.ts Sustituye el marcador por tipos locales de Surface.
Surface 
// contracts.ts
export class ItemSummaryRequest {
  public itemId: number = 0;

  constructor(init: Partial<ItemSummaryRequest> = {}) {
    Object.assign(this, init);
  }
}

export class ItemSummary {
  public id: number = 0;
  public displayName: string = "";
  public total: number = 0;
  public state: string = "";

  constructor(init: Partial<ItemSummary> = {}) {
    Object.assign(this, init);
  }
}

// api.ts
const summary = await serverClient.data<ItemSummary, ItemSummaryRequest>("/items/summary", {
  method: "GET",
  params: new ItemSummaryRequest({ itemId: 3021 }),
});
Gateway 
public function summary(): HttpResponseInterface
{
  $itemId = (int) $this->request->getQuery('itemId', 0);

  return $this->respondJson(
    fn() => $this->getItemSummary->execute($itemId)

}

Headers de sesión

Surface sincroniza estos headers desde HTTP, sesión y errores UI. Si algo falla, debe revisarse Ayuda.

Header Lo envía Lo usa Propósito
X-TAB-SESSION Surface Gateway Identificar sesión por pestaña.
X-REMAINING Gateway Surface Sincronizar contador de expiración.
X-Correlation-Id Gateway Navegador, logs y soporte técnico Rastrear una request entre UI, Gateway y upstreams.
Accept Surface o navegador Gateway Indicar si se espera JSON, HTML completo o fragment HTML.

Ciclo de vida de tab session

  1. Surface obtiene o crea un identificador de pestaña.
  2. En cada request al gateway, serverClient envía X-TAB-SESSION.
  3. Gateway resuelve la tab session antes del use case cuando la ruta lo requiere.
  4. Gateway puede refrescar o cerrar la sesión desde controllers/middleware. El refresh se limita por SESSION_REFRESH_WINDOW y SESSION_REFRESH_COOLDOWN.
  5. Gateway responde X-REMAINING para que Surface actualice el contador y emita el warning que el layout convierte en modal según SESSION_EXPIRY_ALERT.

Refresh, ventana y cooldown

El bridge de sesión no renueva la tab solo porque haya tráfico. Gateway mira los timestamps guardados en tabs.{tabId}.metadata y toma una decisión sencilla: renovar solo cuando ya falta poco y cuando no se renovó hace muy poco.

Pregunta Variable Ejemplo
¿La tab ya está cerca de vencer? SESSION_REFRESH_WINDOW Si vence a las 12:10:00 y son las 12:09:35, faltan 25 segundos. Con ventana de 30, sí puede renovar.
¿Ya pasó suficiente tiempo desde el último refresh? SESSION_REFRESH_COOLDOWN Si se refrescó a las 12:09:35 y entra otra request a las 12:09:36, no se renueva otra vez.

Cuando ambas respuestas son "sí", Gateway actualiza refreshedAtUnix y recalcula expiresAtUnix con SESSION_TIME. Si una respuesta es "no", la request puede continuar, pero X-REMAINING seguirá mostrando el vencimiento anterior. SESSION_REFRESH_COOLDOWN no suma tiempo por sí mismo: solo evita escribir una nueva expiración demasiado pronto; aunque haya pasado el cooldown, Gateway vuelve a refrescar únicamente si la tab está otra vez dentro de SESSION_REFRESH_WINDOW.

Cómo trabaja entre pestañas

El bridge separa dos identidades que suelen confundirse: la cookie PHP identifica la sesión del navegador frente al servidor; el X-TAB-SESSION identifica la pestaña concreta dentro de esa sesión. Por eso dos pestañas pueden compartir cookie, pero Gateway puede leer o limpiar entradas distintas bajo $_SESSION['tabs'].

Capa Qué conserva Qué envía o recibe
Navegador Cookie PHP compartida por el sitio. Lo manda automáticamente en cada request.
Surface Id de pestaña en sessionStorage y contexto en memoria. Envía X-TAB-SESSION y lee X-REMAINING.
Gateway Mapa tabs.{tabId} dentro de $_SESSION y mensajes temporales bajo _flash.{tabId}. Resuelve la tab, valida expiración y responde el tiempo restante.
Mantenimiento Última limpieza en _maintenance.tabsCleanupLastRunUnix. Ejecuta limpieza solo cada SESSION_CLEANUP_INTERVAL.

Mensajes flash por pestaña

Los mensajes flash no son headers ni JSON. Gateway los guarda en la sesión PHP bajo _flash.{tabId} para que una acción pueda redirigir y mostrar un aviso en el siguiente HTML SSR. AppController::flashMessage(...) escribe el mensaje y AppController::pullFlashMessages(...) lo consume al renderizar la vista destino.

Surface no decide esa persistencia temporal: solo recibe el HTML resultante y monta comportamiento si la vista lo declara con data-surface-*.

Variables de tiempo

Las variables de sesión no tienen todas el mismo dueño. Gateway decide expiración, refresh y limpieza. Surface solo decide cuándo mostrar el aviso al usuario, usando el tiempo restante que Gateway le devuelve.

Variable Dueño Significado
SESSION_TIME Gateway Minutos de vida asignados al emitir o refrescar una tab.
SESSION_REFRESH_WINDOW Gateway Segundos restantes desde los que una tab puede extenderse.
SESSION_REFRESH_COOLDOWN Gateway Segundos mínimos entre escrituras de refresh para la misma tab. El código exige que haya pasado más de ese valor, no exactamente ese valor.
SESSION_CLEANUP_INTERVAL Gateway Segundos mínimos entre barridos de tabs expiradas por sesión PHP.
SESSION_CLEANUP_LAST_RUN_KEY Gateway Ruta interna donde se guarda el timestamp Unix del último barrido.
SESSION_EXPIRY_ALERT Surface Segundos restantes para emitir el warning de expiración.

Si una acción depende de sesión, el contrato no pertenece a una integración UI concreta: pertenece al bridge HTTP entre ambos lados.

CSRF y tab session

CSRF y tab session cruzan Gateway y Surface, pero resuelven problemas distintos. Esa diferencia evita errores difíciles: un token CSRF no identifica una pestaña, y una tab session no reemplaza un token CSRF.

Dato Viaja por Lo produce Lo consume
_csrf Campo hidden de formulario SSR. CsrfTokenManager en Gateway. Controller que procesa el formulario.
_tab Campo hidden de formulario si existe. ensureTabSession() en Surface. Gateway al crear o asociar sesión de pestaña.
X-TAB-SESSION Header HTTP de serverClient. Hooks de sesión de Surface. Resolver y middleware de Gateway.
X-REMAINING Header HTTP de respuesta. Gateway al emitir la response. Contador de sesión de Surface.

Checklist al tocar autenticación

  1. La vista de acceso debe renderizar el campo CSRF.
  2. Surface debe llamar ensureTabSession() en layout access/control.
  3. El login debe validar CSRF antes de ejecutar intención de aplicación.
  4. Las rutas autenticadas deben resolver tab session antes del use case.
  5. Surface debe reaccionar a 401/403 como sesión inválida.
  6. El tiempo restante debe viajar desde Gateway, no calcularse a partir de estimaciones en la UI.

Contratos de error HTTP

El bridge no solo transporta casos exitosos. También define cómo viaja un error para que Gateway y Surface no dupliquen decisiones. Gateway clasifica el error; Surface lo interpreta para mostrar UI.

Origen Gateway HTTP típico Surface lo convierte en Qué debe ver el usuario
BAD_REQUEST 400 UserActionError Mensaje corregible por acción del usuario.
VALIDATION 422 UserActionError Validación clara, no stack trace.
CONFLICT 409 UserActionError Conflicto de estado que puede entender.
AUTHENTICATION_REQUIRED o FORBIDDEN 401 o 403 SessionError Sesión inválida, vencida o sin permiso.
DEPENDENCY_UNAVAILABLE upstream 502 FatalError o parcial si hay data usable. Advertencia o error de dependencia externa.
DEPENDENCY_UNAVAILABLE transport 503 FatalError. No se pudo conectar con una dependencia.

Debug, producción y errorMeta

  • errorMeta puede traer detalle técnico solo cuando el runtime permite exponerlo.
  • En producción, Surface debe confiar en message, errors y code, no en detalles internos.
  • Si Surface esperaba HTML y recibe JSON de error, primero intenta leer el envelope y luego muestra el error normalizado.
  • Si Surface esperaba JSON y la respuesta no tiene envelope, eso es error de contrato, no un dato incompleto.

Estados completos del bridge

Estado Gateway debe emitir Surface debe hacer Señal de diagnóstico
Éxito HTML text/html, body no vacío y atributos declarativos correctos si hay UI. Mostrar HTML y montar page/fragment si corresponde. data-surface-*-status="mounted".
Éxito JSON success=true, data usable y errors=[]. Usar data sin advertencia. Status HTTP 200.
Parcialidad success=true, data usable y errors[] con mensajes visibles. Usar data y mostrar advertencia desde partialReporter. Response observable con cantidad de errores y origen.
Fallo bloqueante conocido success=false, status acorde y mensaje seguro. Convertir por status a UserActionError, SessionError o FatalError. message, errors[] y code.
Error de contrato Ocurre cuando se esperaba HTML/JSON y la forma real no coincide. Lanzar HttpContractError. Content-Type, body vacío, JSON sin envelope o HTML con forma de JSON.
Error inesperado Error handler central, mensaje seguro y X-Correlation-Id. Mostrar error global y conservar diagnóstico. Logs Gateway y telemetry del request.

Assets Vite

Surface genera assets, gateway los resuelve. Las integraciones UI no deberían construir rutas públicas de assets manualmente.

La configuración de build está en Vite, styles y assets, y los valores de ruta se documentan en Archivo .env.

Modo Comportamiento correcto
Desarrollo Puede existir fallback razonable y sourcemaps para depurar.
Producción El manifest es fuente de verdad. Si falta, el gateway debe fallar claro.
Integración UI No construye rutas a assets públicos; importa módulos y deja que Vite/Gateway resuelvan.
View PHP Usar vite_styles() y vite_script().

Mapa de contratos

El bridge no es una carpeta física ni una cuarta arquitectura. Es el nombre de los acuerdos entre Gateway y Surface. Cuando el acuerdo está claro, una vista, un endpoint o un binding pueden cambiar sin alterar el contrato del otro lado.

Contrato Lo produce Lo consume Regla simple
HTML SSR Gateway views Browser y Surface runtime Debe ser útil incluso antes de que cargue JavaScript.
data-surface-page View SSR mountPages(...) Debe coincidir con UiIntegration.id.
data-surface-fragment Fragment SSR FragmentRuntime Debe existir en el registry de fragments de la integración.
JSON envelope respondJson(...) serverClient Siempre debe tener success booleano.
Headers de sesión Gateway y Surface Ambos lados X-TAB-SESSION identifica pestaña; X-REMAINING sincroniza tiempo.
Assets Vite Surface build Gateway view layer Gateway resuelve manifest; Surface no arma URLs públicas a mano.
  • Si cambia un atributo HTML compartido, deben revisarse view SSR, registry de Surface y fragment binding.
  • Si cambia el envelope JSON, deben revisarse Gateway response y serverClient.
  • Si cambia sesión, deben revisarse middleware/Gateway y hooks HTTP de Surface al mismo tiempo.
  • Si cambian assets, deben revisarse Vite, manifest y helpers de view.

Matriz Core / Extension → Surface

Esta es la lectura completa del bridge: Core ofrece mecanismos, Extension declara la capacidad concreta y Surface la activa sin convertirse en una segunda aplicación. Debe usarse para diseñar una feature desde cero antes de abrir archivos.

Escenario Core Gateway Extension Gateway Surface Estado visible
Navegar a una página Router, middleware pipeline, controller invoker, ViewResponse. Ruta, controller, use case opcional y view SSR. Si hay data-surface-page, monta integración; si no, deja HTML estático. Página usable; error de render se presenta por handler central.
Ejecutar acción JSON UseCaseResult, ApiResponse, envelope y status resolver. Controller adapta request y use case decide éxito, parcialidad o fallo. serverClient.data/json valida contrato y normaliza errores. Data nueva, advertencia parcial o feedback de error.
Insertar contenido dinámico FragmentResponse, layout de fragment y contrato HTML. Endpoint que renderiza partial/fragment desde datos de aplicación. serverClient.html, validación de HTML embebible, inserción DOM y contentMount. HTML activo o error de contrato si llegó JSON, redirect, layout completo o page inesperada.
Consumir proveedor externo requerido Outbound client, mapper, ConnectorResult y takeOrAbort. Connector traduce upstream; use case bloquea si falta la dependencia. Solo ve endpoint Gateway. Éxito si hay data; fallo bloqueante si la dependencia era obligatoria.
Consumir proveedor externo opcional ConnectorFlowInterface y cierre parcial. Service usa required para lo esencial y optional para degradación. Usar data disponible y mostrar aviso desde partial reporter. success=true con errors[].
Sesión, CSRF o expiración Request, middleware, headers, error kind y response. Middleware/controlador valida request antes del use case. Envía X-TAB-SESSION, lee X-REMAINING y maneja SessionError. Acceso permitido, error de sesión o acción bloqueada antes de tocar aplicación.
Assets y layout ViteAssets, helpers de view y fallo claro de manifest. Layout decide dónde incluir estilos/scripts. Build produce manifest, chunks y CSS. Assets correctos en dev/prod o fallo visible si falta manifest/entry.

Blueprint para una feature nueva

  1. Definir la capacidad: página, fragment, JSON, integración externa, acción de sesión, assets o combinación.
  2. Diseña el contrato visible: HTML SSR, atributo data-surface-*, envelope JSON, headers o manifest.
  3. Implementa primero Gateway: route, controller, use case y response. Agregar service/connector solo si hay composición real.
  4. Implementa Surface solo para activar la UI: integración, binding, api.ts, adapters y cleanup.
  5. Recorre los tres estados: éxito limpio, éxito parcial y fallo bloqueante. Si uno no está explicado, la feature todavía no está documentada.
  6. Verifica observabilidad: status HTTP, message/errors, X-Correlation-Id, status de montaje y logs upstream si aplica.

Flujo completo del bridge

El bridge es la conversación completa entre HTML SSR, runtime UI, requests al gateway y respuestas controladas. No agrega una capa nueva: ordena qué lado decide cada parte del contrato.

Si este traspaso involucra proveedores externos, ve a Flujo externo completo. Si la respuesta vuelve parcial o fallida, revisa JSON envelope.

01

Gateway declara

Vista SSR

@views/items/index.page.php

La vista entrega HTML real y deja marcas que Surface puede reconocer. No le pide a Surface que invente estructura de negocio. 

<div data-surface-page="demo-items">
  <form data-item-search>...
  </form>
</div>
Ayuda de Robo composer robo -- make:integration-page items --id=demo-items --layout=control

Traspaso: el browser recibe HTML con un contrato declarativo.

02

Surface reconoce

Integración UI

@workspace/integrations/items/integration.ts

El id de la vista y el id de la integración deben coincidir. Ese acuerdo permite cargar solo el código UI necesario para esa página. 

id: "demo-items",
page: { load: () => import("./page") }
Ayuda de Robo composer robo -- make:integration-page items --id=demo-items --layout=control

Traspaso: el runtime monta page.ts sobre el nodo SSR.

03

Surface pide

Binding y API

@workspace/integrations/items/page.ts @workspace/integrations/items/api.ts

El binding escucha el evento y la API llama a Gateway. Esta pieza no consulta proveedores externos ni decide permisos. 

form.addEventListener("submit", async (event) => {
  event.preventDefault();
  target.innerHTML = await searchItems(new FormData(form));
});
Ayuda de Robo composer robo -- make:integration-api-html items searchItems post /items/summary --controller-name=ItemFragment

Traspaso: Gateway recibe una request HTTP normal.

04

Gateway recibe

Ruta y controller

@extension/Presentation/Http/Routing/* @extension/Presentation/Http/Controller/*

La ruta apunta al controller. El controller lee el request, llama el use case si hay intención de aplicación y adapta la salida. 

$router->post('/items/summary', [ItemFragmentController::class, 'summary']);
return $this->renderFragmentView('items/summary.fragment', $result->data());
Ayuda de Robo composer robo -- make:integration-api-html items summary post /items/summary --controller-name=ItemFragment

Traspaso: el use case recibe un input de aplicación, no un detalle del DOM.

05

Gateway decide

Use case, service y connector

@extension/Application/UseCase/* @extension/Infrastructure/Outbound/Connector/*

Aquí se resuelve la intención, se componen integraciones si hace falta y se normalizan fallos externos. Surface solo ve el resultado controlado. 

return $this->runConnectorFlow(
  fn(ConnectorFlowInterface $flow) => $this->service->summary($input, $flow)
);
Ayuda de Robo composer robo -- make:use-case SummaryItems --use-case-folder=Items composer robo -- make:service ItemSummary --use-case=SummaryItems composer robo -- make:connector ExternalItem

Traspaso: una respuesta HTML, JSON o un error normalizado.

06

Retorno HTML

Fragment y fragment binding

@views/items/summary.fragment.php @workspace/integrations/items/fragments/summary.ts

Gateway devuelve HTML con marcas de fragment. Surface lo inserta y el runtime monta el binding del fragment sin volver a decidir el contenido. 

<section data-surface-fragment="item-summary">
  <button data-refresh-summary>Actualizar</button>
</section>
Ayuda de Robo composer robo -- make:integration-api-html items summary get /items/summary --controller-name=ItemFragment composer robo -- make:fragment items summary --id=item-summary

Traspaso: UI activa sobre HTML de servidor.

Pregunta práctica Respuesta Archivo donde se ve
¿Quién declara la estructura inicial? Gateway, porque renderiza SSR. Views PHP.
¿Quién conecta esa estructura con JS? Surface, mediante registry e integración. integration.ts.
¿Dónde se maneja el click o submit? Surface binding. page.ts o fragment binding.
¿Dónde se decide la intención de negocio? Gateway use case. Application/UseCase/*.
¿Quién transforma proveedor externo en contrato local? Gateway connector. Infrastructure/Outbound/Connector/*.
¿Quién activa el HTML que volvió? Surface FragmentRuntime. fragments/*.ts.
Frontera Si aparece negocio en Surface, vuelve al contrato del Gateway.
  • Gateway Decide intención de aplicación.
  • Surface Activa interacción sobre contratos ya definidos.
