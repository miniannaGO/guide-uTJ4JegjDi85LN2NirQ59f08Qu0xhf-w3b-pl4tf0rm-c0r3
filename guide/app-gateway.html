App Gateway

Gateway de aplicación también conocido como BFF/SSR (Backend for Frontend/Server-Side Rendering) o backend liviano. Centraliza la entrada HTTP, ejecuta casos de uso, integra APIs HTTP externas y entrega respuestas HTML, JSON y assets desde una capa PHP orientada a actuar como fachada de aplicación.

Overview

`app-gateway` separa la infraestructura reutilizable de la lógica propia del proyecto mediante dos zonas internas: `Core` y `Extension`. `Core` contiene los mecanismos estables del Gateway. `Extension` contiene la aplicación concreta: pantallas, endpoints, reglas, casos de uso e integraciones. La intención es evitar que cada proyecto reescriba infraestructura transversal y, al mismo tiempo, impedir que las features se acoplen a detalles internos del `Core`.

Para ubicar esta división dentro del mapa general, se recomienda revisar Contextos y límites y Ownership rápido.

Los nombres de ejemplo son placeholders. Las rutas, controllers, use cases, services, connectors y views deben ajustarse a la intención real de la solución sin copiar negocio de otra Extension.

Lectura guiada de Gateway

Para una primera lectura, no conviene iniciar por DI, cache u outbound. La idea base es esta: Gateway recibe una intención por HTTP, la traduce a aplicación, ejecuta un use case y devuelve una salida controlada. Todo lo demás existe para que ese flujo sea consistente.

Core / Extension

app-gateway se organiza en dos capas internas: Core concentra las capacidades estables del Gateway: routing, HTTP, results, errores, views, outbound, DI y lifecycle. Extension construye la aplicación sobre esas bases mediante pantallas, endpoints, controllers, use cases, services, connectors e integraciones externas.

Esta separación sigue una lógica similar a Framework/App: Core provee contratos, convenciones y mecanismos reutilizables; Extension declara la solución concreta sin reescribir infraestructura transversal ni depender de piezas internas del motor.

Ámbito Qué contiene Uso desde Extension Qué evitar
Core Bootstrap, contenedor, routing, middleware pipeline, controller base, responses, resultados, errores, outbound y views. Funcionalidad pública: Router, AppController, UseCaseResult, ConnectorResult, helpers de view y clients outbound. Importar clases Internal desde Extension o duplicar un mecanismo transversal.
Extension Rutas, controllers, use cases, services, ports, connectors, DTOs, session adapters, runtime concreto y vistas SSR. Modelado de una capacidad concreta respetando fronteras: controller adapta HTTP, use case decide intención y connector traduce integración externa. Crear un mini-framework paralelo, meter UI en connectors o poner reglas de negocio en adapters técnicos.

Al agregar una feature

  1. Declara la URL en routing.
  2. Crear el controller que adapta el request.
  3. Crear el input/command si hay datos de entrada.
  4. Crear el use case que decide el resultado.
  5. Agregar service solo si compone varias piezas.
  6. Agregar port/connector si hay integración externa.
  7. Devuelve HTML, fragment, JSON o redirect controlado.

Regla simple para identificar ubicación

  • Si es regla transversal reutilizable, probablemente es Core.
  • Si habla del negocio o de una pantalla concreta, vive en Extension.
  • Si transforma una API HTTP externa, es connector o client outbound.
  • Si solo pinta HTML, pertenece a views y responses.

Matriz de capacidades Gateway

Gateway es la frontera de aplicación hacia el navegador. La pregunta operativa es “¿qué capacidad debe entregarse y qué contrato debe recibir Surface?”. Esta matriz resume los escenarios transferibles a cualquier dominio.

Core aporta la infraestructura, Extension expresa la intención, Surface consume HTML/JSON ya normalizado.

HTML navegable aunque Surface no monte nada. Si falla render/layout, el error handler presenta HTML o JSON según Accept.
Página SSR activada por Surface Misma base SSR, assets Vite y contrato data-surface-page. View con root declarativo y datos iniciales seguros. Runtime busca UiIntegration.id, carga page.load y monta el binding. Sin JS sigue existiendo HTML. Si el id no coincide, Surface no debe montar otra integración por accidente.

Si la dependencia falla, el use case termina como fallo y el status refleja validación, upstream o transporte.
Integración externa opcional runConnectorFlow(...), $flow->optional(...) y cierre parcial. Service que compone datos requeridos y opcionales sin ocultar degradación. Data usable con advertencia desde el partial reporter. La data principal puede ser éxito aunque errors[] conserve fallos secundarios.
Assets de Surface en vistas Gateway ViteAssets, manifest, styles, script y modulepreload. Layouts o views llaman vite_styles() y vite_script(). JS/CSS del entry principal servido desde web root. En dev puede haber fallback; en producción falta de manifest o entry debe fallar claro.
Seguridad, sesión y observabilidad Lifecycle, middleware pipeline, headers, telemetry y mapeo central de errores. Middlewares concretos, validación CSRF/tab y responses observables. Headers X-TAB-SESSION, X-REMAINING y X-Correlation-Id. Fallos de presentación se cortan antes del use case; los logs quedan correlacionados por request.
Los feature deben clasificarse como salida HTML, salida JSON, integración externa, lifecycle, seguridad, assets o UI progresiva. La mayor parte del proyecto pertenece a una de esas familias.

Ubicación de la URL

El archivo se elige según el tipo de entrada. Después se escribe la ruta y se apunta al controller que será creado o modificado.

  1. Página pública

    Archivo @extension/Presentation/Http/Routing/PublicRoutes.php
    Contenido 
    $router->get('/items', [ItemController::class, 'index']);
    Resultado
    Una URL sin sesión requerida.
    Siguiente paso: crear `ItemController::index`.

  2. Página autenticada o JSON

    Archivo @extension/Presentation/Http/Routing/AuthenticatedRoutes.php
    Contenido
    Ruta directa o carga de un subarchivo como `ItemRoutes.php`.
    Resultado
    La URL vive dentro del grupo autenticado.
    Siguiente paso: crear el action JSON o SSR en el controller.

  3. Fragment HTML

    Archivo @extension/Presentation/Http/Routing/Authenticated/FragmentRoutes.php
    Contenido 
    $router->get('/items/summary', [ItemFragmentController::class, 'summary']);
    Resultado
    Surface podrá pedir HTML con `serverClient.html(...)`; si el fragment es montable, deberá declarar `expect`.
    Siguiente paso: crear `summary.fragment.php`.
  • Usar grupos para prefijos como `/items` o `/admin`.
  • Aplica middleware en routing, no en el cuerpo del controller.
  • Validar que el action del controller exista y tenga contrato claro.
  • Separa rutas de página, fragment y JSON si el mismo caso de uso puede entregar más de una salida.

Interfaz del router

El router no solo soporta las rutas que hoy ves en `Extension`. Tiene una interfaz del router completa para verbos HTTP, grupos, carga de definiciones, middleware y parámetros tipados. Debe usarse cuando la URL necesite expresar intención con claridad.

Verbos, grupos y loaders 
<?php

use App\Core\Http\Routing\Router;
use App\Extension\Presentation\Http\Controller\ItemController;
use App\Extension\Presentation\Http\Middleware\RequireAuthentication;

return static function (Router $router): void {
  $router->get('/items', [ItemController::class, 'index']);
  $router->post('/items', [ItemController::class, 'store']);
  $router->put('/items/{id:number}', [ItemController::class, 'replace']);
  $router->patch('/items/{id:number}', [ItemController::class, 'update']);
  $router->delete('/items/{id:number}', [ItemController::class, 'delete']);

  $router->group('/admin', __DIR__ . '/AdminRoutes.php', [
    RequireAuthentication::class,
  ]);

  $router->load([
    __DIR__ . '/FragmentRoutes.php',
    static fn(Router $router) => $router->get('/health', [ItemController::class, 'health']),
  ]);
};
Funciones Sirve para
get, post Lectura, formularios, acciones JSON o fragments.
put, patch Reemplazar o modificar recursos existentes.
delete Eliminar o cerrar recursos con intención explícita.
group($prefix, ...) Compartir prefijo y middleware, por ejemplo /auth o /admin.
load(...) Cargar una definición callable, un archivo PHP o un array de definiciones.

Parámetros de ruta

La sintaxis es {nombre} o {nombre:tipo}. Si no indicas tipo, el router usa segment. Internamente compila la URL a un regex con nombres de grupo, por eso después puede inyectar parámetros al action del controller.

Tipo Patrón Ejemplo Hace match con
segment [^/]+ /files/{slug} /files/reporte-2026
alpha [a-zA-Z]+ /locale/{lang:alpha} /locale/es, /locale/EN
number \d+ /items/{id:number} /items/42
Binding por nombre o #[FromRoute] 
use App\Core\Http\Routing\Attribute\FromRoute;
use App\Core\Http\Response\HttpResponseInterface;
//Rutas
$router->get('/items/{id:number}', [ItemController::class, 'show']);
$router->get('/items/{itemId:number}/details/{detailId:number}', [ItemController::class, 'item']);
//Controllers
public function show(string $id): HttpResponseInterface
{
  return $this->respondJson(fn() => $this->showItem->execute((int) $id));
}

public function item(
  #[FromRoute('itemId')] string $itemId,
  #[FromRoute('detailId')] string $detailId,
): HttpResponseInterface {
  return $this->respondJson(fn() => $this->showItem->execute((int) $itemId, (int) $detailId));
}
  • El action debe retornar HttpResponseInterface. El validador falla temprano si no lo hace.
  • Todos los parámetros de ruta deben mapearse por nombre o con #[FromRoute(...)].
  • Los parámetros llegan como string desde el regex. Convierte a int o valida dentro del controller/use case.
  • La firma de duplicado ignora el nombre y conserva el tipo: /users/{id:number} y /users/{userId:number} son la misma firma.
  • En producción, el cache de rutas debe existir. Si falta, el gateway falla claro para evitar servir rutas incompletas.

Use cases

El use case decide intención de aplicación. Ahí vive la validación de input de aplicación, estado y significado final del flujo.

La relación entre use cases, errores y responses se resume en Ownership de contratos y se diagnostica desde Ayuda.

Carriles de use case 
// Simple: una dependencia obligatoria directa.
return $this->run(function () use ($input) {
  return $this->takeOrAbort($this->connector->simpleAction($input));
});

// Robusto: composición, fallback, opcionales o parcialidad.
return $this->runConnectorFlow(
  fn(ConnectorFlowInterface $flow) => $this->service->loadItemSummary($itemId, $flow)
);
`takeOrAbort(...)` no debe mezclarse con `$flow->required(...)` o `$flow->optional(...)`. Cuando se abre un flow, todo connector de ese bloque pasa por el flow.
  • `run(...)` envuelve una decisión de aplicación simple.
  • `takeOrAbort(...)` se usa solo cuando una integración obligatoria directa basta para resolver el caso.
  • `takeOrAbort(...)` debe recibir un resultado ya normalizado por un port/connector; no es una vía para llamar un client outbound directo desde el use case.
  • `runConnectorFlow(...)` se usa cuando hay datos requeridos, opcionales, fallback o respuesta parcial.

Cómo elegir la salida del use case

Situación Funcionalidad recomendada Resultado que llegará al controller Regla de uso
Validación de intención local abortUseCase(...) o fallo explícito. UseCaseResult fallido con mensaje de aplicación. No deben lanzarse errores de HTTP aquí; el controller ya adaptó el request.
Datos calculados sin dependencia externa run(fn() => $data). UseCaseResult::success($data). Devuelve un read model o DTO de aplicación, no arrays improvisados si el shape es compartido.
Una dependencia externa obligatoria directa takeOrAbort($connector->call(...)). Éxito con data, o fallo bloqueante con error del connector. No debe crearse un service si solo delega al connector.
Varias dependencias o fallback runConnectorFlow(...). Éxito completo, parcialidad o fallo según required/optional. Todo connector dentro del bloque debe pasar por el ConnectorFlowInterface.
Transformar data manteniendo errores previos $result->mapData(fn($data) => ...). Mismo estado de éxito/parcialidad/fallo con data mapeada solo si existía data usable. Debe usarse para adaptar output final sin reconstruir errores.

Services y connectors

Un service existe si agrega valor: compone varias llamadas, transforma datos o distingue dependencias obligatorias y opcionales. Un connector habla con un sistema externo y devuelve `ConnectorResult`.

Si el service coordina APIs HTTP externas, continúa en API HTTP clients externos; si solo se requieren pasos de implementación, se debe consultar Consumir un servicio externo.

Pieza Responsabilidad No debe
Service Coordinar integraciones con sentido de aplicación. Crear responses o lanzar errores de aplicación.
Connector Construir requests externos, mapear fallas a `ConnectorResult`. Conocer UI, HTML, JSON final o `UseCaseResult`.
Outbound client Transporte técnico HTTP y mapeo base. Decidir intención de aplicación.

    El use case puede consumir la API HTTP externa sin saber transporte.

2. Registra el cliente en DI

El request declara el endpoint mediante `#[Endpoint]`. En `GET`, las propiedades públicas se envían como query string. En `POST`, `PUT` o `DELETE`, se envían como JSON. Cuando se requiera una forma especial, corresponde implementar `CustomPayloadRequestInterface`.

4. Crear el client y bajar el resultado al connector

`JsonServiceClient` resuelve transporte, decodificación JSON, errores HTTP e hidratación de DTOs. El connector traduce ese resultado al contrato de aplicación mediante `ConnectorResult`.

Service client 
use App\Core\Outbound\Transport\JsonServiceClient;
use App\Core\Outbound\Transport\OutboundRequest;

final class ExternalApiServiceClient extends JsonServiceClient
{
  protected function prepareRequest(OutboundRequest $request): OutboundRequest
  {
    return $request->withBearer();
  }

  protected function serviceName(): string
  {
    return 'external_api';
  }
}
Connector 
use App\Core\Port\Result\ConnectorResult;
use App\Extension\Infrastructure\Outbound\Client\ExternalApi\ExternalApiServiceClient;
use App\Extension\Infrastructure\Outbound\Client\ExternalApi\Request\GetExternalRecordRequest;

final class ExternalItemConnector implements ExternalItemConnectorInterface
{
  public function __construct(private readonly ExternalApiServiceClient $externalApi)
  {
  }

  public function getRecordByItem(int $itemId): ConnectorResult
  {
    $result = $this->externalApi->send(new GetExternalRecordRequest($itemId));

    if (!$result->success)
      return $result->toConnectorResult('No se pudo consultar el registro externo');

    $record = $result->data();

    return ConnectorResult::success(
      new ExternalRecordOutput($record->id, $record->total, $record->status)
    );
  }
}

5. Consumo del connector desde service o use case

Si hay una llamada obligatoria directa, el use case puede usar `takeOrAbort(...)`. Si hay varias llamadas, fallback o datos opcionales, debe abrirse `runConnectorFlow(...)` para que el service declare qué es requerido y qué puede degradar.

Flujo robusto 
public function loadItemSummary(int $itemId, ConnectorFlowInterface $flow): ?ItemSummaryOutput
{
  $record = $flow->required($this->externalItems->getRecordByItem($itemId));
  $details = $flow->optional($this->externalItems->listDetailsByItem($itemId), []);

  if ($record === null)
    return null;

  return new ItemSummaryOutput($itemId, $record, $details);
}

public function execute(int $itemId): UseCaseResult
{
  return $this->runConnectorFlow(
    fn(ConnectorFlowInterface $flow) => $this->items->loadItemSummary($itemId, $flow)
  );
}
  • `JsonServiceClient` no debe llamarse desde controllers, use cases ni desde `app-surface`.
  • Si encuentras una llamada directa desde un use case, trátala como deuda puntual que debe moverse detrás de un port/connector antes de usarla como referencia.
  • `EndpointListRequest` corresponde cuando la API HTTP externa devuelve una lista de DTOs.
  • El connector transforma DTOs externos a read models o outputs de aplicación.
  • Propaga fallos externos con `toConnectorResult(...)` o `asFailure(...)`; no reconstruyas errores si ya existen.
  • Cuando se agregue un servicio nuevo, se debe registrar su provider outbound y confirmar que el port/connector siga la convención de aliases.

Funciones avanzadas del outbound

El client outbound no solo hace GET y POST. También concentra decisiones de contrato para que cada connector no invente su propio cliente HTTP.

Pieza Para qué sirve Regla práctica
EndpointRequest Request que espera un DTO único. Debe usarse cuando el payload externo representa un objeto.
EndpointListRequest Request que espera una lista de DTOs. Debe usarse cuando la raíz de respuesta externa es una lista.
CustomPayloadRequestInterface Permite construir un payload que no proviene directamente de propiedades públicas. Debe usarse para formas no estándar, multipart o contratos heredados.

timeout / connectTimeout / verifyTls Permiten ajustar resiliencia por servicio o endpoint. Configura por services.json o variables API_*.

Middlewares

Middleware revisa condiciones transversales del request: autenticación, tab session, refresh de sesión o filtros previos. Debe cortar o dejar pasar.

Contrato mental 
public function intercept(HttpRequest $request, MiddlewareChainInterface $chain): HttpResponseInterface
{
  // Validar regla transversal del request.
  return $chain->proceed();
}
  • Usar middleware para reglas previas al controller: autenticación, tab session, refresh de sesión o headers requeridos.
  • Si la regla depende de intención de negocio, pertenece al use case, no al middleware.
  • Si corta el flujo, debe emitir una respuesta clara y no dejar al controller inferir qué ocurrió.

Bootstrap y DI

Antes de que exista un controller, Gateway tiene que levantar el entorno, crear el contenedor y registrar las piezas de Core y Extension. Piensa en esta parte como el encendido del framework interno.

Una feature normalmente no toca esta zona. La consulta al agregar una pieza nueva es: "¿la clase ya entra por autowiring, provider o convención, o realmente requiere registro explícito?".

Quién registra qué

Pieza Responsabilidad Cuándo importa
RootProvider.php Importa providers transversales: application, routing, filesystem, outbound, observability, errores, controllers y middleware base. Solo cuando cambias una capacidad compartida de Core.
AppProvider.php Importa providers de la app: controllers, use cases, middleware, runtime, sesión, responses, outbound y connectors. Al agregar una familia nueva de servicios en Extension.
ConnectorProvider.php Usa ConnectorAliasRegistrar para unir ports *ConnectorInterface con implementaciones *Connector. Cuando un connector no se resuelve por convención o hay más de una implementación candidata.
Cache del contenedor En producción se espera usar el contenedor compilado; en desarrollo se prioriza ergonomía. Si algo funciona en local pero falla en producción, revisa cache, providers y variables de entorno.
Regla operativa: no debe registrarse manualmente una clase que ya puede resolverse por autowiring o por convención. El registro manual debe explicar una frontera real: runtime concreto, adapter externo, alias de interfaz o servicio transversal.

Caché de producción

En producción, Gateway no recompila el contenedor ni vuelve a registrar rutas como fallback durante una request. El despliegue debe preparar los artefactos antes de atender tráfico, porque el runtime productivo espera leer archivos ya generados desde var/cache/releases/<VERSION_DEPLOY>.

Esta decisión hace que un error de deploy falle temprano y de forma explícita: si falta el contenedor compilado, aparece PRODUCTION_CONTAINER_CACHE_MISSING; si falta el cache de rutas, aparece PRODUCTION_ROUTE_CACHE_MISSING. No son errores para maquillar con fallback silencioso, sino señales de que el release no fue preparado.

Preparar Gateway para producción 
# En la raíz del workspace: .env debe tener IS_PRODUCTION=true y VERSION_DEPLOY>0
cd app-gateway
composer run build:prod
Paso Qué prepara Por qué importa
IS_PRODUCTION=true Activa las reglas endurecidas del runtime. Sin este valor, build:prod y routes:warm se rechazan para no generar un artefacto productivo con entorno incorrecto.
VERSION_DEPLOY>0 Define el namespace var/cache/releases/<VERSION_DEPLOY>. Permite preparar un release sin pisar otro namespace de caché y evita depender de archivos genéricos de desarrollo.
cache:clear interno Elimina el cache activo, el contenedor compilado y routes.php del namespace actual. Evita que una versión vieja del contenedor o de las rutas sobreviva al deploy.
ContainerFactory::compileCache(...) Compila providers de Core y Extension en CompiledGatewayContainer.php. Congela wiring, aliases, services, controllers y clients para que la request productiva solo cargue el contenedor.
RouteCacheWarmer Registra las rutas en un router y escribe routes.php. Producción exige ese archivo. Si falta, el dispatcher no recorre registrars como fallback.

Orden recomendado de deploy: compila assets de Surface con npm run build, valida que exista el manifest en app-gateway/{PUBLIC_PATH}/ui-assets/.vite/manifest.json y luego ejecuta composer run build:prod en Gateway. Surface produce archivos estáticos; Gateway produce contenedor y rutas. Ambos artefactos son necesarios antes de exponer el release. La parte de assets se explica en Surface: Vite y estilos.

Seguridad, CSRF y sesión

El Gateway aplica protecciones complementarias: CSRF evita envíos falsificados en formularios, mientras que tab session identifica la pestaña autenticada que origina las requests hacia el Gateway.

Contrato Dónde nace Dónde se valida Qué problema resuelve
_csrf CsrfTokenManager::field() en vista SSR. Controller que procesa el formulario protegido antes del use case. Evita aceptar un formulario de inicio de sesión falsificado.
_tab ensureTabSession() lo escribe en inputs si existen. Inicio de sesión y comandos de sesión. Une el inicio de sesión con la pestaña que inició la navegación.
X-TAB-SESSION serverClient lo agrega desde hooks de sesión. TabSessionRequestResolver y middleware. Identifica requests posteriores de esa pestaña.
X-REMAINING RemainingSessionHeaderEmitter. SessionCountdown en Surface. Sincroniza expiración sin duplicar cálculo en Surface.

Flujo de tab session

  1. Surface crea o recupera un id de pestaña desde sessionStorage.
  2. En login, la vista puede enviar _tab junto con el formulario.
  3. Gateway crea contexto de sesión por pestaña en TabSessionStore.
  4. En requests autenticados, serverClient envía X-TAB-SESSION.
  5. Middleware como RequireAuthentication o RefreshAuthTabSession valida o refresca la pestaña. El refresh respeta SESSION_REFRESH_WINDOW y SESSION_REFRESH_COOLDOWN.
  6. Gateway responde X-REMAINING y Surface actualiza el contador.

Cuándo se refresca realmente

RefreshAuthTabSession intenta mantener viva la tab activa, pero PhpTabSessionStore::refreshTab(...) no escribe en sesión cada vez. La decisión final vive en TabSessionExpiryService::shouldRefresh(...), que se puede leer como una regla de dos preguntas.

  1. ¿Ya falta poco para vencer? Eso lo marca SESSION_REFRESH_WINDOW.
  2. ¿Ya pasó suficiente tiempo desde el último refresh real? Eso lo marca SESSION_REFRESH_COOLDOWN.

Con SESSION_TIME=10, SESSION_REFRESH_WINDOW=30 y SESSION_REFRESH_COOLDOWN=60, el flujo se entiende mejor con horas concretas:

  1. 12:00:00: login. La tab vence a las 12:10:00 y refreshedAtUnix queda en 12:00:00.
  2. 12:08:00: entra una request. Faltan 2 minutos para vencer, así que no está dentro de la ventana final de 30 segundos. No se refresca.
  3. 12:09:35: faltan 25 segundos para vencer y el último refresh real fue a las 12:00:00. Ya pasó el cooldown, por eso Gateway actualiza refreshedAtUnix y mueve expiresAtUnix a 12:19:35.
  4. 12:09:36: entra otra request o un doble click en "mantener sesión". Solo pasó 1 segundo desde el refresh anterior. La request puede responder bien, pero Gateway no escribe una nueva expiración.
  5. 12:10:35: pasaron exactamente 60 segundos desde el último refresh. Todavía no alcanza, porque el código exige que haya pasado más de 60.

En resumen: el cooldown no bloquea la request; solo evita que cada request protegida alargue la vida de la tab y escriba el archivo de sesión PHP.

Dónde viven las tabs en sesión PHP

La cookie PHP identifica al navegador frente al servidor, pero el Gateway separa el trabajo por pestaña dentro de la misma sesión. PhpTabSessionStore guarda cada pestaña bajo tabs.{tabId}. El punto en la clave es notación del driver: termina como arrays anidados dentro de $_SESSION.

Ruta lógica Contenido Responsable
tabs.{tabId}.metadata startedAt, refreshedAt, expiresAt y sus timestamps Unix. TabSessionExpiryService.
tabs.{tabId}.accountInfo Usuario autenticado, administrador, perfil y permisos serializados para esa pestaña. PhpTabSessionStore.
_flash.{tabId} Mensajes temporales aislados para una pestaña concreta. TabFlashMessages y helpers de AppController.
_maintenance.tabsCleanupLastRunUnix Timestamp Unix del último barrido de tabs expiradas en esa sesión PHP. TabSessionGarbageCollector.

Cómo conviven varias pestañas

Varias pestañas del mismo navegador comparten la misma cookie de sesión PHP, pero no comparten necesariamente el mismo tabId. Por eso el Gateway no guarda un único usuario plano en sesión para todo el navegador; guarda un mapa tabs indexado por id de pestaña. Una pestaña puede expirar, cerrarse o refrescarse sin borrar directamente el estado de otra.

SESSION_TIME define la vida total emitida al crear o refrescar una tab. El refresh no ocurre en cada request: solo cuando la pestaña está dentro de SESSION_REFRESH_WINDOW y ya pasó SESSION_REFRESH_COOLDOWN desde el último refresh. Esa combinación reduce escrituras sobre el archivo de sesión y evita que cada request protegida alargue la vida de la tab sin control.

Dónde cortar: si falta CSRF, tab session o una sesión activa, el controller o middleware puede cortar antes del use case. El use case no debería saber cómo se llama el header ni cómo se guarda el id de pestaña.
Mantenimiento de sesión: TabSessionGarbageCollector usa SESSION_CLEANUP_INTERVAL y SESSION_CLEANUP_LAST_RUN_KEY para evitar limpiar tabs expiradas en cada request.
Mensajes flash: flashMessage(...) escribe bajo _flash.{tabId} antes de un redirect, y pullFlashMessages(...) lee y elimina esos mensajes al renderizar la siguiente vista.

Errores y resultados

Cada capa clasifica los errores según su responsabilidad. Esto evita que un connector decida sobre la UI, que un service dependa de HTTP o que Surface oculte fallos que el Gateway ya interpretó.

Taxonomía de error

Concepto Qué representa Ejemplos
ErrorKind Tipo de fallo que define el status HTTP esperado. VALIDATION, FORBIDDEN, CONFLICT, DEPENDENCY_UNAVAILABLE.
ErrorOrigin Origen del fallo, útil para diagnóstico y status de dependencias. FRAMEWORK, APPLICATION, UPSTREAM, TRANSPORT.
ErrorKindHttpStatusResolver Traduce kind/origin a HTTP. Validación a 422, auth a 401, dependencia upstream a 502 o transporte a 503.
ErrorPresenter Presenta errores no manejados como HTML o JSON según el request. Error temprano de bootstrap, excepción no capturada o fallo framework.

Dónde nace cada error

Capa Puede fallar por No debe fallar por Salida esperada
Controller Request imposible, CSRF, tab session ausente, parámetro HTTP mal formado. Estado de una API externa o reglas internas del caso. abortController(...) o response segura.
Use case Intención inválida, transición no permitida o input de aplicación inconsistente. Detalles de headers, query string, HTML o transporte. UseCaseResult de éxito, parcial o fallo.
ConnectorFlowInterface Dependencia requerida fallida u opcional degradada. Crear errores nuevos sin venir de un connector. Fallo bloqueante con required o parcialidad con optional.
Service Debe componer datos y decidir qué llamada es requerida u opcional usando el flow recibido. Lanzar errores de aplicación, crear responses o conocer Surface. Read model, output o null controlado.
Connector Contrato externo inválido, upstream fallido o transporte no disponible. Elegir HTML, JSON final o comportamiento visual. ConnectorResult::success/fail.
Response Serialización JSON, render de view, manifest de assets o emisión final. Reinterpretar reglas de aplicación ya decididas. HTTP status, headers, body y contexto observable.

Semántica del envelope

  • `success=true` sin errores: éxito completo.
  • `success=true` con errores: respuesta parcial o degradada.
  • `success=false`: fallo bloqueante.
  • Los fallos secundarios no deben convertirse en éxito limpio si el usuario debe ver degradación.
  • errorMeta solo debe exponerse cuando el runtime lo permite. En producción, el usuario recibe mensajes seguros, no detalles técnicos.
  • Una excepción inesperada no debe salir cruda: el handler central la mapea, la registra y presenta una salida consistente.

Observabilidad

Observabilidad no cambia el resultado funcional de una pantalla, pero permite responder preguntas como: qué request falló, qué upstream tardó más, si el error fue de transporte o de aplicación, y qué correlation id une los logs.

Pieza Qué captura Por qué importa
RequestTelemetryContext Request actual, correlation id, response y llamadas upstream. Da contexto compartido a pipeline, outbound y errores.
CorrelationIdHeaderEmitter Emite X-Correlation-Id. Permite rastrear una request entre cliente, gateway y logs.
TracingHttpClient Registra llamadas externas, duración, status y errores operativos. Ayuda a distinguir fallo propio de fallo upstream.
ObservableResponseInterface Contexto de salida para JSON, view o redirect. Los logs pueden decir qué tipo de respuesta se emitió.
ObservabilityConfig Centraliza el default de LOG_UPSTREAM_SPANS. Mantiene logging y telemetría fuera del runtime de vistas y sesión.
LogWriterFactory Selecciona stdout para CLI y JSONL semanal directo para requests web. Permite capturar procesos CLI con collector sin dejar vacía la bitácora web en producción.
LogChannel Normaliza canales: access, metrics, error, upstream y bootstrap. Desacopla el evento de observabilidad del destino físico final.
LogSanitizer Filtra query, post, JSON, headers y opciones sensibles. Evita que secretos y tokens terminen en logs.

La observabilidad de Gateway usa JSON Lines. En requests web, Core escribe directo en app-gateway/var/log/develop/<semana>/stdout.jsonl o app-gateway/var/log/production/<semana>/stdout.jsonl. En CLI, los eventos salen por stdout y pueden persistirse con tools/log-collector. El visor de logs usa esas rutas fijas por entorno y las crea si no existen. El viewer solo lista carpetas semanales YYYY-WNN, así la carpeta develop o production no se mezcla con las semanas. Así el request PHP no bloquea archivos locales con LOCK_EX.

Cuando se reporta un error, la traza se reduce a los campos file, line, function y class por frame. No se serializan argumentos ni objetos internos del stack.

TracingHttpClient siempre agrega los spans al contexto de la request para que access/metrics conozcan cantidad, errores y upstream más lento. El evento detallado por cada llamada outbound se controla con LOG_UPSTREAM_SPANS, también con valor por defecto auto; por defecto solo queda activo en desarrollo.

  • Cuando se agregue una response nueva, debe evaluarse si corresponde implementar ObservableResponseInterface.
  • Cuando se agregue un client HTTP transversal, debe conservarse el rastro de upstream calls y la sanitización.
  • La observabilidad no debe decidir negocio. Sirve para observar el sistema, no para cambiar el flujo de aplicación.

Ciclo HTTP interno

El ciclo HTTP es el camino que sigue cada request después del bootstrap. Esta parte explica por qué un error puede convertirse en JSON o HTML, por qué se emiten headers compartidos y por qué el controller recibe un HttpRequest ya normalizado.

Paso Qué hace Qué NO debe hacer una feature
HttpRequestFactory Normaliza método, path, query, post, JSON, files y headers desde la request actual. Leer $_GET, $_POST o headers globales de forma manual.
RequestLifecycle::begin() Inicia telemetría y registra el manejador de errores según si el request espera JSON. Crear otro error handler local para un controller.
RequestBootstrapPipeline Ejecuta bootstrappers por request, como sesión PHP y limpieza/initialización de tab session. Inicializar sesión desde una vista o integración UI.
RouteDispatcher Carga o construye rutas, ejecuta middleware y llama el controller por el invoker. Esconder rutas dentro de controllers.
ResponseEmitter Emite headers compartidos y luego delega la salida en la response concreta. Hacer echo directo desde un use case o connector.

Route cache

El router puede exportar sus rutas a cache. En desarrollo carga las definiciones directamente para mantener feedback rápido. En producción, Gateway intenta leer el cache de rutas; si no existe, la request falla con PRODUCTION_ROUTE_CACHE_MISSING. Esa falla obliga a ejecutar build:prod antes de atender tráfico.

  • Cambiar un archivo de rutas debe invalidar o preparar nuevamente la cache de rutas antes de desplegar.
  • El cache guarda definiciones ya compiladas; no debe usarse para saltarse validaciones de handler o middleware.
  • Si dos rutas tienen la misma firma, el router debe fallar claro como ruta duplicada.

Flujo completo de Gateway

Gateway recibe una entrada HTTP, decide la intención de aplicación y devuelve una salida controlada: HTML, JSON, fragment o redirect. El camino cambia según el tipo de caso, pero las fronteras se mantienen.

El contrato que sale de este flujo se consume desde Surface y se explica como frontera compartida en JSON envelope y Contratos HTML.

01

Entrada HTTP

Ruta

@extension/Presentation/Http/Routing/ExtensionRouteRegister.php

Aquí vive la URL, el verbo HTTP y el action del controller. No decide negocio ni arma respuestas. 

$router->post('/items/search', [ItemController::class, 'search']);

Entrega a: ItemController::search(...).

02

Presentación

Controller

@extension/Presentation/Http/Controller/ItemController.php

Aquí se lee el request, se construye el input y se elige la respuesta. Puede cortar por errores de presentación, pero no debe hablar con proveedores externos.

  • $this->request es el HttpRequest que Core inyecta antes de invocar el action. Se usan getQuery(...), getPost(...), getJson(...) y getHeader(...) para leer la entrada HTTP.
  • respondJson(fn() => ...) ejecuta una intención y la convierte al envelope JSON del bridge. Si el callable devuelve datos sin normalizar, se normalizan como éxito; si devuelve UseCaseResult, se respeta su éxito, parcialidad o fallo.
  • $this->searchItems representa un use case: una clase de Application/UseCase inyectada por DI que expresa la intención de aplicación. El nombre debe reemplazarse por la intención real de la feature. 
$input = (string) $this->request->getPost('someInput', '');
return $this->respondJson(fn() => $this->searchItems->execute($input));

Entrega a: el use case que expresa la intención de aplicación.

03

Aplicación

Use case

@extension/Application/UseCase/Items/SearchItems.php

Aquí vive la intención: validar reglas de aplicación, decidir si basta una dependencia directa o si hace falta composición, y devolver un UseCaseResult. 

return $this->runConnectorFlow(
  fn(ConnectorFlowInterface $flow) => $this->service->search($input, $flow)
);

Entrega a: un service cuando hay composición, o a un port directo cuando el caso es simple.

04

Composición opcional

Service

@extension/Application/Service/Items/ItemSearchService.php

Solo existe si agrega valor: varias fuentes, fallback, parcialidad o transformación. Si únicamente delega al connector, este archivo sobra. 

$items = $flow->required($this->items->search($input));
$stats = $flow->optional($this->items->stats($input), null);

Entrega a: un output/read model usable por el use case.

05

Integración

Port y connector

@extension/Application/Port/* @extension/Infrastructure/Outbound/Connector/*

El port nombra lo que la aplicación necesita. El connector adapta clientes externos, payloads y fallos técnicos a ConnectorResult. 

return $this->client
  ->searchItems($input)
  ->toConnectorResult();

Entrega a: el use case o service, nunca a la vista directamente.

06

Salida

Response o view

@views/items/* @extension/Presentation/Http/Response/*

Aquí se adapta el resultado a HTML, JSON, fragment o redirect. La view pinta datos ya decididos; no vuelve a resolver negocio. 

return $this->renderFragmentView(
  'items/summary.fragment',
  $result->data()
);

Entrega a: browser o Surface, según el tipo de respuesta.

Necesidad Pieza a crear o reutilizar Evita ponerlo en
Mostrar una página completa Controller + view SSR. Use case si solo se arma una pantalla estática.
Actualizar una parte de la pantalla Ruta de fragment + controller + fragment PHP. Surface generando HTML de negocio.
Ejecutar una intención de aplicación Controller + use case + respondJson(...). Controller con reglas profundas.

El use case puede consumir un connector directo por su port cuando el carril es simple. No debería hablar con HTTP externo sin normalizar ni conocer URLs, bearer, TLS o payloads de proveedor; eso pertenece a outbound client y connector.
