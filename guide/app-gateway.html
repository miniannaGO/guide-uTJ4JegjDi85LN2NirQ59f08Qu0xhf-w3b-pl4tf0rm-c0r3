App Gateway

Parte del servidor que recibe cada petición, coordina la operación solicitada y decide si debe responder con HTML, un fragmento, JSON o una redirección. Técnicamente actúa como un Gateway de aplicación y cubre funciones de BFF, backend orientado a la interfaz, y SSR, HTML producido en el servidor, desde PHP.

Overview

Esta página funciona como el mapa operativo de app-gateway: muestra cómo una entrada HTTP llega al routing, pasa por controllers y use cases, conversa con integraciones cuando corresponde y termina como HTML, fragment, JSON o redirect.

La frontera Core / Extension define la regla de ubicación para organizar las responsabilidades del backend. Desde ahí, la página explica las piezas que se usan en el flujo normal: routes, controllers, use cases, services, connectors, responses, views, sesión, errores y observabilidad.

Core / Extension

Esta sección es el punto de referencia para decidir ubicación. Core concentra mecanismos transversales y contratos reutilizables; Extension declara la solución concreta sobre esa base. El resto de la página debe leerse desde el flujo operativo; aquí se define qué se puede consumir, qué se debe modelar en la aplicación y qué no conviene duplicar.

Frontera operativa

La ubicación se decide por responsabilidad: si la pieza reduce duplicación transversal pertenece a Core; si expresa una capacidad concreta, pertenece a Extension.

  1. Core

    Motor compartido

    Bootstrap, contenedor, routing, middleware pipeline, controller base, responses, resultados, errores, outbound y views.

    Mecanismos transversales
  2. Extension

    Solución concreta

    Rutas, controllers, use cases, services, ports, connectors, DTOs, session adapters, runtime concreto y vistas SSR.

    Intención de aplicación

Al agregar una feature Ruta Controller Use case Service / connector opcional Response controlada

Desde Extension se consumen únicamente contratos visibles de Core, como Router, AppController, UseCaseResult, ConnectorResult, helpers de view y clients outbound. No se importan clases Internal ni se replica un mecanismo transversal.

El límite práctico es mantener una responsabilidad por pieza: no crear un mini-framework paralelo, no colocar UI dentro de connectors y no esconder reglas de negocio en adapters técnicos.

Routing

El routing es el mapa que conecta una petición visible con el action que debe atenderla. Una ruta responde tres preguntas: qué método HTTP se acepta, qué forma tiene la URL y qué método del controller recibe la entrada. Todavía no decide reglas de aplicación ni construye la respuesta final.

En el proyecto, las rutas se registran desde ExtensionRouteRegister.php. No se deben ocultar dentro de controllers, porque el mapa de entrada debe poder leerse sin abrir cada clase de presentación.

Interfaz del router

La interfaz del router reúne las formas permitidas de declarar ese mapa de entrada. Se elige un verbo para expresar la acción HTTP, un grupo para compartir un prefijo o reglas, un middleware para aplicar una condición transversal y un parámetro tipado cuando la forma de la URL debe limitarse.

Para una ruta nueva, normalmente basta con un verbo, un path y un action de controller. Los grupos, loaders y middleware aparecen después, cuando varias rutas comparten prefijo, archivo o condición transversal. Se deben combinar solo cuando hagan más clara la intención de la URL.

Verbos, grupos y loaders 
<?php
use App\Core\Http\Routing\Router;
use App\Extension\Presentation\Http\Controller\ItemController;
use App\Extension\Presentation\Http\Middleware\RequireAuthentication;

return static function (Router $router): void {
  $router->get('/items', [ItemController::class, 'index']);
  $router->post('/items', [ItemController::class, 'store']);
  $router->put('/items/{id:number}', [ItemController::class, 'replace']);
  $router->patch('/items/{id:number}', [ItemController::class, 'update']);
  $router->delete('/items/{id:number}', [ItemController::class, 'delete']);

  $router->group('/admin', __DIR__ . '/AdminRoutes.php', [
    RequireAuthentication::class,
  ]);

  $router->load([
    __DIR__ . '/FragmentRoutes.php',
    static fn(Router $router) => $router->get('/health', [ItemController::class, 'health']),
  ]);
};
getpost Lectura, formularios, acciones JSON o fragments.
putpatch Reemplazar o modificar recursos existentes.
delete Eliminar o cerrar recursos con intención explícita.
group($prefix, ...) Compartir prefijo y middleware, por ejemplo /auth o /admin.
load(...) Cargar una definición callable, un archivo PHP o un array de definiciones.

Para resolver una petición, el router considera juntos el verbo HTTP y el path. Primero selecciona únicamente las rutas registradas para el verbo recibido y después compara sus paths. Por ejemplo, si existe GET /items, pero llega POST /items, la ruta GET /items no participa en esa búsqueda. En ese caso, la implementación no realiza una segunda comprobación para averiguar si /items existe con otro verbo. Por eso el resultado es 404 Not Found.

Parámetros de ruta

Un parámetro de ruta representa la parte variable de una URL, por ejemplo el identificador dentro de /items/42. Declarar su tipo permite rechazar una forma incompatible antes de ejecutar el controller y deja visible qué clase de valor acepta la ruta.

La sintaxis técnica es {nombre} o {nombre:tipo}. Si no se indica el tipo, el router usa segment. Internamente compila la URL a un regex con nombres de grupo, por eso después puede inyectar parámetros al action del controller.

Binding por nombre o #[FromRoute] 
use App\Core\Http\Routing\Attribute\FromRoute;
use App\Core\Http\Response\HttpResponseInterface;

//Rutas
$router->get('/items/{id:number}', [ItemController::class, 'show']);
$router->get('/items/{itemId:number}/details/{detailId:number}', [ItemController::class, 'item']);

//Controllers
//$id nombre exacto de la ruta
public function show(string $id): HttpResponseInterface
{
  return $this->respondJson(fn() => $this->showItem->execute((int) $id));
}

//$customItemId y $customDetailId no coinciden con los nombres de la ruta, se mapean con #[FromRoute]
public function item(
  #[FromRoute('itemId')] string $customItemId,
  #[FromRoute('detailId')] string $customDetailId,
): HttpResponseInterface {
  return $this->respondJson(fn() => $this->showItem->execute((int) $customItemId, (int) $customDetailId));
}
  • El action debe retornar una instancia de HttpResponseInterface; si devuelve otro tipo de valor, el validador lo detecta antes de enviar la respuesta.
  • Todos los parámetros de ruta deben mapearse por nombre o con #[FromRoute(...)].
  • Los parámetros llegan como string desde el regex.
  • La firma duplicada conserva el path y el tipo, pero no el nombre del placeholder. Para el mismo verbo, /items/{id:number} y /items/{slug:number} representan la misma ruta.

Controllers

El controller traduce entre HTTP y la aplicación. Su trabajo es entender qué llegó desde el navegador, preparar datos claros para la siguiente responsabilidad y elegir cómo se devolverá el resultado. No debe convertirse en el lugar donde se acumula toda la operación.

Esa traducción incluye datos de ruta, query, body, sesión o flash. Después de interpretarlos, el controller puede invocar un use case o responder directamente cuando el trabajo pertenece por completo a presentación, mediante una view, un fragment, un redirect o un JSON controlado.

Puede interrumpir el flujo antes del use case cuando la request no puede interpretarse con seguridad: parámetro de ruta mal formado, entrada HTTP inválida, payload incompatible o una precondición propia de presentación. En esos casos usa abortController(...) o una response segura. No delega esa decisión a services, connectors ni use cases, porque esas capas no son responsables de validar si una request HTTP es aceptable.

Interfaz del controller El action siempre declara una response; los datos HTTP se adaptan dentro del controller.

Antes de ver la implementación completa, esta referencia distingue la entrada pública que puede invocar el router y después agrupa los helpers que el controller usa para decidir y responder.

El router entra por el action registrado en la ruta, por ejemplo [ItemController::class, 'detail']. Ese método debe ser público y retornar HttpResponseInterface. Sus argumentos solo deben representar placeholders de la ruta: Core los resuelve por nombre o mediante #[FromRoute(...)]. El resto de la entrada HTTP no va en la firma del action; se lee desde $this->request, que se explica en Request del controller.

Al heredar de AppController, el controller recibe helpers protegidos. Cada ficha muestra la firma, su propósito y un ejemplo mínimo.

Salida HTTP

Responder desde el action

Estos helpers cierran el action con HttpResponseInterface. La callable opcional aporta datos; en una vista quedan dentro de $viewModel->data y Core completa el contrato ViewData de la plantilla. 

  1. respondJson(callable $action): HttpResponseInterface
    Entrada
    Callable que ejecuta el trabajo necesario para producir el payload, normalmente un use case.
    Efecto
    Entrega JSON con envelope normalizado y convierte fallos controlados en respuesta JSON.
    Ejemplo
    return $this->respondJson(
  fn() => $this->searchItems->execute($input),
);
  2. renderAccessView(
  string $view,
  ?callable $action = null,
): HttpResponseInterface
    Entrada
    Ruta de vista bajo resources/views, sin .php, y callable opcional.
    Uso
    Pantallas que deban presentarse con el layout de acceso y fuera del layout de control.
    Ejemplo
    return $this->renderAccessView('access/login.page');
  3. renderControlView(
  string $view,
  ?callable $action = null,
): HttpResponseInterface
    Entrada
    Misma forma que renderAccessView: vista y callable opcional.
    Uso
    Páginas internas con layout de control, navegación principal y estado activo del menú.
    Ejemplo
    return $this->renderControlView('items/index.page');
  4. renderFragmentView(
  string $view,
  ?callable $action = null,
): HttpResponseInterface
    Entrada
    Partial o fragment, por ejemplo <feature>/panel.fragment.
    Uso
    SSR parcial para Surface, recargas progresivas o composición HTML acotada.
    Ejemplo
    return $this->renderFragmentView('items/panel.fragment');
Flujo y feedback

Decidir antes de responder

Estos helpers preparan la decisión: inspeccionan resultados, cortan el flujo, redirigen o guardan mensajes flash por pestaña. 

  1. runUseCase(callable $useCase): UseCaseResult
    Entrada
    Callable que puede devolver UseCaseResult o payload simple.
    Uso
    Normaliza un payload como UseCaseResult cuando el controller necesita inspeccionarlo antes de elegir vista, redirect u otra response. No se debe anidar dentro de respondJson(...).
    Ejemplo
    $result = $this->runUseCase(
  fn() => $this->saveItem->execute($input),
);
  2. redirectTo(string $url): HttpResponseInterface
    Entrada
    URL destino absoluta o relativa.
    Uso
    Cambios explícitos de flujo posteriores a una acción o navegaciones que deban terminar en otra URL.
    Ejemplo
    return $this->redirectTo('/items');
  3. abortController(
  string $userMessage,
  ErrorKind $errorKind = ErrorKind::VALIDATION,
  ?string $technicalMessage = null,
  ErrorOrigin $origin = ErrorOrigin::APPLICATION,
): never
    Entrada
    Mensaje visible seguro, clasificación del error, detalle técnico opcional y origen.
    Efecto
    Lanza un corte controlado que Core convierte en respuesta HTML o JSON.
    Ejemplo
    $this->abortController('El nombre es obligatorio.');
  4. flashMessage(
  FlashMessageType $type,
  string $message,
  ?string $tabId = null,
): void
    Entrada
    Tipo semántico SUCCESS, INFO, WARNING o ERROR; mensaje visible y tab opcional.
    Efecto
    Guarda el mensaje para la siguiente respuesta; si no hay tab explícito, se resuelve desde la request y debe existir una tab válida.
    Ejemplo
    $this->flashMessage(
  FlashMessageType::SUCCESS,
  'El item fue guardado.',
);
  5. pullFlashMessages(?string $tabId = null): array
    Entrada
    Tab opcional; si se omite, se usa el tab actual de la request.
    Entrega
    Lista consumida de mensajes con type como FlashMessageType y message como texto visible.
    Ejemplo
    'messages' => $this->pullFlashMessages()

Para ver estos helpers dentro de actions completos, se puede continuar en Ciclo de un action y adaptación de salida.

Si la ruta declara /items/{id:number}, el action debe mapear id por nombre o con #[FromRoute('id')]. Si un parámetro requerido del action no corresponde a un placeholder de ruta, el registro de la ruta falla antes de atender requests.

Request del controller $this->request trae la request HTTP normalizada por Core.

El controller no debe buscar datos HTTP en variables globales ni reconstruir la petición. Recibe una sola representación ya preparada y la usa para leer query, formulario, JSON, headers y otros datos de entrada.

En los controllers de Extension que heredan de AppController, $this->request es la entrada HTTP normalizada que Core entrega al action actual. Sus métodos expuestos permiten tomar datos de presentación, validarlos o normalizarlos, y construir inputs explícitos antes de llamar al caso de uso.

Datos enviados

Leer valores por clave

Estos métodos buscan un valor en una fuente concreta de la request. El controller todavía debe convertirlo y validarlo antes de construir el input de aplicación. 

  1. getQuery(string $key, mixed $default = null): mixed
    Lee
    Un valor de la query string, por ejemplo ?query=teclado. Si la clave no existe, entrega el valor por defecto.
    Ejemplo
    $query = trim((string) $this->request->getQuery('query', ''));
  2. getPost(string $key, mixed $default = null): mixed
    Lee
    Un campo de formulario enviado como POST tradicional, incluidos valores técnicos como un token CSRF o el identificador de pestaña.
    Ejemplo
    $name = trim((string) $this->request->getPost('name', ''));
  3. getJson(string $key, mixed $default = null): mixed
    Lee
    Un valor del body decodificado cuando Content-Type contiene application/json. Si el body no produce un array, los datos JSON quedan vacíos.
    Ejemplo
    $limit = (int) $this->request->getJson('limit', 20);
  4. getHeader(string $key, ?string $default = null): ?string
    Lee
    Un header técnico. Core normaliza los nombres y el método acepta la clave sin distinguir mayúsculas de minúsculas.
    Ejemplo
    $tabId = $this->request->getHeader('x-tab-session');
Contexto HTTP

Consultar la request completa

Estas propiedades y consultas describen la petición actual. Sirven para decisiones puntuales de presentación, no para expresar reglas de aplicación. 

  1. public readonly string $method
    Entrega
    El verbo HTTP recibido. La selección principal del action ya ocurrió en routing; aquí solo corresponde una decisión de presentación muy puntual.
    Ejemplo
    $method = $this->request->method;
  2. public readonly string $path
    Entrega
    El path normalizado sin el script base. Puede usarse para navegación activa o para una response que necesite conocer la URL actual.
    Ejemplo
    $currentPath = $this->request->path;
  3. public readonly array $files
    Entrega
    Los archivos subidos recibidos por PHP. El controller debe validarlos antes de convertirlos en una intención de aplicación.
    Ejemplo
    $document = $this->request->files['document'] ?? null;
  4. expectsJson(): bool
    Reconoce
    Una expectativa JSON mediante Accept: application/json o X-Requested-With: XMLHttpRequest. Un body con Content-Type: application/json no determina por sí solo el formato de salida.
    Ejemplo
    if ($this->request->expectsJson()) {
  return $this->respondJson(
    fn(): array => ['format' => 'json'],
  );
}

Los parámetros declarados en la ruta, como /items/{id:number}, no se buscan en $this->request. Se reciben como argumentos del action, por nombre o mediante #[FromRoute(...)]. Así se mantiene separada la lectura de placeholders de ruta y la lectura del resto de la request HTTP.

Continuidad del action Un controller se lee desde la entrada HTTP hasta la response, no como helpers aislados.

El ciclo normal empieza cuando el router ya eligió el action. El controller recibe parámetros de ruta, lee el resto de la request con $this->request, corta si la entrada HTTP no se puede interpretar con seguridad, y recién entonces construye un input de aplicación.

Action como ciclo 
public function detail(#[FromRoute('id')] string $rawId): HttpResponseInterface
{
  $id = filter_var($rawId, FILTER_VALIDATE_INT);

  if ($id === false || $id <= 0)
    $this->abortController('El identificador del item no es válido');

  return $this->renderControlView(
    'items/detail.page',
    fn() => $this->showItem->execute(new ShowItemInput($id))
  );
}

En ese ejemplo, #[FromRoute('id')] conecta el placeholder de la ruta con el argumento del action. La validación de formato pertenece a presentación porque todavía se está interpretando HTTP. Si el identificador no sirve, abortController(...) devuelve un fallo controlado; si sirve, el use case recibe un ShowItemInput ya explícito y la vista recibe el resultado normalizado.

La firma HttpResponseInterface es el punto común: no significa que todo sea JSON ni que todo sea vista. Significa que el action debe terminar con una response HTTP. El helper elegido define la rama concreta:

  • JSON respondJson(...) Ejecuta la callable, normaliza el payload o UseCaseResult y devuelve ApiResponse con el envelope JSON.
  • HTML render*View(...) Ejecuta la callable, normaliza el resultado como ViewData y carga la plantilla. Allí se lee como $viewModel; el detalle práctico está en Datos en la vista.
  • Redirect redirectTo(...) Devuelve una response de redirección. Si necesita feedback visible, el controller puede guardar un flash antes de cambiar de URL.

Cuando la salida será consumida por Surface, se elige una de esas mismas ramas. La diferencia está en el último adaptador: respondJson(...) convierte el resultado en envelope JSON y renderFragmentView(...) usa la rama HTML para entregar un fragment embebible.

Internamente, la callable también puede devolver una HttpResponseInterface ya construida y AppController la deja pasar. Es un escape avanzado para una response técnica puntual, no el camino normal para omitir ApiResponse o ViewData.

Excepción de presentación Una respuesta local solo corresponde cuando no existe intención de aplicación.

Un action debe terminar con una response HTTP. respondJson(...) permite construirla sin instanciar ApiResponse manualmente. Se le entrega una callable: una función que todavía no se ha ejecutado y que contiene el trabajo necesario para obtener los datos.

Este carril se reserva para adaptar request o configuración técnica ya disponible. Si se consulta, modifica o valida estado de la aplicación, corresponde un use case. El ejemplo solo prepara un dato breve:

Use cases

Un use case representa una capacidad de la aplicación: una intención que el sistema puede resolver aplicando sus propias reglas, sin depender de la interfaz, la URL ni el formato de request desde el cual fue invocado. Su valor está en darle un nombre claro al trabajo real que debe ejecutarse y mantener ese significado aunque cambie el mecanismo de entrada HTTP.

El controller permanece en la frontera HTTP: interpreta la request, extrae la información necesaria y la traduce a nombres que la aplicación entiende. Una vez cruzada esa frontera, el use case no debería necesitar saber si los datos llegaron por query string, formulario, JSON, headers o parámetros de ruta. Solo recibe una entrada ya expresada en términos de la intención que debe resolver.

En la guía, esos datos explícitos que cruzan hacia aplicación se denominan input de aplicación. A partir de esa entrada, el use case mide cuánto trabajo debe coordinar: puede resolver una regla local, tomar una dependencia obligatoria directa o coordinar varias piezas.

Por eso un service no es un requisito de todo use case. Aparece cuando aporta composición real: ordenar varias llamadas, aplicar fallback, transformar datos compartidos o mantener legible una operación amplia. Si solo se valida o calcula algo local, o si solo se toma una dependencia obligatoria directa, agregar un service de paso añade sobreingeniería sin aclarar el flujo.

La relación entre use cases, errores y responses se diagnostica desde Ayuda.

Interfaz del use case execute(...) expresa la intención pública; los helpers protegidos normalizan decisión y fallos.

El use case se invoca desde presentación mediante un método público con nombre estable, normalmente execute(...). Esa firma recibe input de aplicación y devuelve UseCaseResult; no recibe HttpRequest, headers, query strings ni detalles de transporte.

Al heredar de AppUseCase, el caso de uso obtiene helpers protegidos para envolver la operación, cortar por regla de aplicación y entregar un resultado estable. Cada ficha muestra la firma visible, cuándo se usa y un ejemplo mínimo.

Aplicación

Entrar y cerrar la intención

Estas firmas pertenecen al ciclo propio del use case: reciben datos de aplicación, ejecutan la decisión y entregan un UseCaseResult estable al controller. 

  1. execute(SearchItemsInput $input): UseCaseResult
    Entrada
    Input de aplicación, value object o parámetros ya traducidos por el controller.
    Entrega
    Resultado de aplicación con éxito completo, parcialidad o fallo controlado.
    Ejemplo
    return $this->searchItems->execute($input);
  2. run(Closure $callback): UseCaseResult
    Entrada
    Callback que devuelve data simple o un UseCaseResult.
    Efecto
    Normaliza data como éxito y convierte UseCaseFailure o abortUseCase(...) en fallo controlado.
    Ejemplo
    return $this->run(fn() => OperationOutput::from($input));
  3. abortUseCase(
  string $userMessage,
  ErrorKind $errorKind = ErrorKind::VALIDATION,
  ?string $technicalMessage = null,
  ErrorOrigin $origin = ErrorOrigin::APPLICATION,
): never
    Entrada
    Mensaje seguro para usuario, clasificación del error, detalle técnico opcional y origen.
    Efecto
    Corta la intención dentro de run(...) y entrega un UseCaseResult fallido.
    Ejemplo
    $this->abortUseCase('Debe indicar un criterio de búsqueda');

Este panel fija la entrada pública y la envoltura de aplicación. El controller solo llama execute(...) y adapta el UseCaseResult; la elección entre carriles se desarrolla en Carriles internos, cuando ya se reconoce qué tipo de dependencia interviene.

Cómo elegir la salida del use case

La salida debe contar qué ocurrió, no cómo se mostrará. Para elegirla se debe observar si la operación terminó por completo, si puede entregar datos parciales o si debe detener el flujo con un fallo comprensible. La tabla traduce esas situaciones a los mecanismos concretos disponibles.

Situación Funcionalidad recomendada Resultado que llegará al controller Regla de uso
Validación de intención local abortUseCase(...) o fallo explícito. UseCaseResult fallido con mensaje de aplicación. No deben lanzarse errores de HTTP aquí; el controller ya adaptó el request.
Datos calculados sin dependencia externa run(fn() => $data). UseCaseResult::success($data). Devuelve un read model o DTO de aplicación, no arrays improvisados si el shape es compartido.
Una dependencia externa obligatoria directa takeOrAbort($connector->call(...)). Éxito con data, o fallo bloqueante con error del connector. No debe crearse un service si solo delega al connector.
Varias dependencias o fallback runConnectorFlow(...). Éxito completo, parcialidad o fallo según required/optional. Todo connector dentro del bloque debe pasar por el ConnectorFlowInterface.
Transformar data manteniendo errores previos $result->mapData(fn($data) => ...). Mismo estado de éxito/parcialidad/fallo con data mapeada solo si existía data usable. Debe usarse para adaptar output final sin reconstruir errores.

Elegir el adaptador según la salida del controller

El use case entrega significado de aplicación; el controller decide cómo presentarlo. Por eso la misma operación puede terminar como JSON, HTML o una redirección sin cambiar la responsabilidad del use case.

Para JSON se usa respondJson(...); para una vista se entrega el callable a renderControlView(...), renderAccessView(...) o renderFragmentView(...); y cuando el controller necesita inspeccionar el resultado antes de responder, se usa runUseCase(...).

Tres formas de adaptar el mismo contrato 
// JSON: el resultado se convierte en envelope.
return $this->respondJson(
  fn() => $this->searchItems->execute($input)
);

// View SSR: el resultado se convierte en ViewData.
return $this->renderControlView(
  'items/index.page',
  fn() => $this->listItems->execute($input)
);

// Redirect: el controller inspecciona el resultado antes de elegir response.
$result = $this->runUseCase(
  fn() => $this->saveItem->execute($input)
);

if ($result->success)
  return $this->redirectTo('/items');

return $this->renderControlView('items/form.page', fn() => $result);

Conservar el resultado dentro o fuera del adaptador

Si la response final ya es JSON, la ejecución y cualquier efecto de presentación relacionado pueden permanecer dentro del callable de respondJson(...). Cuando el controller necesita inspeccionar el resultado para elegir entre vista, redirect u otra response, primero usa runUseCase(...) y decide después.

Dos ubicaciones válidas para el resultado

    $result = $this->runOperation->execute(

// Varias responses: el resultado se inspecciona antes de responder.
public function submitOperation(): HttpResponseInterface
{
  $result = $this->runUseCase(
    fn() => $this->processOperation->execute(
      $this->operationInput()
    )
  );

  if (!$result->success) {
    return $this->renderControlView(
      'operation/form.page',

  • El controller llama execute(...); no llama run(...), takeOrAbort(...) ni runConnectorFlow(...).
  • El input que cruza la frontera debe expresar aplicación, no detalles de transporte como query string, headers o HttpRequest.
  • Un caso estrecho puede recibir un valor simple o value object. Cuando intervienen varios campos relacionados, conviene agruparlos en un command o input explícito.
  • respondJson(...) y los helpers render*View(...) normalizan el resultado para salida HTTP. runUseCase(...) se reserva para el caso donde el controller debe decidir entre responses.
  • Un UseCaseResult devuelto dentro de respondJson(...) conserva éxito, parcialidad o fallo y no se debe envolver de nuevo.
  • runUseCase(...) normaliza el valor para que el controller pueda inspeccionarlo. No sustituye el ciclo de respondJson(...) ni debe anidarse dentro de él.

Carriles internos

Los carriles internos existen para que el use case conserve el significado de la operación cuando algo sale bien, falla o queda incompleto. No eligen la response HTTP y no reemplazan al controller: empiezan después de que execute(...) ya recibió input de aplicación. Su pregunta principal es: ¿cuánto debe coordinar esta operación para cumplir su intención?

Si todo ocurre con datos locales, basta run(...). Si se necesita una sola dependencia obligatoria y el caso termina cuando esa dependencia falla, se usa el carril simple con takeOrAbort(...). Si se combinan varias respuestas, existen datos opcionales, hay fallback o se acepta una salida parcial, se usa el carril robusto con runConnectorFlow(...).

  • Local run(...) Reglas y datos propios del use case; no hay connector que interpretar.
  • Simple takeOrAbort(...) Una dependencia obligatoria directa: si falla, no hay resultado útil.
  • Robusto required(...) / optional(...) Varias piezas, fallback, datos opcionales o respuesta parcial controlada.
Carriles de use case

// Simple: una dependencia obligatoria directa.

  return $this->takeOrAbort($this->connector->simpleAction($input));

// Robusto: composición, fallback, opcionales o parcialidad.

run(...) La operación valida, calcula o arma una salida con datos ya disponibles. Un callback que devuelve data, un UseCaseResult o corta con abortUseCase(...). Éxito cuando hay data válida, o fallo de aplicación cuando la intención no puede continuar.
takeOrAbort(...) Hay una sola dependencia obligatoria y, si falla, la operación completa debe detenerse. Un ConnectorResult ya producido por un port/connector. Data del connector si tuvo éxito; fallo bloqueante dentro del UseCaseResult si falló.
runConnectorFlow(...) Hay varias fuentes, datos opcionales, fallback o una respuesta que todavía sirve aunque falte una parte. Un callback que recibe ConnectorFlowInterface y decide qué es requerido u opcional. Éxito completo, éxito parcial con errores acumulados, o fallo bloqueante.
Dependencias

Interpretar connectors

Estas firmas solo aparecen cuando el use case consume ports/connectors. Mantienen la decisión en aplicación y evitan que el controller lea ConnectorResult. 

  1. takeOrAbort(ConnectorResultInterface $result)
    Entrada
    Resultado de connector que representa una dependencia obligatoria directa.
    Entrega
    Data del connector si tuvo éxito; si falló, corta con un UseCaseResult bloqueante.
    Ejemplo
    $item = $this->takeOrAbort($this->items->find($input->id));
  2. runConnectorFlow(
  Closure $callback
): UseCaseResult
    Entrada
    Callback que recibe ConnectorFlowInterface y devuelve data compuesta o null.
    Uso
    Varias fuentes, dependencias opcionales, fallback, composición o resultado parcial.
    Ejemplo
    return $this->runConnectorFlow(
  fn(ConnectorFlowInterface $flow) => $this->items->summary($input, $flow),
);
  3. $flow->required(ConnectorResultInterface $result)
    Entrada
    Resultado de connector sin el cual la salida no es válida.
    Entrega
    Data si tuvo éxito; null y fallo bloqueante acumulado si falló.
    Ejemplo
    $item = $flow->required($this->items->find($input->id));
  4. $flow->optional(
  ConnectorResultInterface $result,
  mixed $fallback
)
    Entrada
    Resultado de connector degradable y valor de fallback.
    Entrega
    Data si tuvo éxito; fallback y error acumulado si falló.
    Ejemplo
    $notes = $flow->optional($this->items->notes($item), []);
Cómo leer cada pieza run(...) envuelve la intención; takeOrAbort(...) y el flow interpretan dependencias.

run(...) es la envoltura común de aplicación. Ejecuta el callback del use case, normaliza un valor normal como UseCaseResult::success(...) y transforma fallos controlados de aplicación en un UseCaseResult fallido. Por eso el controller recibe siempre un resultado inspeccionable, no una mezcla de valores sueltos y excepciones esperadas.

takeOrAbort(...) resuelve el caso estrecho: recibe un ConnectorResult, toma su data si la integración fue correcta y corta la operación si esa dependencia obligatoria falló. Ese corte no es una excepción técnica para mostrar al usuario; es una forma controlada de producir un UseCaseResult fallido dentro del ciclo de run(...).

runConnectorFlow(...) abre un flow para una composición. Dentro de ese bloque, $flow->required(...) significa: sin esta respuesta, el resultado no es válido. $flow->optional(...) significa: si falla, se usa un fallback y el error queda registrado para informar que el resultado fue degradado.

  • Requerido $flow->required(...) Si falla, marca fallo bloqueante y devuelve null.
  • Opcional $flow->optional(..., $fallback) Si falla, conserva el error y devuelve el fallback.
  • Cierre runConnectorFlow(...) Al terminar el bloque, convierte lo acumulado en éxito, parcialidad o fallo.
Carril único No se debe mezclar el atajo simple con el flow robusto.

Cada carril concentra una sola forma de decidir fallos. Si se usa takeOrAbort(...) dentro de un bloque robusto, el use case termina con dos lugares diferentes interpretando errores: uno corta de inmediato y el otro acumula decisiones. Esa mezcla vuelve difícil saber qué error bloquea, qué error degrada y qué debe llegar al controller.

La regla práctica es directa: si el use case abrió runConnectorFlow(...), todo connector de ese bloque debe pasar por $flow->required(...) o $flow->optional(...). Si solo existe una llamada obligatoria directa, se queda en takeOrAbort(...) y no se crea un service de paso.

  • El controller nunca llama run(...), takeOrAbort(...) ni runConnectorFlow(...); solo invoca execute(...).
  • run(...) pertenece al use case y convierte la decisión de aplicación en UseCaseResult.
  • takeOrAbort(...) solo se usa con una dependencia obligatoria directa ya normalizada como ConnectorResult.
  • runConnectorFlow(...) se usa cuando la operación necesita distinguir entre requerido, opcional, fallback o parcialidad.
  • Un service aparece cuando agrega coordinación real; no es obligatorio y no debe existir si solo delega una llamada al connector.
  • El use case consume ports/connectors o services de aplicación; no llama clients outbound directos ni decide formato HTTP.
Implementación guiada · Use case SearchItems::execute(...) recibe aplicación, no HTTP.

En este punto la petición HTTP ya fue entendida. El use case recibe una instrucción expresada con datos de aplicación y debe devolver un resultado sin saber si terminará como JSON, una vista o un redirect.

Técnicamente, la llamada entra por el método público execute(...). Esa es la conexión visible entre presentación y use case: execute(...) recibe SearchItemsInput, valida reglas de aplicación y elige el carril interno. El ejemplo siguiente muestra el carril robusto porque necesita composición con un service; no debe leerse como una plantilla obligatoria para todos los use cases.

SearchItems::execute() 
final class SearchItems extends AppUseCase
{
  public function __construct(
    private readonly ItemSearchService $items,
  ) {
  }

  /** @return UseCaseResult<ItemSearchOutput|null> */
  public function execute(SearchItemsInput $input): UseCaseResult
  {
    return $this->run(function () use ($input): UseCaseResult {
      if (trim($input->query) === '')
        $this->abortUseCase('Debe indicar un criterio de búsqueda');

      return $this->runConnectorFlow(
        fn(ConnectorFlowInterface $flow) => $this->items->search($input, $flow)
      );
    });
  }
}

En este caso el constructor recibe ItemSearchService por DI porque la operación necesita coordinación fuera del método. La pieza fija es execute(...): recibe input de aplicación y entra a run(...), que normaliza valores y fallos controlados. runConnectorFlow(...) solo aparece cuando se elige el carril robusto; allí el service puede distinguir dependencias obligatorias y opcionales mediante el flow.

Services y connectors

Estas dos piezas aparecen cuando una operación necesita coordinar trabajo o salir de la aplicación. El service organiza una decisión que requiere varias acciones o transformaciones; el connector cruza la frontera hacia una dependencia externa y traduce su respuesta a un contrato que la aplicación entiende.

Un service solo se justifica si agrega valor: compone llamadas, transforma datos o distingue dependencias obligatorias y opcionales. Un connector no decide presentación ni negocio; habla con el sistema externo y devuelve ConnectorResult.

Si el service coordina APIs HTTP externas, la lectura debe continuar en API HTTP clients externos; si solo se requieren pasos de implementación, se debe consultar Consumir un servicio externo.

Pieza Responsabilidad No debe
Service Coordinar integraciones con sentido de aplicación. Crear responses o lanzar errores de aplicación.
Connector Construir requests externos, mapear fallas a ConnectorResult. Conocer UI, HTML, JSON final o UseCaseResult.
Outbound client Transporte técnico HTTP y mapeo base. Decidir intención de aplicación.
Implementación guiada · Integración Service, port y connector continúan el mismo hilo conductor.

La operación guiada necesita una búsqueda obligatoria y un dato complementario que puede faltar. Esa diferencia es la razón para separar la coordinación del acceso externo: el service declara qué necesita el resultado y el connector se limita a obtener y traducir datos.

En el código, SearchItems::execute(...) delega al service. El service expresa la combinación mediante ConnectorFlowInterface y consume un port de aplicación; no conoce la clase concreta del connector ni el transporte HTTP externo.

ItemSearchService y port 
interface ItemSearchConnectorInterface
{
  public function search(SearchItemsInput $input): ConnectorResult;
  public function stats(SearchItemsInput $input): ConnectorResult;
}

final class ItemSearchService
{
  public function __construct(
    private readonly ItemSearchConnectorInterface $items,
  ) {
  }

  public function search(
    SearchItemsInput $input,
    ConnectorFlowInterface $flow,
  ): ?ItemSearchOutput {
    $items = $flow->required($this->items->search($input));
    $stats = $flow->optional($this->items->stats($input), null);

    if ($items === null)
      return null;

    return new ItemSearchOutput($items, $stats);
  }
}

El port nombra únicamente lo que la aplicación necesita. El connector lo implementa y adapta un client outbound. El alias registrado por ConnectorProvider permite que el contenedor inyecte ItemSearchConnector cuando el service solicita ItemSearchConnectorInterface.

API HTTP clients externos

Cuando la aplicación necesita información de otro sistema, Gateway debe proteger al resto del proyecto de los detalles de ese proveedor. La URL, autenticación, formato de datos y errores externos se traducen en una frontera controlada antes de llegar al use case o a Surface.

Esta sección desarrolla esa frontera de extremo a extremo: configuración, registro, contratos de request y response, transporte, connector y consumo desde aplicación. recipes.html conserva el checklist práctico; aquí se explica por qué existe cada archivo y qué entrega al siguiente.

1. Configurar el servicio

services.json declara el cliente base. Las variables .env API_<SERVICIO>_* pueden sobrescribirlo sin cambiar código.

2. Modelado de request y respuesta externa

Los contratos externos describen qué se envía y qué se espera recibir. Su propósito es aislar la forma del proveedor: si el proveedor cambia un nombre o una estructura, el cambio se corrige en esta frontera y no se propaga como datos ambiguos por toda la aplicación.

El request declara el endpoint mediante #[Endpoint]. En GET, las propiedades públicas se envían como query string. En POST, PUT o DELETE, se envían como JSON. Cuando se requiera una forma especial, corresponde implementar CustomPayloadRequestInterface.

Payload outbound Se debe usar un punto de escape cuando el payload no debe salir crudo.
  • Contrato CustomPayloadRequestInterface Expone payload() para armar el body manualmente.
  • Factory EndpointOutboundRequestFactory Detecta el contrato antes de serializar propiedades.
  • Fallback get_object_vars(...) Se usa cuando la request no implementa el contrato.
  • Fechas date-time -> ATOM / date -> Y-m-d El generador normaliza formatos antes de enviar.
Contrato generado La clase principal respeta PSR-4 y los auxiliares quedan internos.
  • Archivo Una request por archivo y una response por archivo.
  • OpenAPI auxiliar @internal El generador puede agrupar clases internas en el mismo archivo.
  • Límite Esas clases pertenecen al contrato generado, no a la API pública.

4. Consumo del connector desde service o use case

La aplicación debe decidir cuánto depende de cada respuesta externa. Una sola llamada indispensable puede detener la operación si falla; varias llamadas o datos complementarios necesitan distinguir qué es obligatorio y qué puede faltar sin perder todo el resultado.

En el primer caso se puede usar takeOrAbort(...). Cuando hay composición, fallback o datos opcionales, se abre runConnectorFlow(...) para que la pieza que coordina el bloque declare qué es requerido y qué puede degradar.

Flujo robusto 
public function loadItemSummary(int $itemId, ConnectorFlowInterface $flow): ?ItemSummaryOutput
{
  $record = $flow->required($this->externalItems->getRecordByItem($itemId));
  $details = $flow->optional($this->externalItems->listDetailsByItem($itemId), []);

  if ($record === null)
    return null;

  return new ItemSummaryOutput($itemId, $record, $details);
}

public function execute(int $itemId): UseCaseResult
{
  return $this->runConnectorFlow(
    fn(ConnectorFlowInterface $flow) => $this->items->loadItemSummary($itemId, $flow)
  );
}
  • JsonServiceClient no debe llamarse desde controllers, use cases ni desde app-surface.
  • Si se encuentra una llamada directa desde un use case, debe tratarse como deuda puntual y trasladarse detrás de un port/connector antes de usarla como referencia.
  • EndpointListRequest corresponde cuando la API HTTP externa devuelve una lista de DTOs.
  • El connector transforma DTOs externos a read models o outputs de aplicación.
  • Propaga fallos externos con toConnectorResult(...) o asFailure(...); no se deben reconstruir errores ya existentes.
  • Cuando se agregue un servicio nuevo, se debe registrar su provider outbound y confirmar que el port/connector siga la convención de aliases.

Funciones avanzadas del outbound

Estas funciones existen para resolver variaciones frecuentes sin crear un cliente HTTP diferente para cada connector. La elección depende de la forma esperada de la respuesta, la serialización del body o la necesidad de descargar contenido, no del nombre del proveedor.

El client outbound concentra esas decisiones además de los verbos GET y POST, de modo que cada connector no invente su propio transporte.

Pieza Para qué sirve Regla práctica
EndpointRequest Request que espera un DTO único. Debe usarse cuando el payload externo representa un objeto.
EndpointListRequest Request que espera una lista de DTOs. Debe usarse cuando la raíz de respuesta externa es una lista.

JsonServiceResponseMapper Hidrata DTO único o lista y falla si la forma no coincide. Los shapes externos incorrectos no se deben aceptar como éxito silencioso.

Views y respuestas HTTP

Gateway debe entregar una respuesta que el siguiente actor pueda entender sin conocer cómo se produjo. Para navegación o contenido embebible entrega HTML; para intercambio de datos entrega JSON; y para activar la experiencia del navegador publica referencias a los assets compilados por Surface.

Esas salidas forman contratos: Surface consume el HTML, el envelope JSON y las rutas de assets después de que Gateway ya decidió y normalizó la respuesta.

Este punto es el puente central y se desarrolla con mayor detalle en Contratos HTML, JSON envelope y Runtime de pages y fragments.

Controller → vista PHP La vista recibe un modelo ViewData, no variables extraídas automáticamente ni el envelope JSON del bridge.

Este apartado continúa la rama HTML presentada en Ciclo y salidas. El action ya eligió renderAccessView(...), renderControlView(...) o renderFragmentView(...); desde aquí la pregunta es cómo el archivo PHP lee el modelo que recibió.

Cuando renderAccessView(...), renderControlView(...) o renderFragmentView(...) ejecutan su callable, Core normaliza el resultado como ViewData<TData>. El layout incluye después el archivo .page.php, .fragment.php o partial dentro del mismo scope, donde el objeto está disponible con el nombre exacto $viewModel.

Dentro de la plantilla cumple el papel de modelo de vista, pero conserva su nombre y su responsabilidad de salida. Middlewares

Un middleware actúa como una puerta anterior al controller. Sirve cuando la misma condición debe revisarse para varias rutas y no pertenece a una operación concreta. Su decisión es limitada: detener la petición con una respuesta o dejar que el siguiente paso continúe.

Allí caben condiciones transversales como autenticación, tab session, refresh de sesión o headers requeridos. No debe contener la intención funcional que corresponde al use case.

Estructura base 
public function intercept(HttpRequest $request, MiddlewareChainInterface $chain): HttpResponseInterface
{
  // Validar regla transversal del request.
  return $chain->proceed();
}
  • Usar middleware para reglas previas al controller: autenticación, tab session, refresh de sesión o headers requeridos.
  • Si la regla depende de intención de negocio, pertenece al use case, no al middleware.
  • Si corta el flujo, debe emitir una respuesta clara y no dejar al controller inferir qué ocurrió.
  • Los middlewares se ejecutan en el orden declarado. Cada uno decide si llama a proceed(); por eso autenticación puede detener la cadena y refresh debe continuarla.

Seguridad, CSRF y sesión

No toda información de seguridad responde a la misma pregunta. Una protección comprueba que una acción fue enviada desde una página legítima; otra identifica qué pestaña mantiene el contexto autenticado. Confundirlas deja huecos porque ninguna sustituye a la otra.

Gateway aplica ambas protecciones de forma complementaria: CSRF evita envíos falsificados en formularios, mientras que tab session identifica la pestaña autenticada que origina las requests hacia el Gateway.

Flujo de tab session

El recorrido mantiene una identidad separada por pestaña sin crear una cookie distinta para cada una. Surface conserva el identificador local, Gateway crea y valida el contexto, y los headers sincronizan el tiempo restante en cada petición.

  1. Surface crea o recupera un id de pestaña desde sessionStorage.
  2. En login, la vista puede enviar _tab junto con el formulario.
  3. Gateway crea contexto de sesión por pestaña en TabSessionStore.
  4. En requests autenticados, serverClient envía X-TAB-SESSION.
  5. Middleware como RequireAuthentication o RefreshAuthTabSession valida o refresca la pestaña. El refresh respeta SESSION_REFRESH_WINDOW y SESSION_REFRESH_COOLDOWN.
  6. Gateway responde X-REMAINING y Surface actualiza el contador.

Cuándo se refresca realmente

Renovar en cada petición produciría escrituras innecesarias y haría que una sesión activa se extendiera sin un límite legible. La renovación solo ocurre cerca del vencimiento y después de esperar un intervalo mínimo desde la última escritura real.

RefreshAuthTabSession intenta mantener viva la tab activa, pero PhpTabSessionStore::refreshTab(...) no escribe en sesión cada vez. La decisión final vive en TabSessionExpiryService::shouldRefresh(...), que se puede leer como una regla de dos preguntas.

  1. ¿Ya falta poco para vencer? Eso lo marca SESSION_REFRESH_WINDOW.
  2. ¿Ya pasó suficiente tiempo desde el último refresh real? Eso lo marca SESSION_REFRESH_COOLDOWN.

Con SESSION_TIME=10, SESSION_REFRESH_WINDOW=30 y SESSION_REFRESH_COOLDOWN=60, el flujo se entiende mejor con horas concretas:

  1. 12:00:00: login. La tab vence a las 12:10:00 y refreshedAtUnix queda en 12:00:00.
  2. 12:08:00: entra una request. Faltan 2 minutos para vencer, así que no está dentro de la ventana final de 30 segundos. No se refresca.
  3. 12:09:35: faltan 25 segundos para vencer y el último refresh real fue a las 12:00:00. Ya pasó el cooldown, por eso Gateway actualiza refreshedAtUnix y mueve expiresAtUnix a 12:19:35.
  4. 12:09:36: entra otra request o un doble click en "mantener sesión". Solo pasó 1 segundo desde el refresh anterior. La request puede responder bien, pero Gateway no escribe una nueva expiración.
  5. 12:10:35: pasaron exactamente 60 segundos desde el último refresh. Todavía no alcanza, porque el código exige que haya pasado más de 60.

En resumen: el cooldown no bloquea la request; solo evita que cada request protegida alargue la vida de la tab y escriba el archivo de sesión PHP.

Relación entre ventana, aviso y cooldown

Estas tres variables no forman una cadena lineal. Dos viven en Gateway y deciden si se escribe una nueva expiración; la otra vive en Surface y solo decide cuándo se muestra el aviso al usuario. Para que el comportamiento sea legible, primero debe separarse qué pregunta responde cada una.

Variable Quién la usa Pregunta que responde
SESSION_REFRESH_WINDOW Gateway ¿La tab ya está suficientemente cerca de vencer como para permitir una renovación?
SESSION_REFRESH_COOLDOWN Gateway ¿Ya pasó suficiente tiempo desde la última escritura real de refresh para no volver a escribir sesión de inmediato?
SESSION_EXPIRY_ALERT Surface ¿Cuándo debe aparecer el warning o modal de expiración para que el usuario pueda pulsar "mantener sesión"?

El refresh real se decide con una conjunción estricta: debe cumplirse la ventana y debe haber pasado el cooldown. El código lo evalúa como remainingSeconds <= window y now - refreshedAtUnix > cooldown. Ese > es importante: si el cooldown vale 60, exactamente a los 60 segundos todavía no pasa; pasa recién cuando la diferencia es mayor que 60.

Regla práctica El aviso debe estar dentro de la ventana; el cooldown no necesita ser menor que la ventana.
  • Aviso visible SESSION_EXPIRY_ALERT <= SESSION_REFRESH_WINDOW Si el aviso aparece antes de la ventana, Surface puede ofrecer "mantener sesión" cuando Gateway todavía no permite extender.
  • Cooldown independiente puede ser > SESSION_REFRESH_WINDOW Es válido y suele ser deseable. Después de un refresh, la tab sale de la ventana final y no necesita volver a renovarse inmediatamente.
  • Límite superior SESSION_REFRESH_COOLDOWN < SESSION_TIME * 60 Si el cooldown iguala o supera la vida completa de la tab, una tab recién creada difícilmente podrá refrescarse antes de expirar.

Si se espera que el primer click del modal renueve una tab que no se refrescó desde el login, el cooldown debe haber terminado para cuando aparece el aviso. Esa relación se puede leer como SESSION_REFRESH_COOLDOWN < (SESSION_TIME * 60) - SESSION_EXPIRY_ALERT. Con los defaults de esta guía, la cuenta es 60 < (10 * 60) - 30, es decir, 60 < 570; por eso el primer aviso llega cuando el cooldown ya pasó de sobra.

Con los valores habituales, SESSION_TIME=10, SESSION_REFRESH_WINDOW=30, SESSION_EXPIRY_ALERT=30 y SESSION_REFRESH_COOLDOWN=60, el primer aviso aparece cuando la tab ya está dentro de la ventana permitida por Gateway. Además, como el último refresh real fue el login de hace casi diez minutos, el cooldown de 60 segundos ya quedó superado de sobra. Por eso el primer click en "mantener sesión" dentro de esa ventana sí puede renovar.

El problema aparece cuando el aviso se configura por encima de la ventana. Por ejemplo, con SESSION_REFRESH_WINDOW=30 y SESSION_EXPIRY_ALERT=120, Surface mostraría el modal cuando faltan dos minutos, pero Gateway solo acepta refresh cuando faltan treinta segundos o menos. En ese intervalo el usuario puede pulsar "mantener sesión" y ver una respuesta correcta sin que la expiración se mueva, lo que se percibe como un botón inútil aunque el backend esté obedeciendo su regla.

Tampoco conviene llevar el aviso al extremo opuesto. Si SESSION_EXPIRY_ALERT es mucho menor que SESSION_REFRESH_WINDOW, por ejemplo 5 segundos frente a una ventana de 30, Gateway sí permitiría renovar, pero el usuario tendría muy poco margen para leer el modal, decidir y completar la request antes del vencimiento. En redes lentas o con pestañas en segundo plano, ese margen puede ser insuficiente.

El cooldown se interpreta distinto: no mide cuántos segundos faltan para expirar, sino cuántos segundos pasaron desde la última renovación real. Por eso no tiene que ser menor que la ventana. Si el cooldown vale 60 y la ventana vale 30, el sistema funciona bien porque ambas condiciones se miran desde puntos temporales distintos. La ventana mira el futuro de la tab; el cooldown mira el pasado de la última escritura.

La única precaución fuerte para el cooldown es no hacerlo tan grande que choque contra la vida completa de la tab. Con SESSION_TIME=10, la vida equivale a 600 segundos. Un cooldown de 60 es seguro; uno de 590 dejaría solo los últimos segundos como oportunidad real de refresh; uno de 600 o más bloquearía, en la práctica, el refresh de una tab recién emitida antes de que expire.

Casos de prueba de refresh

Los tiempos concretos convierten una regla abstracta en una decisión comprobable: antes de la ventana no se renueva, dentro de la ventana puede renovarse y durante el cooldown no se vuelve a escribir. Estos escenarios validan el límite exacto y la escritura real de expiresAtUnix. Funcionan como pruebas de lectura para comprobar que el sistema no renueva por cada request autenticada.

Escenario de prueba Explicación práctica Resultado esperado
12:00:00, login con SESSION_TIME=10. Se emite metadata nueva: startedAtUnix, refreshedAtUnix y expiresAtUnix. refreshedAtUnix=12:00:00 y expiresAtUnix=12:10:00.
12:08:00, request autenticada. Faltan 120 segundos; todavía es mayor que SESSION_REFRESH_WINDOW=30. No hay refresh. La tab sigue venciendo a las 12:10:00.
12:09:29, borde antes de la ventana. Faltan 31 segundos, apenas fuera de la ventana final. No hay refresh. Sirve para probar el límite exacto de la ventana.
12:09:35, primera request dentro de la ventana. Faltan 25 segundos y pasaron 575 desde el último refresh real. Sí hay refresh. El nuevo expiresAtUnix queda en 12:19:35.
12:09:36, doble click, fetch repetido o fragment inmediato. Tras el refresh anterior faltan 599 segundos y solo pasó 1 segundo de cooldown. No hay nuevo refresh. La request puede ser válida, pero no debe escribir otra expiración.

Bootstrap y DI

Antes de atender una petición, Gateway necesita conocer su entorno y saber cómo construir las piezas que participarán en el flujo. Ese encendido inicial se denomina bootstrap. La inyección de dependencias, o DI, permite que una clase declare lo que necesita sin crearlo manualmente.

Durante ese encendido se crea el contenedor y se registran las piezas de Core y Extension. Una feature normal consume el resultado de este proceso; no debería modificarlo por rutina.

Una feature normalmente no toca esta zona. La consulta al agregar una pieza nueva es: "¿la clase ya entra por autowiring, provider o convención, o realmente requiere registro explícito?".

Errores y resultados

Un error describe por qué una parte del trabajo no pudo completarse; un resultado explica qué pudo entregarse a pesar de ello. Mantener ambas ideas permite distinguir un fallo que bloquea toda la operación de una degradación que todavía deja datos utilizables.

Cada capa clasifica los errores según su responsabilidad. Esto evita que un connector decida sobre la UI, que un service dependa de HTTP o que Surface oculte fallos que el Gateway ya interpretó.

Dos recorridos Un fallo esperado no atraviesa el mismo camino que un error inesperado.
  • Controlado ControllerAbort / UseCaseAbort Las fachadas de Extension lo convierten en ViewData o ApiResponse.
  • Inesperado Throwable / error PHP / shutdown fatal El ErrorHandler central limpia, reporta y presenta una respuesta segura.

Controller Request imposible, CSRF, tab session ausente, parámetro HTTP mal formado. Estado de una API externa o reglas internas del caso. abortController(...) o response segura.
Use case Intención inválida, transición no permitida o input de aplicación inconsistente. Detalles de headers, query string, HTML o transporte. UseCaseResult de éxito, parcial o fallo.

Fallback de error fatal y bootstrap

El manejo central intenta presentar errores con el formato correcto, pero conserva una salida mínima si la propia presentación falla. La idea es no dejar buffers parciales ni trazas crudas en el navegador.

Momento Qué intenta el sistema Fallback si algo vuelve a fallar
Bootstrap temprano Construye una request segura si puede y usa ErrorPresenter para HTML o JSON. BootstrapErrorResponder emite HTML o JSON mínimo con mensaje público.
Durante el request ErrorHandler registra errores PHP, excepciones y shutdown fatal. Limpia buffers abiertos y emite JSON de error interno o texto 500 Internal Server Error.
Render de error Mapea el throwable, lo reporta y decide salida por expectsJson(). Si presentar el error original falla, vuelve al fallback mínimo sin exponer stack crudo.
Serialización JSON Intenta codificar envelope o payload con json_encode(...). Emite un fallo de serialización estable para que el cliente reciba JSON válido.

Semántica del envelope

  • success=true sin errores: éxito completo.
  • success=true con errores: respuesta parcial o degradada.
  • success=false: fallo bloqueante.
  • Los fallos secundarios no deben convertirse en éxito limpio si el usuario debe ver degradación.
  • errorMeta solo debe exponerse cuando el runtime lo permite. En producción, el usuario recibe mensajes seguros, no detalles técnicos.
  • Una excepción inesperada no debe salir cruda: el handler central la mapea, la registra y presenta una salida consistente.

Ciclo HTTP interno

El ciclo HTTP es la cadena común que atraviesa toda petición, incluso cuando las features y respuestas son distintas. Su propósito es preparar una entrada consistente, ejecutar las reglas transversales, invocar el destino correcto y emitir una salida segura.

Esta parte explica por qué un error puede convertirse en JSON o HTML, por qué se emiten headers compartidos y por qué el controller recibe un HttpRequest ya normalizado.

Paso Qué hace Qué NO debe hacer una feature
HttpRequestFactory Normaliza método, path, query, post, JSON, files y headers desde la request actual. Leer $_GET, $_POST o headers globales de forma manual.
RequestLifecycle::begin() Inicia telemetría y registra el manejador de errores según si el request espera JSON. Crear otro error handler local para un controller.
RequestBootstrapPipeline Ejecuta extensiones registradas con app.request_bootstrapper. Actualmente no hay bootstrappers de request registrados. Suponer que aquí se abre sesión PHP o se limpian tabs: esas operaciones son lazy y viven en las piezas de sesión que las necesitan.
RouteDispatcher Carga o construye rutas, ejecuta middleware y llama el controller por el invoker. Esconder rutas dentro de controllers.
ResponseEmitter Emite headers compartidos y luego delega la salida en la response concreta. Hacer echo directo desde un use case o connector.

Route cache

El router puede exportar sus rutas a cache. RouteDispatcher intenta cargarlo primero en cualquier entorno. Si no existe en desarrollo, registra las definiciones y vuelve a calentar el cache. En producción, si no existe, la request falla con PRODUCTION_ROUTE_CACHE_MISSING. Esa falla obliga a ejecutar build:prod antes de atender tráfico.

  • Cambiar un archivo de rutas debe invalidar o preparar nuevamente la cache de rutas antes de desplegar.
  • El cache guarda definiciones ya compiladas; no debe usarse para saltarse validaciones de handler o middleware.
  • Si dos rutas tienen la misma firma, el router debe fallar claro como ruta duplicada.

Caché de producción

En producción se favorece un arranque predecible: el despliegue prepara una vez el contenedor y el mapa de rutas, y las peticiones posteriores reutilizan esos artefactos. Así una petición real no paga el costo ni asume el riesgo de reconstruir la aplicación mientras atiende tráfico.

Por esa razón, Gateway no recompila el contenedor ni vuelve a registrar rutas como fallback durante una request. El runtime productivo espera leer archivos ya generados desde var/cache/releases/<VERSION_DEPLOY>.

Esta decisión hace que un error de deploy falle temprano y de forma explícita: si falta el contenedor compilado, aparece PRODUCTION_CONTAINER_CACHE_MISSING; si falta el cache de rutas, aparece PRODUCTION_ROUTE_CACHE_MISSING. No son errores para maquillar con fallback silencioso, sino señales de que el release no fue preparado.

Preparar Gateway para producción 
# En la raíz del workspace: .env debe tener IS_PRODUCTION=true y VERSION_DEPLOY>0
<raíz-del-proyecto>/app-gateway> composer run build:prod

  • 2. Manifest app-gateway/{PUBLIC_PATH}/ui-assets/.vite/manifest.json Debe existir antes del build productivo de Gateway.

Observabilidad

Cuando una petición cruza rutas, controllers y sistemas externos, un mensaje aislado no basta para entender el fallo. La observabilidad conserva señales del recorrido para responder qué ocurrió, cuánto tardó y en qué frontera cambió el resultado, sin modificar el comportamiento funcional de la petición.

Esas señales permiten saber qué ruta y action se ejecutaron, qué response salió, qué llamada externa fue la más lenta, si hubo degradación parcial y qué correlationId une los registros de la misma ejecución.

La configuración rápida de variables vive en Getting Started / Logs. Esta sección explica el modelo completo: lifecycle, writers, JSON Lines, canales, spans upstream, collector CLI, retención y sanitización.

Pieza Responsabilidad Límite
RequestTelemetryContext Mantiene el contexto vivo de la request: entrada HTTP, correlationId, ruta, response y llamadas upstream observadas. No decide negocio ni modifica la salida; solo conserva datos para cerrar el registro.
RequestTelemetryLogger Escribe access, metrics, error y upstream usando el writer configurado. Respeta LOG_TELEMETRY_ENABLED y LOG_UPSTREAM_SPANS; no debe mezclarse con decisiones de dominio.
TracingHttpClient Envuelve llamadas outbound y registra duración, status, timeouts, origen del error y payload sanitizado. Solo observa el client; no transforma un fallo upstream en éxito de negocio.
LogWriterFactory Selecciona el destino: JSONL semanal para web, stdout para CLI. El canal lógico del evento no implica archivo separado; todos los canales se serializan como líneas JSON.
ObservabilityConfig Centraliza los defaults de LOG_TELEMETRY_ENABLED y LOG_UPSTREAM_SPANS. No controla retención ni flush del collector; esas variables se aplican en otras piezas.
WeeklyLogNamespacePruner Limpia carpetas semanales de logs según LOG_RETENTION_WEEKS. Solo actúa cuando se ejecuta el comando de limpieza; no borra logs automáticamente en cada request.
LogSanitizer Recorre estructuras antes de serializarlas y reemplaza claves sensibles por [SENSITIVE]. Reduce exposición accidental, pero no convierte el log en un almacén para datos de negocio sensibles.

Lifecycle, correlation id y cierre

El registro debe abrirse al comenzar la petición, enriquecerse mientras avanza y cerrarse una sola vez cuando se conoce el resultado. Ese recorrido se denomina lifecycle. El correlation id es el identificador que permite reunir eventos escritos en momentos o canales distintos.

La telemetría normal empieza en RequestLifecycle::begin(). Si LOG_TELEMETRY_ENABLED=true, RequestTelemetryContext crea un contexto para la request actual. Ese contexto toma el header X-CORRELATION-ID cuando existe; si no llega desde el cliente, genera un identificador propio para unir los eventos de la misma ejecución.

Durante el dispatch, la ruta puede marcar controller y action; una response observable puede marcar status, response type y contexto de salida; y un client HTTP instrumentado puede agregar spans upstream. Al final, el Kernel completa la telemetría en finally solo cuando la response ya fue emitida. Para errores no manejados, RequestErrorReporter cierra el mismo contexto por una ruta especializada. El cierre es idempotente: una misma request no debe producir access/metrics duplicados.

Momento Qué ocurre Señal resultante
Inicio Se crea el contexto si LOG_TELEMETRY_ENABLED=true. Queda disponible correlationId para request, outbound y error reporter.
Routing El dispatcher marca controller y action resueltos. access puede indicar qué action atendió la entrada.
Outbound TracingHttpClient mide cada llamada y la agrega al contexto. metrics y access pueden incluir resumen upstream.
Response La response observable aporta status, tipo y contexto de salida. El log no queda limitado a una excepción: también sabe qué se emitió.
Cierre RequestTelemetryCompletion reclama el cierre y escribe los canales necesarios. Se evitan duplicados aunque el cierre normal y el reporter de errores compitan por la misma request.

JSON Lines y destinos físicos

Los registros deben poder agregarse y consultarse sin volver a escribir un documento completo. Por eso cada evento se guarda como una unidad independiente en una línea. Este formato se denomina JSON Lines o JSONL.

El archivo puede crecer de forma incremental, leerse línea por línea y filtrarse por channel, correlationId, status o path.

El canal no define un archivo físico separado. LogWriterInterface recibe un LogChannel, pero el writer agrega ese valor como campo channel dentro del JSON. En web, el destino físico es una carpeta semanal bajo app-gateway/var/log; en CLI, el destino inicial es stdout.

  • Web develop app-gateway/var/log/develop/YYYY-WNN/stdout.jsonl
  • Web production app-gateway/var/log/production/YYYY-WNN/stdout.jsonl
  • Semana ISO YYYY-WNN La carpeta se calcula con el año ISO y número de semana.
  • CLI php://stdout El proceso emite líneas; otra pieza puede persistirlas.

Si el writer web no puede abrir el archivo, no debe romper la response del usuario. Por eso la escritura de logs está aislada: crea la carpeta si falta, intenta escribir en modo append y retorna sin interrumpir el flujo si el destino no está disponible.

Canales y lectura operativa

Un canal es una etiqueta que indica qué clase de señal representa una línea: acceso, métricas, error o llamada externa. No es necesariamente otro archivo; es una forma de separar preguntas dentro del mismo registro.

Para leer un archivo JSONL, conviene empezar filtrando por channel y luego por correlationId. Así se reconstruye una request desde su entrada, métricas, errores y llamadas externas.

Canal Cuándo aparece Qué permite diagnosticar
access Al completar una request o al reportar un error no manejado con type=error_access. Une método, path, ruta, tab, status, response type, duración, request sanitizado, response context y resumen upstream.
metrics En el cierre normal o en el cierre por error de una request con telemetría activa. Permite leer costo total del request, cantidad de upstreams, duración acumulada, errores y llamada más lenta.
error Con status >= 500, degradación por upstream operativo o error no manejado reportable. Distingue server_error_response, degraded_response y unhandled_error.
upstream Cuando LOG_UPSTREAM_SPANS permite detalle por llamada outbound. Diagnostica latencia, timeouts, status externos, origen del error, excepción técnica y tamaño de respuesta.
bootstrap Cuando el fallo ocurre antes o durante la construcción inicial del Gateway. Explica fallos de contenedor, rutas, entorno, versión de deploy, cache y artefactos esperados.

Spans upstream

Un span es el registro de una operación con inicio, duración y resultado. Se denomina upstream cuando esa operación es una llamada que Gateway realiza hacia un sistema externo.

TracingHttpClient observa esas llamadas. Cuando la telemetría general está activa, el span siempre se agrega al contexto de la request para que access y metrics puedan resumir cantidad de llamadas, errores, errores operativos y llamada más lenta. La línea detallada del canal upstream se escribe solo si LOG_UPSTREAM_SPANS lo permite.

Valor Resultado Uso recomendado
auto Activo si IS_PRODUCTION=false; desactivado si IS_PRODUCTION=true. Valor normal. Da detalle en desarrollo sin llenar producción con una línea por dependencia.
true Escribe un evento upstream por cada llamada outbound. Útil en diagnóstico controlado cuando se necesita seguir cada request hacia servicios externos.
false No escribe el detalle por llamada. El resumen puede seguir en access y metrics. Adecuado cuando solo interesa saber conteos, duración total y upstream más lento.
  • Identidad serviceName / method / baseUri / endpoint Permite ubicar qué dependencia recibió la llamada.
  • Tiempo durationMs / timeoutSeconds Ayuda a distinguir lentitud propia de lentitud externa.
  • Fallo origin / exceptionClass / timedOut Un error operativo es transporte, timeout o status >= 500.
  • Payload payload Se registra sanitizado antes de salir al JSONL.

CLI, stdout y collector

Un proceso web puede persistir sus eventos directamente. Un comando de consola, en cambio, suele escribirlos en su salida estándar para que otra pieza decida dónde guardarlos. Esa salida se denomina stdout y la pieza que la lee y persiste se denomina collector.

En web, Gateway escribe en el archivo semanal. En CLI, el writer elegido por LogWriterFactory es StreamLogWriter apuntando a php://stdout. Eso significa que el proceso de consola emite líneas JSON, pero no necesariamente las deja persistidas en var/log.

El collector existe para ese segundo escenario: toma una salida de consola, la lee como flujo de líneas y la persiste en la misma organización semanal por entorno. En términos de ingeniería, actúa como puente entre un proceso que solo sabe escribir en stdout y el almacenamiento JSONL esperado por la observabilidad.

  • Productor Proceso CLI Emite una línea JSON por evento.
  • Transporte stdout La salida estándar funciona como stream intermedio.
  • Collector tools/Observability/log-collector/collect.php Lee el stream y persiste eventos por entorno.
  • Flush LOG_COLLECTOR_FLUSH_EVERY Define cuántas líneas se acumulan antes de forzar escritura del lote.

Un valor bajo de LOG_COLLECTOR_FLUSH_EVERY reduce la ventana de pérdida si el proceso se corta de forma abrupta, porque el collector empuja datos al archivo con más frecuencia. Un valor alto agrupa más eventos antes de escribir, lo que puede ser más eficiente en salidas grandes. Esta variable no participa en requests web normales.

Retención de logs

Conservar todos los registros indefinidamente consume espacio y dificulta la operación. La retención define durante cuánto tiempo se mantienen y elimina grupos completos cuando quedan fuera del período configurado.

En este proyecto se calcula por carpetas semanales, no por líneas individuales. WeeklyLogNamespacePruner interpreta LOG_RETENTION_WEEKS, calcula el inicio de la semana ISO actual y elimina carpetas con nombre YYYY-WNN anteriores al corte.

Configuración Comportamiento Detalle
LOG_RETENTION_WEEKS=12 Conserva la semana actual y 11 anteriores. Es el default de runtime si el valor falta o no es numérico.
LOG_RETENTION_WEEKS=1 Conserva solo la semana ISO actual. Es agresivo; útil solo para entornos con poco espacio o logs regenerables.
LOG_RETENTION_WEEKS=0 Falla al ejecutar la limpieza. El pruner exige un entero final mayor que 0.
composer run logs:prune Ejecuta la limpieza. Se revisan var/log/develop, var/log/production y el legado directo bajo var/log.

La limpieza no se dispara automáticamente por cada request. Debe ejecutarse como tarea operativa o paso manual cuando se quiera aplicar el corte configurado.

Sanitización, headers y límites

La observabilidad registra datos útiles para diagnóstico, pero no debe convertirse en un espejo completo del request. RequestTelemetryLogger filtra headers antes de enviarlos al sanitizador: conserva host, referer, cookie y headers sec-ch-ua*. Luego LogSanitizer reemplaza valores asociados a claves sensibles.

  • Claves sensibles authorization / cookie / password / token También cubre bearer, secret, api key, client secret y CSRF.
  • Valor sustituido [SENSITIVE] El campo queda visible, pero no su contenido real.
  • Strings largos 500 caracteres Luego se agrega el marcador ...[TRUNCATED].
  • Resources [RESOURCE] No se intenta serializar handles del runtime.

Cuando se reporta un error, la traza se reduce a campos de ubicación como archivo, línea, función y clase antes de llegar a logs o respuestas. La regla práctica es simple: el log debe permitir diagnosticar el flujo, pero no debe exponer secretos ni capturar objetos internos completos.

Relacionado: configuración de logs en .env y Troubleshooting.

  • Cuando se agregue una response nueva, debe evaluarse si corresponde implementar ObservableResponseInterface.
  • Cuando se agregue un client HTTP transversal, debe conservarse el rastro de upstream calls y la sanitización.
  • La observabilidad no debe decidir negocio. Sirve para observar el sistema, no para cambiar el flujo de aplicación.

Flujo completo de Gateway

Gateway recibe una entrada HTTP, decide la intención de aplicación y devuelve una salida controlada: HTML, JSON, fragment o redirect. El camino cambia según el tipo de caso, pero las fronteras se mantienen: el resultado se consume desde Surface y se expresa mediante el JSON envelope o los contratos HTML.

Este mapa consolida la implementación guiada por etapas: ruta, controller, use case, service, port y connector y response JSON.

  1. Entrada HTTP

    Ruta

    @extension/Presentation/Http/Routing/ExtensionRouteRegister.php

    Aquí vive la URL, el verbo HTTP y el action del controller. Si la ruta tiene middlewares, se ejecutan antes de llegar al action. No decide negocio ni arma respuestas. 

    $router->post('/items/search', [ItemController::class, 'searchItems']);

    Entrega a: ItemController::searchItems(...). Ver detalle.

  2. Presentación

    Controller

    @extension/Presentation/Http/Controller/ItemController.php

    Aquí se lee el request, se construye el input y se elige la respuesta. Puede cortar por errores de presentación, pero no debe hablar con proveedores externos.

    • $this->request es el HttpRequest que Core inyecta antes de invocar el action. Se usan getQuery(...), getPost(...), getJson(...) y getHeader(...) para leer la entrada HTTP.
    • respondJson(fn() => ...) ejecuta una intención y la convierte al envelope JSON del bridge. Si el callable devuelve datos sin normalizar, se normalizan como éxito; si devuelve UseCaseResult, se respeta su éxito, parcialidad o fallo.
    • $this->searchItems representa un use case: una clase de Application/UseCase inyectada por DI que expresa la intención de aplicación. El nombre debe reemplazarse por la intención real de la feature. 
    public function __construct(
  private readonly SearchItems $searchItems,
) {
}

public function searchItems(): HttpResponseInterface
{
  $input = new SearchItemsInput(
    query: (string) $this->request->getJson('query', ''),
    status: (string) $this->request->getJson('status', ''),
  );

  return $this->respondJson(
    fn() => $this->searchItems->execute($input)
  );
}

    Use case

    @extension/Application/UseCase/Items/SearchItems.php

    return $this->runConnectorFlow(
