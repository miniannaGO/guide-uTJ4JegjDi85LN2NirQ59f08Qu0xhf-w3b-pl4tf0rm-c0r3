Cómo usar estas guías

Cada receta es una ruta de construcción. Primero se presenta el resumen del escenario para identificar el contrato involucrado; después aparece el checklist completo. Los pasos de verificación son obligatorios porque ahí suelen aparecer los errores de bridge. El orden baja desde Gateway hacia Surface: ruta, controller, salida HTML/JSON, outbound cuando exista, integración UI, sesión, assets y diagnóstico.

Crear una página SSR con comportamiento UI

Antes de crear archivos, debe revisarse cómo se conectan Controllers, Runtime de pages y fragments y Contratos HTML.

  1. Agregar o ubicar la ruta en `Extension/Presentation/Http/Routing`.
  2. Crear el método en controller y usar `renderControlView(...)` o `renderAccessView(...)`.
  3. Crear la vista `.page.php` en `resources/views`.
  4. Cuando necesite JS, debe declararse `data-surface-page="feature-id"`.
  5. Crear `workspace/integrations/feature/integration.ts`.
  6. Crear `page.ts` con `UiBinding` o `mount(...)`.
  7. Registra la integración en `workspace/integrations/registry.ts`.
  8. Ejecutar `npm run lite:build` para compilar assets en modo watch local.
Vista SSR + root surface 
<div class="row" data-surface-page="demo-items">
  <button id="btn-search" type="button" class="btn btn-primary">Buscar elementos</button>
  <div id="item-search-result"></div>
</div>

Crear un fragment dinámico

Los fragments son un contrato compartido: amplía en Contratos HTML y Runtime de pages y fragments.

  1. Declara ruta de fragment bajo el grupo correcto.
  2. El controller responde `renderFragmentView(...)`.
  3. La vista `.fragment.php` devuelve HTML real.
  4. Cuando necesite JS, debe usarse `data-surface-fragment="fragment-id"`.
  5. Registra el fragment en la integración propietaria.
  6. Desde surface inserta el HTML con `serverClient.html(...)`; si el fragment es montable, declara el `fragmentId` esperado con `expect`.
Cargar fragment desde page binding 
this.onClick(button, async () => {
  const html = await serverClient.html("/items/summary", {
    expect: { kind: "fragment", fragmentId: "item-summary" },
  });
  this.setHtml("#item-summary-container", html);
});

Crear un endpoint JSON

Para entender qué debe devolver este endpoint, consulta JSON envelope y HTTP, sesión y errores UI.

  1. Declara ruta.
  2. Controller prepara input y llama use case.
  3. Use case retorna `UseCaseResult`.
  4. Controller responde con `respondJson(...)`.
  5. En Surface, declara las firmas visibles del endpoint Gateway en `workspace/integrations/<feature>/contracts.ts`.
  6. Si existe Swagger/OpenAPI, puedes generar ese bloque con `composer robo -- surface:contract <feature> <RequestSignature> <ResponseSignature> <swaggerPath>`. La implementación Surface vive en `tools/HttpContractGenerator/Surface`; Gateway vive en `tools/HttpContractGenerator/Gateway` y lo común en `tools/HttpContractGenerator/Shared`.
  7. `api.ts` importa esas firmas y tipa `serverClient.data(...)` o `serverClient.json(...)`.
  8. `actions.ts` arma el request tipado desde valores recibidos de `page.ts` o del fragment. `page.ts` debe quedarse leyendo DOM y llamando acciones.
  9. Surface consume con `serverClient.json(...)` o `serverClient.data(...)`.
Controller JSON 
public function search(): HttpResponseInterface
{
  $input = SearchItemsInput::fromRequest($this->request());

  return $this->respondJson($this->searchItems->execute($input));
}

Consumir un servicio externo

Esta receta cruza hacia un backend proveedor o API HTTP externa, que sirve como dependencia outbound: amplía en API HTTP clients externos, Flujo externo completo y Tools.

  1. Revisar `app-gateway/services.json`.
  2. Agregar overrides `API_<SERVICIO>_*` si hace falta.
  3. Crear o generar DTO en `Contract/Outbound`.
  4. Crear o generar request con `#[Endpoint]` bajo `Infrastructure/Outbound/Client/<Servicio>/Request`.
  5. Implementa connector en `Infrastructure/Outbound/Connector`.
  6. Definir o reutilizar un port en `Application/Port`.
  7. Consumir desde use case simple o service robusto.

Agregar un provider o resolver DI

Antes de un registro manual, se debe revisar Bootstrap y DI y confirma si autowiring o ConnectorAliasRegistrar ya resuelven la clase.

  1. Ubica si la pieza pertenece a Core o Extension.
  2. Si es transversal de Core, corresponde revisar RootProvider.php.
  3. Si es concreta de la app, corresponde revisar AppProvider.php.
  4. Para ports/connectors, primero intenta la convención *ConnectorInterface → *Connector.
  5. Registra manualmente solo si hay alias, runtime concreto o adapter externo.
  6. Si producción usa cache de contenedor, el deploy debe regenerarla o limpiarla.

Agregar una integración UI

Cuando se requiera lifecycle, limpieza o adapters, la referencia principal es Bindings y lifecycle y Workspace integrations.

  1. Crear carpeta en `workspace/integrations/<feature>`.
  2. Definir `integration.ts` con `id`, `layout`, `page.load` y fragments.
  3. Crear `page.ts` con `UiBinding` cuando se requiera lifecycle.
  4. Crear `contracts.ts` cuando haya payloads o responses JSON de Gateway visibles para Surface.
  5. Usar `surface:contract` si las firmas vienen de Swagger/OpenAPI; su implementación está en `tools/HttpContractGenerator/Surface` y genera clases TypeScript.
  6. Centraliza llamadas en `api.ts` y usa tipos de `contracts.ts`.
  7. Centraliza intención UI en `actions.ts`: recibe valores de `page.ts`, arma requests tipados y coordina feedback.
  8. Centraliza adapters repetidos en `controls.ts`.
  9. Registra la integración en `registry.ts`.

Montar HTML remoto dentro de modal o toast

La mecánica completa está en Content mount y el contrato HTML en Contratos HTML.

  1. Gateway debe devolver un fragment HTML embebible con renderFragmentView(...).
  2. Cuando el fragment tenga comportamiento, debe agregarse data-surface-fragment.
  3. Registra ese fragment en la integración propietaria.
  4. En el binding, usa simpleModal.withContentMount(this.contentMount) o toastAdapter.withContentMount(...).
  5. Si necesitas showRemote, importa modal o toast desde @/platform/infrastructure/feedback y declara expect si el contenido trae fragment montable.
  6. No deben ejecutarse scripts embebidos ni montarse fragments manualmente.
Modal remoto con contentMount 
import { simpleModal } from "@/platform/infrastructure/feedback";

private readonly modal = simpleModal.withContentMount(this.contentMount);

await this.modal.showRemote("/items/summary", {
  method: "GET",
  params: { itemId },
  expect: { kind: "fragment", fragmentId: "item-summary" },
});

Montar un adapter UI

Los adapters deben consumirse desde `toolkit` y destruirse durante el desmontaje. No se debe acceder a globals legacy directamente cuando existe un adapter.

La regla de limpieza se explica en Bindings y lifecycle y el catálogo de helpers en Toolkit, adapters y feedback.

Mount / unmount controls 
protected mount(): void {
  this.select = this.require<HTMLSelectElement>("#my-select");
  select2Adapter.initialize({ element: this.select });
}

protected unmount(): void {
  if (this.select) select2Adapter.destroy(this.select);
}

Validar CSRF y tab session

Amplía la frontera entre ambos lados en CSRF y tab session y Seguridad, CSRF y sesión.

  1. La vista SSR de acceso debe imprimir el campo _csrf.
  2. Surface debe ejecutar ensureTabSession() en layout access/control.
  3. Si hay formulario, ensureTabSession() debe completar _tab.
  4. El controller valida CSRF antes de ejecutar el use case.
  5. Las rutas autenticadas leen X-TAB-SESSION desde serverClient.
  6. X-REMAINING debe llegar en respuestas para sincronizar expiración.

Mostrar un mensaje flash

La API vive en Controllers y el storage por pestaña se explica en Seguridad, CSRF y sesión.

  1. Ejecuta la acción de aplicación desde el controller.
  2. Si la acción termina bien y vas a redirigir, llama flashMessage(...).
  3. En la vista destino, pasa pullFlashMessages() como data para renderizar los avisos.
  4. No leas $_SESSION desde la view ni desde Surface.
Controller con flash 
public function store(): HttpResponseInterface
{
  $input = new SaveItemInput(
    name: (string) $this->request->getPost('name', '')
  );

  $result = $this->saveItem->execute($input);

  if ($result->success) {
    $this->flashMessage('success', 'Elemento guardado correctamente');
    return $this->redirectTo('/items');
  }

  return $this->renderControlView('items/form.page', fn() => $result);
}

public function index(): HttpResponseInterface
{
  return $this->renderControlView(
    'items/index.page',
    fn() => ['flashMessages' => $this->pullFlashMessages()]
  );
}

Diagnosticar route cache

El ciclo está explicado en Ciclo HTTP interno. Cuando una ruta nueva no aparezca en producción, el diagnóstico debe iniciar aquí.

  1. Confirmar que la ruta exista en el archivo correcto de Extension/Presentation/Http/Routing.
  2. Validar que el grupo padre cargue ese archivo con $router->load(...).
  3. Revisar duplicados de firma: misma ruta parametrizada y mismo verbo.
  4. En producción, limpia o recalienta cache antes de probar la ruta.
  5. Si falla el handler, deben revisarse el binding por nombre y #[FromRoute(...)].

Trazar un error con correlation id

La relación entre errores y headers se explica en Observabilidad y Contratos de error HTTP.

  1. Busca X-Correlation-Id en la respuesta del navegador.
  2. Ubica el registro relacionado en logs de Gateway.
  3. Revisar el status HTTP y el envelope si la respuesta fue JSON.
  4. Si hubo upstream, deben revisarse duración, status y origin registrado.
  5. Si Surface lanzó HttpContractError, compara Accept, Content-Type y body.

Agregar una variable .env

Para clasificar defaults, obligatoriedad y efectos reales, consulta Archivo .env y Assets Vite.

  1. Definir si la variable es runtime, assets, sesión, UI u outbound.
  2. Agregar documentación en `.env.template`.
  3. Leer la variable desde el factory/config correspondiente.
  4. Si afecta Surface, valida `vite.config.ts` y `app-config.ts`.
  5. Actualiza referencia y soluciona problemas si cambia onboarding.

Actualizar documentación viva
