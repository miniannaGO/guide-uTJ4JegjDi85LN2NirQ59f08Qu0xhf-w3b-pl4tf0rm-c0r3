Método de diagnóstico

Diagnosticar consiste en encontrar la primera promesa que dejó de cumplirse, no en cambiar el archivo más cercano al síntoma. Primero se describe qué debía recibir el usuario o la capa siguiente; después se compara esa expectativa con la salida real y con la evidencia disponible.

El fallo se debe leer en el mismo orden en que corre la solución: request HTTP, ruta, middleware, controller, use case, service/connector si existe, response y finalmente Surface. Si el error aparece al final, igual conviene confirmar que los pasos anteriores entregaron el contrato esperado.

En cada paso se responde lo mismo: qué entró, qué debía salir, qué salió realmente y qué señal permite demostrarlo. La búsqueda termina en la primera diferencia comprobable. Solo entonces corresponde revisar la implementación responsable de esa frontera.

Para aplicar el método sin perder el mapa, se puede cruzar esta página con Referencia, JSON envelope, Assets Vite y Runtime de pages y fragments.

La pregunta inicial no es “¿qué archivo cambio?”, sino “¿qué promesa se rompió?”. Si el navegador esperaba HTML y recibió JSON, el problema está en el contrato de respuesta. Si Surface no monta, primero se debe confirmar que el HTML tenga el atributo correcto. Si el use case falla, debe revisarse si el error nació por input, por estado de aplicación o por una dependencia externa. Esa disciplina evita arreglos al azar.

  1. Identificar la salida esperada: página, fragment, JSON, redirect o asset.
  2. Revisar status HTTP y Content-Type. Si se esperaba HTML y llegó JSON, se trata de un error de contrato.
  3. Si es JSON, validar success, data, message y errors[].
  4. Si es Surface, revisar data-surface-page-status o data-surface-fragment-status.
  5. Si hay sesión, confirmar X-TAB-SESSION en request y X-REMAINING en response.
  6. Si hay proveedor externo, seguir el rastro desde use case hacia service, connector, client y ConnectorResult.
  7. Usar X-CORRELATION-ID para unir navegador, logs de Gateway y llamadas upstream.

Entrada HTTP, controller y respuesta

Esta frontera responde si el request llegó al destino correcto y si el destino produjo el tipo de respuesta prometido. Antes de revisar lógica interna, se confirman método, URL, parámetros, middleware, acción del controller, status y Content-Type.

Ruta nueva no responde

Validar que el archivo de routing se cargue, que no exista una firma duplicada y que la cache de rutas/contenedor no esté desactualizada en producción.

Ver: Routing, interfaz del router, caché de producción y make:route-controller.

CSRF inválido

Debe revisarse que la vista SSR renderice _csrf, que el formulario lo envíe y que el controller valide antes del use case. No lo debe confundirse con X-TAB-SESSION.

Ver: seguridad y sesión, controllers y HTTP de Surface.

HTML esperado pero llega JSON o layout

serverClient.html(...) lo tratará como contrato roto si llega JSON, redirect, layout completo, page de Surface o un fragment distinto al esperado. Deben revisarse controller, renderFragmentView(...) y la opción expect.

Ver: views y fragments, serverClient.html, content mount y contratos HTML.

JSON inválido

El body debe tener success booleano. Deben revisarse respondJson(...), ApiResponse y use case.

Ver: JSON envelope, respondJson, use cases y consumo desde Surface.

JSON del request llega vacío

Gateway solo decodifica body JSON cuando Content-Type declara application/json. Si el body no decodifica a array, getJson(...) verá fallbacks en vez de lanzar una excepción.

Ver: request del controller, serverClient y headers HTTP.

Ruta existe, pero otro método falla

El router busca dentro del verbo HTTP recibido. Si el path existe en otro método, el comportamiento actual es ruta no encontrada; no hay una respuesta 405 separada.

Ver: interfaz del router, errores y status y rutas.

Error temprano de bootstrap

Si el contenedor, configuración o bootstrap fallan antes del lifecycle HTTP normal, Gateway intenta construir una request segura y presentar HTML o JSON. Si esa presentación también falla, responde con un fallback mínimo.

Ver: fallback de errores, caché de producción y observabilidad.

Error durante render o serialización

Si una view, response o serialización JSON falla, el handler central limpia buffers antes de presentar el error. Si el error presenter tampoco puede responder, la salida cae a JSON de error interno o texto 500.

Ver: errores Gateway, responses y señales de diagnóstico.

HTML vacío, layout o Content-Type raro

serverClient.html(...) exige HTML embebible. Debe revisarse que Gateway no devuelva JSON, body vacío, redirect, layout completo, page inesperada ni Content-Type incompatible desde el controller o el error presenter.

Ver: views, JSON y assets, errores Gateway y validación HTML en Surface.

Use case, service y resultado

Después de confirmar la entrada HTTP, se comprueba si la operación entendió la intención solicitada y conservó su resultado al coordinar otras piezas. Aquí importan los datos de entrada, el éxito, los errores y la parcialidad; todavía no corresponde discutir cómo se muestran en HTML o en Surface.

Parcialidad no se muestra

El envelope debe ser success=true con errors.length > 0. Debe revisarse setPartialReporter(...) en startup y que el use case no convierta una degradación en éxito limpio.

Ver: parcialidad JSON, use cases, services y connectors y partial reporter.

Connector, service client y contratos externos

Si la operación depende de otro sistema, se separa primero un fallo de construcción de un fallo de comunicación o de interpretación. El recorrido va desde provider y alias hacia connector, client y objeto de respuesta: cada paso debe recibir una forma conocida y devolver otra forma comprobable.

DI no encuentra clase

Deben revisarse namespace PSR-4, provider correspondiente, tags/aliases y cache del contenedor.

Ver: Bootstrap y DI, caché de producción y make:service-client.

Alias de connector falla

ConnectorAliasRegistrar espera un port *ConnectorInterface y una implementación única *Connector bajo Infrastructure/Outbound/Connector. Si hay cero o varias coincidencias, el alias se debe registrar explícitamente o el nombre se debe corregir.

Ver: services y connectors, clients externos y make:connector.

DTO externo no hidrata

Debe revisarse si el request implementa EndpointRequest o EndpointListRequest según la forma real. Si la API HTTP Externa devuelve objeto cuando se esperaba lista, JsonServiceResponseMapper debe fallar claro.

Ver: API HTTP clients externos, http:contract y flujo ConnectorResult.

Contrato outbound inválido

Si falta #[Endpoint(...)], el path está vacío o responseClass no existe, el fallo debe aparecer antes de despachar la llamada externa. No debe resolverse en Surface ni esconderse como data vacía.

Ver: funciones outbound, referencia outbound y http:contract.

Servicio externo no configura

Si falta la entrada en services.json, la URI queda vacía, un timeout no es numérico o TLS no se puede parsear como booleano, la definición del servicio falla antes del connector.

Ver: variables outbound, configurar el servicio y outbound rápido.

Surface: page, fragment y adapters

Surface se revisa después de demostrar que Gateway entregó el HTML o JSON correcto. Entonces se valida que el DOM declare la integración esperada, que el registry la conozca, que el montaje encuentre su raíz y que eventos, fragments y adapters se limpien al desmontar.

No monta una page

Validar data-surface-page, integration.id, layout correcto y registro en uiIntegrationRegistry.

Ver: runtime de montaje, workspace integrations y startup y layouts.

Page registrada con otro id

El valor de data-surface-page debe coincidir con UiIntegration.id. Si no coincide, el runtime avisa y no debe montar un módulo no correspondiente por accidente.

Ver: interfaz de runtime, registro de integraciones y atributos SSR en Gateway.

No monta un fragment

El fragment debe estar en fragments de la integración propietaria. Si está en modal/toast, debe usarse withContentMount.

Ver: runtime, content mount y fragments SSR.

Fragment en modal no monta

El modal o toast debe usar withContentMount(...). Confirmar que el HTML tenga data-surface-fragment y que el fragment esté registrado en la integración propietaria.

Ver: montaje de HTML remoto, toolkit de feedback y consumo Gateway.

Estado externo sin destruir

Debe revisarse que unmount() destruya o limpie cualquier plugin legacy, listener externo o estado fuera del binding antes de reemplazar HTML. El problema no es tener otro archivo adapter, sino montar estado externo sin su destroy correspondiente.

Ver: bindings, adapters de toolkit y ciclo de reemplazo.

Sesión, runtime y assets

Este grupo reúne síntomas parecidos con causas distintas. La sesión determina identidad y tiempo; los headers transportan esas señales; el runtime decide qué integración montar; los assets determinan si el código compilado llegó al navegador. Cada carril debe comprobarse por separado.

Mantener sesión no suma tiempo

No toda llamada de refresh extiende la sesión. Gateway solo suma tiempo cuando la tab está en ventana de renovación y ya pasó el cooldown.

  • Respuesta X-REMAINING Permite confirmar si el vencimiento cambió.
  • Metadata tabs.{tabId}.metadata Permite revisar la expiración y el último refresh de la tab.
  • Ventana SESSION_REFRESH_WINDOW Solo refresca si la tab ya está cerca de expirar.
  • Cooldown SESSION_REFRESH_COOLDOWN Evita que se sume tiempo en requests demasiado seguidas.

Ejemplo: si renovó a las 12:09:35 y se vuelve a pedir a las 12:09:36 con SESSION_REFRESH_COOLDOWN=60, es normal que no sume más tiempo.

Ver: renovación en Gateway, contador en Surface y hooks de sesión HTTP.

No carga manifest Vite

En local debe ejecutarse npm run lite:build en app-surface y validarse PUBLIC_PATH. En producción debe usarse npm run build; el manifest es obligatorio.

Ver: Vite y estilos, helpers de assets Gateway y contrato de assets.

Falta una entrada del manifest

Si el manifest existe pero no contiene el entry esperado, deben revisarse vite.config.ts, el nombre de entrada y el build de Surface. En producción no debe haber fallback silencioso.

Ver: configuración Vite, orden de deploy y manifest Vite.

Sesión por pestaña falla

Validar ensureTabSession(), header X-TAB-SESSION y estado de sesión PHP.

Ver: sesión Gateway, sesión Surface y headers HTTP.

Refresh HTML pierde la tab activa

En una navegación HTML normal no viaja X-TAB-SESSION. Debe revisarse si Surface escribió la cookie técnica X-TAB-SESSION-NAV, si el evento pagehide o beforeunload pudo sincronizarla y si la URL heredada conserva un _tab que Surface debería limpiar.

Ver: navegación HTML y tab, tabs en Surface y headers.

Observabilidad y rastreo

Cuando un síntoma cruza varias capas, el correlation id permite reunir evidencia de una misma operación sin adivinar por hora, usuario o mensaje. Se toma desde la respuesta visible y se usa para localizar el recorrido correspondiente en Gateway y en llamadas upstream.

No se puede rastrear un fallo

Debe copiarse X-CORRELATION-ID desde la respuesta del navegador y usarse para ubicar logs de Gateway, response context y llamadas upstream relacionadas.

Ver: observabilidad Gateway, errores y referencia rápida.

No aparecen logs por request

Debe revisarse LOG_TELEMETRY_ENABLED. Si está en false, Gateway no inicia telemetría normal por request y tampoco recolecta spans upstream; los fallos de bootstrap pueden seguir registrándose por su carril temprano.

Ver: variables de logs, observabilidad Gateway y señales de diagnóstico.

Respuesta parcial o degradada

Si la response tiene data usable, pero hubo errores operativos de upstream, se debe buscar degraded_response y request_metrics. La UI puede continuar, pero el flujo no debe cerrarse como éxito limpio.

Ver: eventos de observabilidad, JSON envelope y partial reporter.
