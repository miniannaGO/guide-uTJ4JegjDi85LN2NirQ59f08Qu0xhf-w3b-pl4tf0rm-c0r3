App Surface

Comportamiento TypeScript que mejora el HTML ya entregado por Gateway sin sustituirlo. La página explica cómo iniciar una integración, montar páginas o regiones parciales de HTML llamadas fragments, llamar al servidor y liberar los recursos creados en el navegador.

Overview

app-surface agrega interacción a páginas que ya pueden mostrarse como HTML. No crea una aplicación paralela en el navegador ni reemplaza las decisiones de Gateway: activa botones, formularios, fragmentos y componentes visuales sobre una estructura existente.

Este enfoque se denomina Progressive Enhancement: monta comportamiento UI sobre HTML emitido por las views de app-gateway.

Los nombres de integraciones son didácticos y transferibles. Surface debe activar HTML y consumir contratos del Gateway; no debe absorber reglas de negocio de la Extension.

Panorama de Surface

Surface no crea pantallas desde cero. Parte del HTML que Gateway ya renderizó. Cuando encuentra una marca declarativa, carga el módulo correspondiente, monta comportamiento y limpia cuando ese HTML desaparece. La lectura del código de una feature Surface debe comenzar por integration.ts: allí se declara qué id SSR atiende la integración y qué módulo se carga después.

Esto significa que Surface no es “la aplicación completa en el navegador”. Es una capa de activación. Su trabajo es pequeño pero importante: encontrar el HTML correcto, conectar eventos, llamar rutas Gateway con serverClient, montar adapters visuales cuando hagan falta y desmontarlos sin dejar estado colgado. Cuando una explicación necesite reglas de negocio, permisos o proveedores externos, esta página solo los menciona como frontera y envía el detalle a Gateway o Bridge.

  • Declarar integration.ts → registry El id SSR y los loaders identifican qué comportamiento pertenece a la pantalla.
  • Activar runtime → UiBinding → cleanup El runtime descubre HTML; el binding controla DOM, eventos y adapters dentro de esa raíz.
  • Comunicar actions → api → serverClient → Gateway Surface consume contratos HTML o JSON y deja sesión, errores y URLs en infraestructura.

Orden sugerido dentro de esta página: workspace, startup, runtime, interfaz, bindings, infraestructura HTTP, consumo Gateway, capacidades de referencia, sesión runtime, content mount, toolkit, Vite y flujo completo.

Cómo funciona Surface

Surface no reemplaza al Gateway ni funciona como una SPA completa. Actúa como una capa progresiva de UI: detecta HTML existente, carga el módulo correspondiente y agrega comportamiento específico a páginas o fragments.

La regla práctica es simple: si el comportamiento pertenece a una página, fragment, helper técnico o Gateway, esa decisión define su ubicación y responsabilidad dentro del proyecto.

Zona Responsabilidad Ejemplos No debería tener
platform/startup Arranque global, layout actual, errores UI globales y assets por layout. startApplication(), resolveLayout(), mountLayout(). Reglas de una pantalla concreta.
platform/runtime Montaje/desmontaje de pages, fragments y bindings. mountPages(), FragmentRuntime, UiBinding. HTTP de una feature, permisos o negocio.
platform/infrastructure HTTP, sesión, config y errores técnicos de UI. serverClient, ensureTabSession(), AppConfig. Adapters visuales o lógica de pantalla.
toolkit Wrappers técnicos para DOM, feedback y librerías UI que se importan solo cuando se necesitan. Select2, DataTables, DateRangePicker, Bootstrap modal, Swal. Imports globales pesados o negocio de aplicación.
workspace Integraciones UI concretas del producto. feature/page.ts, actions.ts, api.ts, contracts.ts, fragments/*.ts. Reescribir runtime, sesión global o contratos HTTP.

Regla de oro

  • Los datos deben solicitarse al gateway mediante serverClient.
  • El HTML dinámico debe pedirse como fragment SSR.
  • Los plugins visuales deben montarse desde el binding que los usa.
  • Si algo debe limpiarse, se debe registrar su unmount.

Flujo para una pantalla nueva

  1. Gateway renderiza una view con data-surface-page.
  2. Surface registra una integración con el mismo id.
  3. La integración carga su page.ts de forma lazy.
  4. El binding escucha eventos y pide datos/HTML al gateway.
  5. Los fragments insertados se montan automáticamente.

Filesystem de Surface

El árbol de Surface ayuda a decidir dónde colocar un cambio de interfaz. Primero se debe reconocer si el código pertenece a una integración concreta, si es una ayuda técnica opcional o si sostiene el funcionamiento compartido de todas las páginas.

Con esa decisión, app-surface se organiza en tres zonas: platform para runtime e infraestructura UI, toolkit para helpers técnicos que se importan solo cuando se necesitan y workspace para integraciones concretas del producto. El entry único es main.ts y Vite publica el build hacia Gateway.

Convención Surface se escribe como Vite vanilla TypeScript.

  • Excepciones Assets de documentación, scripts legacy cargados por Gateway o casos puntuales.

Workspace integrations

Una integración reúne el comportamiento que pertenece a una zona concreta del HTML: cómo se reconoce, qué eventos escucha, qué datos solicita y qué fragmentos monta. Es el lugar normal donde el dev trabaja una experiencia de Surface.

@workspace/integrations contiene esas integraciones. Puede incluir actions.ts, api.ts, contracts.ts, controls.ts, fragments/, integration.ts, page.ts y request.ts, pero cada archivo se crea solo cuando existe esa responsabilidad.

Dos recorridos Dependencia de archivos y ejecución de UI no avanzan en el mismo sentido.
  • Entrada de lectura integration.ts Conecta el id SSR con loaders lazy y permite localizar la feature sin ejecutar comportamiento.
  • Dependencias contracts → api → actions → binding Los tipos sostienen el transporte; la action lo coordina y el binding lo consume desde el DOM.
  • Ejecución binding → actions → api → serverClient → Gateway El evento empieza en la pantalla y viaja hacia el endpoint antes de volver como data o HTML validado.
  • UI bajo demanda controls.ts Se agrega solo si la feature necesita montar y desmontar adapters visuales.

integrations/<feature>/integration.ts Declara id, layout, page.load y loaders de fragments. Side effects, queries DOM o llamadas HTTP.
integrations/<feature>/page.ts Binding principal para el root con data-surface-page. HTML de negocio, reglas que pertenecen a Gateway o payloads HTTP armados a mano si existe una acción.
integrations/<feature>/request.ts Builders o validaciones opcionales cuando el armado del request crece. Tipos base del contrato, reglas de negocio profundas o DTOs externos de PHP.
integrations/registry.ts Lista las integraciones disponibles para el runtime. Lógica de montaje, HTTP o reglas de feature.
workspace/styles CSS base, layouts, tokens y vendors. Estilos escondidos dentro de runtime o toolkit.

Startup y layouts

Al cargar una página, Surface necesita saber qué conjunto de comportamientos generales debe activar antes de buscar una integración concreta. Esa preparación inicial se denomina startup; el layout identifica el tipo general de página, por ejemplo acceso o control autenticado.

El arranque configura errores UI, respuestas parciales y comportamientos globales, y resuelve el layout desde body.id.

body.id Layout Qué monta
main-body-access access ensureTabSession() y pages de acceso.
main-body-control control Sesión, expiración, menú y pages autenticadas.

Base URL inyectada por SSR

Los layouts SSR deben declarar window.__BASE_URL__ antes de cargar el bundle Vite. Surface usa esa base para baseUrl(...), requests de serverClient, redirecciones de sesión y recursos públicos resueltos desde TypeScript compilado.

El layout control valida la base antes de montar su sesión y menú. Las pages de access también deben respetar el mismo contrato cuando hacen requests o construyen URLs; una integración no debe concatenar rutas físicas del Gateway ni depender de PUBLIC_PATH para llamar endpoints.

Qué ocurre en startApplication()

Startup prepara reglas globales de UI. No monta una feature por su cuenta; deja listo el terreno para que el runtime encuentre páginas y fragments declarados por el HTML SSR.

Paso Responsabilidad Detalle importante
configureUiErrorReporter(...) Define cómo se muestran errores UI globales. Hoy usa feedback con Swal desde startup.
setPartialReporter(...) Define cómo avisar respuestas parciales. Una parcialidad no bloquea data usable; se muestra como advertencia.
resolveLayout() Lee body.id y decide access/control. Si el body no coincide, startup falla claro.
loadLayoutAssets(...) Importa CSS del layout y muestra el documento. Evita cargar CSS de control en páginas de acceso.
pageshow Restaura layout si el navegador vuelve desde BFCache. Rehidrata estado sin volver a montar todo duplicado.
Carga visual inicial La página se muestra cuando termina de cargar el CSS de layout.
  • Entry main.ts Carga el CSS base.
  • Layout assets loadLayoutAssets(...) Importa CSS de access o control.
  • Visibilidad document.documentElement.style.visibility Pasa a visible al terminar la carga.
  • Optimización Mover CSS crítico al entry o al SSR sería un cambio de implementación.

Control layout

  • mountControlLayout() delega la UX de sesión en bootControlSession(), hidrata contexto, sincroniza menú y monta pages registradas.
  • MENU_LAYOUT controla si el menú intenta modo box o wide.
  • Si el navegador restaura una pestaña desde cache, se ejecuta restoreControlLayout() para refrescar sesión y menú.

Runtime de pages y fragments

El runtime es el mecanismo que descubre qué HTML necesita activación y coordina su montaje y limpieza. No navega por la aplicación ni crea páginas: observa marcas declaradas por el servidor y carga únicamente el comportamiento asociado.

Para hacerlo, busca atributos declarados por el HTML SSR. No hay routing cliente. La práctica para crear una raíz activable se desarrolla en Crear una página SSR.

HTML SSR 
<div data-surface-page="demo-items">
  <section data-surface-fragment="item-summary"></section>
</div>
Integración UI 
export const itemsIntegration = {
  id: "demo-items",
  layout: "control",
  page: { load: () => import("@/workspace/integrations/items/page") },
  fragments: {
    "item-summary": {
      load: () => import("@/workspace/integrations/items/fragments/summary"),
    },
  },
} satisfies UiIntegration;
  • data-surface-page apunta al registry global.
  • data-surface-fragment apunta al registry de fragments de su integración propietaria.
  • MutationObserver monta fragments agregados y desmonta fragments removidos.
  • Si un fragment necesita datos nuevos, el HTML se debe solicitar al gateway; la vista no se debe reconstruir desde un JSON externo.

Interfaz runtime

Esta interfaz define el acuerdo mínimo entre una integración y el mecanismo que la monta. La integración aporta un id y módulos activables; el runtime aporta el elemento raíz, el contexto y una forma de limpiar lo que se inicializó.

Se mantiene pequeña a propósito: no incluye router cliente, store global ni módulos autónomos. Solo expone integración UI, módulos montables, contexto de montaje y limpieza.

Pieza Qué significa Detalle importante
UiIntegration.id Valor que debe coincidir con data-surface-page. Si no coincide con el registry, el runtime lanza error.
layout access o control. Por defecto es control.
autoMount Permite desactivar montaje automático. Por defecto es true.
page.load Import lazy del módulo principal de la página. Debe exportar mount o clase UiBinding default.
fragments Mapa de loaders por data-surface-fragment. Solo aplica dentro de la integración propietaria.
MountContext Contexto que recibe page o fragment al montar. Incluye integrationId, registry de fragments y mountContent.
Formas válidas de módulo montable 
import { UiBinding } from "@/platform/runtime/binding";
import type { MountContext, Unmount } from "@/platform/runtime/contracts";
//Forma 1: función mount simple.
export function mount(root: HTMLElement, context: MountContext): Unmount {
  const button = root.querySelector("button");
  const listener = () => console.log(context.integrationId);
  button?.addEventListener("click", listener);

  return () => button?.removeEventListener("click", listener);
}
//Forma 2: clase con lifecycle y helpers DOM.
export default class ItemsPage extends UiBinding {
  protected mount(): void {
    this.onClick(this.require("#btn-search"), () => this.search());
  }

  private async search(): Promise<void> {
    // Acción UI de la página.
  }
}
  • El runtime marca nodos con data-surface-page-status y data-surface-fragment-status para evitar doble montaje.
  • El desmontaje corre deepest-first: primero se limpian hijos, luego padres.
  • MutationObserver observa fragments agregados o removidos dentro de la page montada.
  • context.mountContent(root) sirve para montar fragments dentro de HTML insertado manualmente por un binding.

Bindings y lifecycle

Un binding une comportamiento TypeScript con un elemento HTML concreto. Durante el montaje encuentra controles y registra eventos; durante el desmontaje retira listeners, adapters y recursos para que el mismo HTML pueda desaparecer o volver a montarse sin duplicaciones. Esa secuencia de vida se denomina lifecycle.

Un módulo montable puede exportar mount(root, context) o una clase UiBinding por defecto. UiBinding reúne helpers DOM y limpieza ordenada.

Si el binding monta librerías visuales, el contexto se amplía en Toolkit, adapters y feedback y en Montar un adapter UI.

UiBinding 
export default class ExampleBinding extends UiBinding {
  protected mount(): void {
    const button = this.find<HTMLButtonElement>("#btn-example");
    if (!button) return;

    this.onClick(button, async () => {
      // Acción UI protegida por guardUiAction.
    });
  }

  protected unmount(): void {
    // Destruye adapters o estado externo.
  }
}
  • Ubicar aquí eventos DOM, adapters visuales y coordinación de interacción.
  • Mantener las llamadas HTTP en api.ts para que el binding no mezcle DOM con transporte.
  • Los adapters que crean estado externo deben registrar su limpieza en unmount.
  • this.onClick(...) registra y retira el listener automáticamente. No se debe duplicar ese cleanup en unmount().
  • El desmontaje sigue beforeUnmount → unmount → cleanups automáticos → afterUnmount. Los cleanups automáticos se ejecutan en orden inverso.
  • Dentro de pages y fragments se prefiere this.onClick(...). guardClick(...) protege una acción global, pero no registra cleanup del binding.

Infraestructura HTTP

Las integraciones no deberían repetir cómo construir una URL, validar una respuesta, transportar la identidad de pestaña o convertir un fallo en un error visible. Surface concentra esas reglas en un solo cliente para que cada feature se limite a declarar qué necesita.

Toda llamada a endpoints de Gateway pasa por serverClient, que valida el JSON envelope o contratos HTML, sincroniza los headers de sesión y normaliza errores UI.

Método Cuándo usarlo Qué exige
serverClient.json(...) Cuando se necesita el envelope completo. success booleano.
serverClient.data(...) Cuando se necesita data obligatoria. data no nula.
serverClient.html(...) Cuando se necesita HTML SSR o fragment. HTML embebible, no JSON accidental ni layout completo.

X-TAB-SESSION identifica la pestaña activa. X-REMAINING sincroniza el contador de expiración.

Surface no inventa la sesión: solo transporta el id de pestaña y consume el tiempo restante que calcula Gateway. El estado autoritativo vive en sesión PHP; el estado de Surface es una copia operativa para saber qué header enviar y cuándo mostrar el modal.

Opciones de request

serverClient construye la URL usando AppConfig. Por eso la pantalla no debería concatenar BASE_URI, PUBLIC_PATH ni rutas internas del gateway. La pantalla debe declarar la intención: método, parámetros, body y tipo de respuesta esperada.

Caso Forma Qué genera
GET con query string { method: "GET", params: { q: "abc" } } Agrega ?q=abc y filtra valores nulos.
POST JSON { method: "POST", body: payload } Serializa JSON y agrega Content-Type: application/json.
FormData { method: "POST", body: formData, bodyType: "form-data" } Envía multipart sin setear Content-Type manual.
HTML fragment serverClient.html(route, options) Envía Accept de HTML, exige HTML embebible y puede validar el fragment esperado con expect.

Cómo se convierten errores en UI

  • Si no hay conexión con el servidor, se lanza FatalError.
  • Si el contrato JSON o HTML no coincide, se lanza HttpContractError.
  • HTTP 400, 409 o 422 se tratan como errores accionables por el usuario.
  • HTTP 401 o 403 se tratan como error de sesión.
  • Una respuesta parcial es success=true con errors.length > 0; startup decide cómo mostrar la advertencia.

Resultado de cada tipo de respuesta

Respuesta de Gateway Método Surface Qué ocurre en runtime Cómo debe reaccionar un binding
200 + envelope exitoso con data serverClient.data(...) Devuelve data tipada. Pinta estado nuevo y deja cleanup listo.
200 + envelope parcial serverClient.json/data Reporta advertencia con partialReporter. La data puede usarse, pero la advertencia no debe eliminarse ni convertirse en éxito silencioso.
4xx con envelope esperado serverClient.json/data/html Se transforma en UserActionError o SessionError. Muestra feedback o deja que startup/session lo maneje.
5xx con envelope esperado serverClient.json/data/html Se transforma en FatalError. No se debe reintentar sin una decisión explícita de UX.
HTML embebible válido serverClient.html(...) Devuelve string HTML; si se declaró expect, exige el data-surface-fragment esperado. Inserta y llama contentMount si el HTML trae fragments activos.
HTML vacío, JSON accidental, redirect, layout completo, page de Surface o content-type incompatible serverClient.html(...) Lanza HttpContractError. Se debe corregir Gateway o la ruta llamada; el HTML no se debe parchear en frontend.
Sin conexión o fetch rechazado Cualquier método Lanza FatalError de conexión. Muestra estado de fallo y conserva la UI previa si aplica.
Mensajes flash Son parte del render SSR, no del cliente HTTP de Surface.
  • No viajan por serverClient / envelope / headers Gateway los consume antes de entregar HTML.
  • Surface data-surface-<element> Solo monta el HTML resultante si la vista lo declara.

Consumir endpoints del gateway

Cuando una interacción necesita datos nuevos, Surface pide una capacidad a Gateway y trabaja únicamente con la respuesta visible. No necesita saber si detrás existe una base de datos, un service o un proveedor remoto.

Por esa frontera, Surface no consume APIs HTTP externas directamente. Gateway expone un endpoint JSON o un fragment HTML y Surface lo consume con serverClient.

Para diseñar el endpoint del lado Gateway, se deben consultar Controllers, Use cases y Crear un endpoint JSON.

Consumo seguro Surface solo ve el contrato del Gateway.

Esta frontera evita que el navegador reciba secretos, direcciones de proveedores o errores propios del transporte externo. La integración conoce la ruta interna y la forma de la respuesta que necesita para presentar la UI.

  • Vive en Gateway API key / bearer / base URL / errores externos El navegador no debe cargar credenciales ni URLs de proveedor.
  • Vive en Surface ruta / request local / response esperada Solo el contrato visible para pintar la interfaz.
Cadena de archivos El consumo del Gateway se lee como continuidad: contrato, llamada, acción y DOM.

Los archivos de una integración no compiten entre sí. Cada uno toma una decisión más concreta que el anterior: contracts.ts nombra la forma visible, api.ts llama al Gateway, actions.ts arma la intención UI y page.ts conecta esa intención con el DOM.

  • Contrato contracts.ts Define nombres TypeScript para request y response visibles desde Surface.
  • HTTP api.ts Usa el cliente HTTP de plataforma, ruta Gateway, método y validación de envelope o fragment.
  • Acción actions.ts Convierte valores semánticos de UI en request tipado y coordina una o más llamadas.
  • Binding page.ts / fragments/*.ts Lee el DOM, escucha eventos, pinta resultados y limpia recursos al desmontar.

1. Declarar contracts.ts

Las firmas TypeScript de entrada y salida viven junto a la integración que las consume. Nombran el contrato de Gateway que ve Surface, aunque el shape coincida con un DTO externo porque Gateway hizo passthrough.

La continuidad empieza aquí porque todavía no se ejecuta ninguna llamada. Solo se fija el vocabulario que usarán las piezas siguientes. Si un endpoint cambia de payload, esta es la primera señal que debe revisarse antes de tocar DOM o adapters.

2. Crear un api.ts por integración

api.ts funciona como la puerta HTTP de una integración. Centralizar allí las llamadas permite cambiar una ruta, un método o un tipo sin buscar detalles de red entre selectores y eventos DOM.

El archivo conoce rutas Gateway, método HTTP y tipos importados desde contracts.ts; no conoce DOM ni feedback visual. Si la ruta todavía no existe, los comandos make:integration-api-data, make:integration-api-json y make:integration-api-html crean el esqueleto coordinado entre api.ts, controller y routing.

En el siguiente bloque se ven dos salidas distintas del mismo puente: una función devuelve data tipada para pintar información y otra devuelve HTML validado como fragment embebible. Ambas usan rutas Gateway; ninguna conoce proveedores externos ni secretos.

@workspace/integrations/items/api.ts 
import type { ItemSearchResponse, SearchItemsRequest } from "./contracts";
    
import { serverClient } from "@/platform/infrastructure/http";

export async function searchItems(request: SearchItemsRequest): Promise<ItemSearchResponse> {
  return await serverClient.data<ItemSearchResponse, SearchItemsRequest>("/items/search", {
    method: "POST",
    body: request,
  });
}

export async function fetchItemSummaryHtml(itemId: number): Promise<string> {
  return await serverClient.html("/items/summary", {
    method: "GET",
    params: { itemId },
    expect: { kind: "fragment", fragmentId: "item-summary" },
  });
}

A partir de aquí, page.ts no vuelve a construir la URL ni a interpretar el envelope. Solo llama una función con nombre de intención y recibe datos o HTML ya mediados por la infraestructura HTTP.

3. Coordinar desde actions.ts

actions.ts expresa lo que la interfaz intenta hacer sin depender de dónde se leyó cada valor. Recibe datos comprensibles para la UI, prepara la petición y devuelve un resultado cómodo para presentar.

Cuando necesita armar un payload, crea el request tipado desde valores semánticos. page.ts lee el DOM y llama esa acción; solo importa contracts.ts si necesita anotar o leer directamente la data.

Esta capa intermedia evita que el binding mezcle selectores, transformación de payload y varias llamadas HTTP en el mismo método. La función de acción recibe valores ya leídos por la UI y devuelve una respuesta cómoda para pintar.

actions.ts armando request 
import { SearchItemsRequest, type ItemSearchResponse } from "./contracts";
import { searchItems } from "./api";

export async function runItemSearch(query: string, status: string): Promise<ItemSearchResponse> {
  const request = new SearchItemsRequest({ query, status });

  return await searchItems(request);
}

Después, page.ts queda cerca del DOM: escucha el evento, extrae valores, llama la acción y actualiza la zona correspondiente. En el recorrido completo recibe data tipada; no interpreta el envelope ni reconstruye el payload HTTP.

page.ts llamando actions.ts 
import { UiBinding } from "@/platform/runtime/binding";
import { runItemSearch } from "./actions";

export default class ItemsPage extends UiBinding {
  protected mount(): void {
    const searchButton = this.require<HTMLButtonElement>("#btn-search-items");

    this.onClick(searchButton, () => this.search());
  }

  private async search(): Promise<void> {
    const query = this.require<HTMLInputElement>("#item-query").value.trim();
    const status = this.require<HTMLSelectElement>("#item-status").value;
    const result = await runItemSearch(query, status);

    this.require("#item-count").textContent = String(result.items.length);
  }
}

Un recorrido JSON termina con una actualización del DOM a partir de result.items. Si otra interacción necesita HTML embebible, puede usar fetchItemSummaryHtml(...) como carril adicional: en ese caso Surface inserta el HTML renderizado por Gateway y monta cualquier data-surface-fragment declarado.

4. Selección del método correcto

La elección depende de qué necesita la UI después de la llamada: solo los datos, el envelope completo para interpretar mensajes y errores, o HTML listo para insertar. Se debe elegir el método más específico que conserve la información necesaria sin obligar a la integración a validar el contrato de nuevo.

Necesidad UI Método Resultado
Datos tipados para pintar una tabla o contador. serverClient.data<T>(...) Devuelve data y falla si no existe.
Envelope completo para leer message, errors o code. serverClient.json<T>(...) Devuelve ApiResponse<T>.
Fragment SSR listo para insertar en el DOM. serverClient.html(...) Devuelve HTML embebible y rechaza JSON, redirects, layouts o pages.
Subida de archivos o formulario multipart. bodyType: "form-data" Envía FormData sin forzar Content-Type manual.

  • No deben construirse URLs con BASE_URI manualmente; serverClient ya usa la configuración de la aplicación.
  • En GET se usa params; en POST, PUT y DELETE, se usa body.
  • No deben enviarse tokens externos desde Surface. Debe existir un endpoint del gateway que represente la intención de UI.
  • Cuando se requiera HTML, debe consumirse un fragment SSR con serverClient.html(...).
  • contracts.ts define las firmas visibles para Surface; api.ts las usa para tipar la llamada; actions.ts crea el request cuando la acción tiene intención propia.
  • page.ts debe mantenerse cerca del DOM: lee inputs, escucha eventos y llama acciones. La composición de negocio sigue en Gateway.
Esqueleto progresivo Tres comandos agregan el puente API desde una integración existente.
  • Data make:integration-api-data Devuelve directamente data tipada desde Surface.
  • JSON make:integration-api-json Conserva el envelope completo del Gateway.
  • HTML make:integration-api-html Prepara consumo de fragmentos SSR embebibles.

Los tres crean api.ts si falta, agregan una función async lowerCamelCase, registran la ruta, crean o completan controller y dejan CustomResponse como marcador para reemplazar por tipos locales de contracts.ts.

Implementación guiada · Surface La misma implementación guiada continúa desde el contrato TS hasta el DOM.

La continuidad en Surface separa cuatro decisiones: nombrar la forma de los datos, realizar la llamada, expresar la acción de UI y actualizar el DOM. Ningún archivo necesita conocer la operación completa.

Gateway ya expuso la ruta de la implementación guiada POST /items/search y devuelve un ItemSearchOutput dentro del envelope JSON. Surface no replica el use case ni conoce connectors externos: declara la forma visible para el navegador, llama la ruta mediante serverClient.data(...), arma la intención UI y pinta el resultado.

  • Contrato visible contracts.ts Declara SearchItemsRequest e ItemSearchResponse.
  • HTTP api.ts Llama POST /items/search con serverClient.data(...).
  • Intención UI actions.ts Construye el request tipado desde valores semánticos.
  • DOM page.ts Lee controles, dispara la acción y muestra la data.

serverClient.data(...) no evita el envelope: internamente llama serverClient.json(...), valida el contrato, reporta respuestas parciales y recién después exige data utilizable.

Sesión runtime

Surface refleja el estado de sesión que Gateway controla. Su responsabilidad es mantener identificada la pestaña, mostrar el tiempo restante y reaccionar a renovación o cierre; no puede conceder permisos ni prolongar la sesión por decisión propia.

Para ello coordina el id de pestaña, lee contexto de sesión desde Gateway, sincroniza el tiempo restante y ejecuta acciones visibles como refrescar o cerrar sesión.

Piezas de sesión en Surface

Estas piezas se reparten el trabajo para que ninguna integración tenga que implementar sesión. Unas conservan la identidad local, otras sincronizan HTTP y otra controla la cuenta regresiva visible.

Pieza Qué hace Quién depende de ella
ensureTabSession() Crea o reutiliza un id de 32 caracteres desde sessionStorage. Access layout, control layout y hooks HTTP.
sessionContext Guarda contexto hidratado: tab, usuario y estado de sesión. Startup y llamadas HTTP que necesitan header de pestaña.
configureHttpSession(...) Conecta serverClient con tab id y X-REMAINING. requestResource(...).
SessionCountdown Cuenta segundos restantes y dispara warning/expired. El umbral visible sale de SESSION_EXPIRY_ALERT. Eventos de expiración; startup/control/session.ts decide modal y logout.
refreshSession() Pide al gateway extender la pestaña actual. Botón "mantener sesión".
logout() Cierra sesión en Gateway y redirige al acceso. Logout manual o expiración.

La relación crítica para Surface es SESSION_EXPIRY_ALERT <= SESSION_REFRESH_WINDOW. El aviso debe aparecer dentro del tramo donde Gateway ya acepta refresh. Si el aviso aparece antes, el modal puede pedir "mantener sesión" cuando el backend todavía responde sin mover expiresAtUnix. Si aparece demasiado tarde, el usuario tendrá poco margen para decidir y para que la request complete antes de expirar.

SESSION_EXPIRY_ALERT se incorpora al bundle de Surface mediante Vite. Al cambiar ese valor para el frontend, debe regenerarse el build de Surface para que el contador use el nuevo umbral visible. En cambio, SESSION_REFRESH_WINDOW y SESSION_REFRESH_COOLDOWN los decide Gateway en runtime al evaluar la request.

Tabs en el navegador

Cada pestaña necesita una identidad propia aunque comparta la cookie general del navegador. Surface conserva esa identidad en un almacenamiento aislado por pestaña y la envía a Gateway en cada petición relevante.

ensureTabSession() guarda el id bajo la clave X-TAB-SESSION en sessionStorage. Ese almacenamiento pertenece a la pestaña actual del navegador, por eso una navegación normal en una pestaña nueva obtiene su propio id. La cookie PHP puede ser la misma para todo el navegador, pero el header separa qué entrada de tabs debe usar Gateway.

Dato local Dónde está Para qué sirve
X-TAB-SESSION sessionStorage. Identifica la pestaña actual y se envía como header en requests a Gateway.
sessionContext.idTab Memoria del runtime de Surface. Permite que serverClient agregue el header sin que cada feature lo haga manualmente.
sessionContext Memoria hidratada desde Gateway. Expone datos de usuario útiles para UI, pero no reemplaza validación ni permisos del backend.
SessionCountdown Runtime de sesión de Surface. Cuenta localmente desde X-REMAINING y emite warning al llegar a SESSION_EXPIRY_ALERT.

Navegación HTML y cookie técnica

ensureTabSession() sincroniza varias señales porque no todas las navegaciones pasan por fetch. El id de pestaña vive primero en sessionStorage; las demás señales solo ayudan a transportarlo hacia Gateway según el tipo de request.

Señal Dónde se escribe Regla
X-TAB-SESSION sessionStorage y header HTTP. Si ya existe un id válido en sessionStorage, ese valor tiene prioridad sobre el id que venga en HTML SSR.
input[name="_tab"] DOM SSR o formulario. Se actualiza con la tab real para formularios tradicionales, pero no debe llevarse a la URL.
X-TAB-SESSION-NAV Cookie del navegador en layout control. Dura 300 segundos, usa el path de baseUrl(), SameSite=Lax y agrega Secure cuando la página usa HTTPS.
pagehide / beforeunload Eventos del navegador. Reescriben la cookie técnica antes de salir o recargar, para que una navegación HTML mantenga la tab activa.
_tab en query string URL heredada. Surface intenta quitarlo con history.replaceState(...). El id vigente queda en storage, header, input y cookie técnica.

Qué pasa con X-REMAINING

Este header transporta una medición calculada por Gateway: los segundos que le quedan al contexto de la pestaña. Surface no los incrementa por su cuenta; actualiza su contador con el valor recibido y reacciona cuando alcanza los umbrales visibles.

  1. Gateway emite el header en la respuesta.
  2. serverClient lo lee después de cada fetch.
  3. sessionCountdown.sync(...) ajusta el contador local.
  4. Cuando faltan los segundos definidos por SESSION_EXPIRY_ALERT, el contador emite warning.
  5. startup/control/session.ts recibe warning/expired, abre el modal o ejecuta logout y vuelve al acceso.

Variables que afectan el runtime

Estas variables responden preguntas distintas: cuánto dura la sesión, cuándo puede renovarse, cuánto debe esperarse entre renovaciones y cuándo se avisa al usuario. Surface observa el efecto de todas, pero solo consume directamente el umbral del aviso.

SESSION_EXPIRY_ALERT es la única variable de este grupo que Surface usa directamente. Las demás viven en Gateway, pero condicionan si el botón "mantener sesión" puede extender o no la tab actual.

Variable Efecto visible en Surface
SESSION_TIME Define el máximo inicial que llegará en X-REMAINING después de login o refresh.
SESSION_REFRESH_WINDOW El modal debe aparecer dentro de esta ventana para que "mantener sesión" pueda extender en Gateway.
SESSION_REFRESH_COOLDOWN Evita refreshes seguidos para la misma tab. Si Gateway renovó a las 12:09:35 y el usuario vuelve a pulsar a las 12:09:36, la request puede responder bien, pero la expiración no se mueve otra vez.
SESSION_EXPIRY_ALERT Define cuándo Surface emite warning; si no existe, Vite usa SESSION_REFRESH_WINDOW como fallback.

Qué ve Surface cuando hay cooldown

El cooldown es el tiempo mínimo entre dos renovaciones reales. Aunque el usuario vuelva a pulsar el botón, Surface debe aceptar el tiempo que Gateway responda y no asumir que cada interacción agrega una duración completa.

Surface no decide si una sesión se puede renovar. Cuando el usuario pulsa "mantener sesión", refreshSession() llama a /auth/refresh-session. Gateway valida la tab, aplica SESSION_REFRESH_WINDOW y SESSION_REFRESH_COOLDOWN, y responde con X-REMAINING.

Ejemplo: si la tab vencía a las 12:10:00 y Gateway aceptó el refresh a las 12:09:35, la nueva expiración queda cerca de 12:19:35. En ese caso X-REMAINING vuelve a un valor cercano a SESSION_TIME en segundos. Si el usuario pulsa otra vez a las 12:09:36, todavía no pasó el cooldown; la respuesta puede ser correcta, pero X-REMAINING conserva el vencimiento ya calculado. Por eso el contador de Surface se sincroniza con el header y no asume que todo click suma tiempo.

Regla de frontera Una integración puede reaccionar, pero no implementar sesión.
  • Workspace workspace Puede mostrar errores o reaccionar a estado de sesión.
  • Infraestructura platform/infrastructure/session Con startup administra la sesión real de Surface.

Content mount, modales y toasts

A veces el HTML nuevo no se coloca dentro de la raíz original de la página, sino en una superficie temporal como un modal o un toast. Insertarlo no basta: si contiene fragments, también debe entrar al ciclo normal de montaje y limpieza.

En esos casos Surface inserta HTML fuera del root de la página: por ejemplo dentro de un modal o toast. Ese HTML también puede traer data-surface-fragment. Para conservar el lifecycle, el runtime expone context.mountContent(root).

Regla base: si el HTML vino del gateway, sigue siendo SSR. Surface lo inserta, solicita al runtime el montaje de sus fragments y conserva una función de limpieza para desmontarlo cuando el modal o toast desaparece.

Modal con HTML remoto

    const button = this.find<HTMLButtonElement>("#btn-open-summary");

      await this.modal.showRemote("/items/summary", {
        method: "GET",
        params: { itemId: 3021 },
        expect: { kind: "fragment", fragmentId: "item-summary" },

  }

  • Usar contentMount cuando se inserte HTML SSR fuera del root normal de la página.
  • El modal no debe convertirse en router ni en mini aplicación. Solo muestra HTML y delega fragments al runtime.
  • Si el contenido remoto no trae fragments, igual puede usarse; en ese caso no habrá bindings que montar.

Vite, styles y assets

El navegador no ejecuta directamente la estructura de trabajo de Surface. Primero, Vite transforma TypeScript, estilos y módulos en archivos publicables; después, Gateway consulta el manifest generado para incluir las rutas correctas en el HTML.

La compilación parte de app-surface/main.ts y escribe en app-gateway/{PUBLIC_PATH}/ui-assets. Gateway resuelve el manifest con vite_styles() y vite_script().

TS a build Vite Surface se edita en TypeScript y se publica como assets de navegador.

El código fuente se trabaja en app-surface: main.ts es el entry y las integraciones usan archivos como integration.ts, page.ts, actions.ts, api.ts, contracts.ts o fragments/*.ts. Vite transforma esa fuente en archivos de navegador, CSS y manifest dentro de app-gateway/{PUBLIC_PATH}/ui-assets.

  • Fuente app-surface/**/*.ts Es lo que se edita en Surface. El trabajo normal vive en TypeScript de startup, infraestructura, toolkit, workspace e integraciones.
    main.ts integration.ts page.ts actions.ts api.ts contracts.ts fragments/*.ts
  • Build tsc && vite build Valida tipos y emite artefactos de navegador. Los archivos emitidos son resultado del build, no fuente normal de trabajo.
    tsc vite build assets/[name]-[hash].js CSS manifest.json
  • Gateway vite_styles() / vite_script() Lee el manifest y publica los assets emitidos. Extension declara HTML SSR y atributos Surface; no compila TypeScript.
    vite_styles() vite_script() data-surface-page data-surface-fragment Extension

Si el asset no carga, deben revisarse Assets Vite, Archivo .env, qué instala Surface y Ayuda.

Env de Vite y runtime inyectado

Vite inyecta __APP_ENV__ en build time para que Surface conozca preferencias de UI y datos públicos de build sin leer archivos del Gateway. Las llamadas HTTP no se arman desde BASE_URI ni PUBLIC_PATH; usan window.__BASE_URL__, que Gateway declara en el SSR.

Variable Uso en Surface Regla
BASE_URI Participa en la base pública de assets generados por Vite y queda disponible en __APP_ENV__. No usarlo manualmente para requests HTTP de una feature.
PUBLIC_PATH Define el segmento donde Vite publica ui-assets dentro del gateway. No usarlo para construir URLs HTTP de serverClient.
MENU_LAYOUT Controla layout de menú en startup. Debe afectar layout, no reglas de negocio.
IS_PRODUCTION Permite ajustar comportamiento de build/runtime. No se debe usar para ocultar errores funcionales.
SESSION_EXPIRY_ALERT Define cuándo el contador emite warning de expiración. Debe estar alineado con la ventana de refresh del backend. Si no existe, Vite usa SESSION_REFRESH_WINDOW como fallback.
SPEED_UP_BUILD No es runtime env. Solo cambia opciones internas de Vite. Puede estar en .env, pero no llega al navegador como configuración de aplicación.
  • Los estilos globales y de layout viven bajo workspace/styles.
  • Los CSS de layout se cargan de forma lazy desde startup.
  • Las integraciones concretas deben importar solo lo que usan.
  • Los sourcemaps están pensados para desarrollo, no para producción.

Flujo completo de Surface

Surface arranca después de recibir HTML SSR nacido en las views de Gateway. Su flujo normal es descubrir atributos declarativos definidos por los contratos HTML, cargar módulos UI bajo demanda, montar bindings y comunicarse solo con gateway cuando necesita datos o HTML nuevo.

La lectura del código Surface comienza en integration.ts, continúa por page.ts o fragments y desciende a actions.ts, api.ts y contracts.ts cuando la UI necesita hablar con Gateway. La implementación guiada de este mapa se explica con detalle en implementación guiada.

  1. Precondición Gateway

    HTML recibido

    @views/items/index.page.php

    Gateway deja marcas declarativas. Surface no adivina qué página es: lee data-surface-page y trabaja sobre el HTML existente. 

    <div data-surface-page="demo-items">
  <section data-item-summary></section>
</div>
    Ayuda de Robo composer robo -- make:integration-page items --id=demo-items --layout=control

    Entrega a: el registry de Surface que conoce la integración demo-items.

  2. Registro UI

    Integración

    @workspace/integrations/items/integration.ts

    Aquí se conecta el id SSR con sus módulos lazy: page y fragments. No se escriben eventos DOM ni llamadas HTTP largas en este archivo. 

    id: "demo-items",
layout: "control",
page: { load: () => import("./page") }
    Ayuda de Robo composer robo -- make:integration-page items --id=demo-items --layout=control

    Entrega a: page.ts y a los fragment bindings registrados.

  3. Interacción

    Page binding

    @workspace/integrations/items/page.ts

    Aquí se coordinan nodos DOM, eventos y render de respuestas. La intención de negocio sigue en Gateway; este archivo solo activa la experiencia y llama acciones. 

    form.addEventListener("submit", async (event) => {
  event.preventDefault();
  const result = await runItemSearch(readQuery(form), readStatus(form));
  target.textContent = String(result.items.length);
});
    Ayuda de Robo composer robo -- make:integration-page items --id=demo-items --layout=control

    Entrega a: actions.ts, con valores semánticos leídos desde el DOM.

  4. Intención UI

    Actions

    @workspace/integrations/items/actions.ts

    Aquí se arma el request tipado desde valores semánticos que llegan del binding y se coordina la llamada a api.ts con feedback visual. 

    const request = new SearchItemsRequest({ query, status });
return await searchItems(request);

    Entrega a: api.ts, sin exponer detalles del payload HTTP al DOM.

  5. Comunicación

    API de la integración

    @workspace/integrations/items/contracts.ts @workspace/integrations/items/api.ts

    Las firmas visibles para Surface viven en contracts.ts. Las llamadas a Gateway viven en api.ts para que el DOM no quede mezclado con URLs, métodos HTTP o parsing de respuestas. 

    return serverClient.data<ItemSearchResponse, SearchItemsRequest>("/items/search", {
  method: "POST",
  body: request,
});
    Ayuda de Robo composer robo -- make:integration-api-data items searchItems post /items/search --controller-name=Item composer robo -- surface:contract items SearchItemsRequest ItemSearchResponse <swaggerPath>

    Entrega a: serverClient, que valida el envelope y exige data utilizable.

  6. Contrato mediado

    HTTP de plataforma

    @platform/infrastructure/http/client.ts

    serverClient.data(...) reutiliza la validación de serverClient.json(...), reporta parcialidad y retorna la propiedad data. Si no existe data utilizable, corta el flujo antes de que el binding pinte la UI. 

    const apiResponse = await requestJson<TResult, TRequest>(route, options);

if (apiResponse.data === undefined || apiResponse.data === null)
  throw new FatalError("Respuesta inválida del servidor");

return apiResponse.data;
    Contrato relacionado Envelope de SearchItems

    Retorna a: actions.ts y luego al binding con un ItemSearchResponse utilizable.

  7. Actualización visual

    DOM de la página

    @workspace/integrations/items/page.ts

    El binding recibe data tipada y actualiza la interfaz. No decide reglas de aplicación ni vuelve a interpretar el envelope. Fragments, modales y adapters siguen disponibles como carriles opt-in cuando otra interacción realmente los necesita. 

    const result = await runItemSearch(query, status);
this.require("#item-count").textContent = String(result.items.length);

    Resultado: la pantalla conserva SSR inicial y agrega comportamiento TypeScript progresivo.
