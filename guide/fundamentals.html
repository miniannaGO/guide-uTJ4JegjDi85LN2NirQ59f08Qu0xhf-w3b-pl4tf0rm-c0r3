Vocabulario

Antes de leer Gateway, Surface o Bridge, conviene fijar estos términos. La guía los repite con frecuencia porque son los contratos conceptuales de la solución. Cuando un término aparezca más adelante, este glosario funciona como referencia base.

Modelo del proyecto

El proyecto se divide para que cada decisión tenga un lugar reconocible. Un lado recibe peticiones, aplica decisiones de aplicación y prepara respuestas; el otro toma el HTML ya entregado y agrega interacción en el navegador. La regla más importante es no resolver dos veces la misma responsabilidad.

Para un primer acercamiento, se debe leer como una conversación: Gateway recibe una petición, decide qué significa para la aplicación y responde con HTML, JSON o un error controlado. Surface llega después: toma ese HTML ya renderizado y le suma interacción. Según el reparto de responsabilidades, si algo exige decidir permisos, consultar una API externa o interpretar reglas de aplicación, pertenece a Gateway. Si algo escucha clicks, monta un plugin visual o actualiza un fragment ya recibido, pertenece a Surface.

Modelo operativo

Cada nodo conserva una frontera distinta: Core entrega mecanismos compartidos, Extension expresa la aplicación y Surface activa la experiencia sobre el HTML SSR.

  1. Core

    Motor compartido

    Bootstrap, DI, HTTP, routing, middleware, responses, view, errores, outbound y composición de use cases.

    Mecanismos transversales
  2. Extension

    Aplicación concreta

    Features reales: controllers, use cases, services, connectors, views, sesión y routing de la aplicación.

    Intención de aplicación
  3. Surface

    Mejora progresiva

    Activa comportamiento UI sobre HTML SSR. No es SPA, no decide negocio y no duplica permisos.

    SSR + TypeScript

Contextos y límites

Un contexto agrupa código que responde al mismo tipo de responsabilidad. El límite indica hasta dónde puede decidir ese grupo antes de entregar el trabajo al siguiente. Reconocerlos evita colocar reglas de aplicación dentro de infraestructura o decisiones del servidor dentro del navegador.

En los nombres del proyecto, Gateway se divide entre Core, que aporta mecanismos compartidos, y Extension, que los usa para expresar la aplicación. Surface separa la plataforma común, las integraciones UI concretas y los helpers opcionales.

app-gateway

Gateway

El backend separa los mecanismos compartidos de Core de la intención concreta que Extension expresa para la aplicación.

  1. app-gateway/Core Core
    Transversal

    Define mecanismos transversales reutilizables.

    No contiene lógica concreta de una feature.

  2. app-gateway/Extension Extension
    Aplicación

    Declara rutas, controllers, use cases, services, connectors y views.

    No crea otro mini-framework paralelo ni usa clases Internal de Core.

app-surface

Surface

El frontend progresivo separa infraestructura de plataforma, integraciones UI concretas y herramientas técnicas opt-in.

  1. app-surface/platform Platform
    Infraestructura

    Arranca layouts y coordina runtime, HTTP y errores UI.

    No resuelve reglas de negocio ni permisos.

  2. app-surface/workspace Workspace
    Integración UI

    Define integraciones UI concretas.

    No duplica reglas de negocio que pertenecen a Gateway.

  3. app-surface/toolkit Toolkit
    Opt-in

    Ofrece adapters y helpers técnicos que se importan solo cuando se necesitan.

    No carga vendors globales sin necesidad.

Para llevar estos límites al flujo real, se recomienda revisar SSR + Progressive Enhancement y Runtime de pages y fragments.

Cómo leer cambios

La lectura debe concentrarse en los archivos correctos. Esta regla ayuda a delimitar el análisis antes de modificar código:

Esto evita dos errores típicos al empezar: buscar lógica de negocio dentro de un binding de Surface, o buscar problemas de montaje dentro de un use case de Gateway. El orden de lectura no siempre es el orden físico de carpetas; es el orden en que la responsabilidad viaja por la solución.

Flujo completo

El flujo debe leerse como una cadena de responsabilidades: Gateway recibe, decide y responde; Surface solo activa lo que el HTML declara.

Para reconocer dónde intervenir, se debe seguir el dato y preguntar quién lo transforma en cada paso. La entrada todavía es HTTP; el routing elige un destino; la aplicación decide el resultado; la respuesta lo convierte en HTML o JSON; y Surface agrega comportamiento únicamente cuando el navegador ya tiene una estructura válida.

  1. HTTP

    Entrada HTTP

    El Core de gateway recibe el request y prepara el runtime inicial.

    Cliente public/index.php BootstrapRunner ContainerFactory
  2. CORE

    Kernel y routing

    El kernel arma el ciclo HTTP y encuentra el action correcto.

    Kernel RequestLifecycle RequestBootstrapPipeline RouteDispatcher MiddlewarePipeline
  3. APP

    Aplicación

    La intención se resuelve en Extension, usando Core como contrato.

    Controller UseCase Service si compone Connector si integra
  4. OUT

    Salida

    Gateway emite un contrato consumible: HTML SSR o envelope JSON.

    Response HTML o JSON ResponseEmitter Browser
  5. UI

    Surface

    Monta comportamiento sobre el HTML recibido.

    app-surface/main.ts startApplication mountPages FragmentRuntime

El mismo flujo se desarma por contrato en Contratos HTML, JSON envelope y Consumir endpoints del gateway.
