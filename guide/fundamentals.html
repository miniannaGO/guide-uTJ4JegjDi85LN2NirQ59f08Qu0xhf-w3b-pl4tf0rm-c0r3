Vocabulario mínimo

Antes de leer Gateway, Surface o Bridge, conviene fijar estos términos. La guía los repite con frecuencia porque son los contratos conceptuales de la solución. Cuando un término aparezca más adelante, esta tabla funciona como referencia base.

Término Qué significa aquí Dónde se profundiza
Gateway Backend PHP que recibe HTTP, ejecuta intención de aplicación y entrega HTML, JSON, redirects, headers o errores. Gateway
Surface Frontend TypeScript que activa comportamiento sobre HTML SSR. No es SPA y no decide negocio. Surface
Bridge Conjunto de contratos entre Gateway y Surface: HTML, data-surface-*, envelope JSON, headers, sesión y assets. Bridge
Core Mini-framework interno de Gateway: routing, HTTP, views, resultados, errores, outbound, DI y lifecycle. Core / Extension
Extension Aplicación concreta que consume Core: routes, controllers, use cases, services, ports, connectors y views. Capacidades Gateway
Use case Intención de aplicación. Decide si algo termina en éxito, parcialidad o fallo, sin conocer HTML ni transporte externo. Use cases
Service Composición opcional dentro de Extension. Solo existe si coordina varias fuentes, fallback o transformación real. Services y connectors
Connector Adaptador hacia una dependencia externa. Devuelve ConnectorResult, no HTML ni JSON final. Outbound
Envelope JSON Forma estándar de las respuestas JSON: success, data, message, errors y errorMeta. JSON envelope
Page View SSR navegable. Si trae data-surface-page, Surface puede activar un binding. Contratos HTML
Fragment HTML parcial que Gateway renderiza y Surface puede pedir, insertar y montar. Content mount
Binding Clase o función de Surface que escucha eventos, llama Gateway, inicializa adapters y registra cleanup. Bindings

Ruta recomendada después de esta tabla: Modelo mental, Gateway, Surface y Bridge.

Modelo mental

El proyecto tiene un Gateway framework-like controlado y un Surface (Frontend) progresivo. La regla más importante es no mezclar responsabilidades.

Para revisar esas responsabilidades con más detalle, la lectura continúa en App Gateway, App Surface y Ownership rápido.

Core

Motor compartido

Bootstrap, DI, HTTP, routing, middleware, responses, view, errores, outbound y use case composition.

Extension

Aplicación concreta

Features reales: controllers, use cases, services, connectors, views, sesión y routing de la app.

Surface

Mejora progresiva

Activa comportamiento UI sobre HTML SSR. No es SPA, no decide negocio, no duplica permisos.

Contextos y límites

Área Puede hacer No debería hacer
app-gateway/Core Definir mecanismos transversales reutilizables. Contener lógica concreta de una feature.
app-gateway/Extension Declarar rutas, controllers, use cases, services, connectors y views. Crear otro mini-framework paralelo o usar clases `Internal` de Core.
app-surface/platform Arrancar layouts, montar runtime, HTTP y errores UI. Resolver reglas de negocio o de permisos.
app-surface/workspace Definir integraciones UI concretas. Convertirse en dominio Surface soberano.
app-surface/toolkit Ofrecer adapters y helpers técnicos opt-in. Cargar vendors globales sin necesidad.

Para llevar estos límites al flujo real, se recomienda revisar SSR + Progressive Enhancement y Runtime de pages y fragments.

Flujo completo

El flujo debe leerse como una cadena de responsabilidades: Gateway recibe, decide y responde; Surface solo activa lo que el HTML declara.

01

Entrada HTTP

El gateway recibe el request y prepara el runtime inicial.

  • Cliente
  • public/index.php
  • BootstrapRunner
  • ContainerFactory
02

Kernel y routing

El kernel arma el ciclo HTTP y encuentra el action correcto.

  • Kernel
  • RequestLifecycle
  • RequestBootstrapPipeline
  • RouteDispatcher
  • MiddlewarePipeline
03

Aplicación

La intención se resuelve en `Extension`, usando Core como contrato.

  • Controller
  • UseCase
  • Service si compone
  • Connector si integra
04

Salida

Gateway emite un contrato consumible: HTML SSR o envelope JSON.

  • Response HTML o JSON
  • ResponseEmitter
  • Browser
05

Surface

Monta comportamiento sobre el HTML recibido.

  • app-surface/main.ts
  • startApplication
  • mountPages
  • FragmentRuntime

El mismo recorrido se desarma por contrato en Contratos HTML, JSON envelope y Consumir endpoints del gateway.

Ownership de contratos

Gateway

Decide contrato y estado

  • Estado de aplicación y permisos.
  • HTML SSR, JSON, redirect y errores.
  • Layouts, fragments y `data-surface-*`.
  • Headers de sesión y assets Vite.
Contrato compartido HTML SSR + envelope JSON + headers + manifest Vite
Surface

Activa interacción y feedback

  • Listeners, adapters y feedback UI.
  • Pages y fragments declarados por HTML.
  • HTTP hacia gateway con `serverClient`.
  • Firmas TS locales en `contracts.ts` por integración.
  • Montaje/desmontaje limpio del DOM.

Cada contrato se desarrolla con ejemplos en Contratos HTML, JSON envelope y Assets Vite.

Cómo leer cambios

La lectura debe concentrarse en los archivos correctos. Esta regla ayuda a delimitar el análisis antes de modificar código:

Cuando este mapa deba convertirse en pasos concretos, las Guías prácticas y los diagramas sirven como validación cruzada.

Cambio SSR

  1. routing
  2. controller
  3. response/view
  4. plantilla PHP
  5. integración UI si aplica

Cambio JSON

  1. routing
  2. controller
  3. use case
  4. response JSON
  5. consumidor surface

Cambio runtime UI

  1. platform/runtime
  2. platform/startup
  3. registry
  4. integración concreta

Cambio assets

  1. app-surface/vite.config.ts
  2. main.ts/styles
  3. gateway ViteAssets/parciales
