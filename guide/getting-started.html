Empezar

Instala el proyecto, configura `.env`, compila assets y valida que el gateway y surface estén conversando.

Requisitos

Esta guía asume un entorno local de desarrollo. El proyecto actual usa PHP para `app-gateway` y TypeScript/Vite para `app-surface`.

Para entender el rol de cada contexto antes de instalar, consulta Contextos, App Gateway y App Surface.

PHP

PHP 8.2 o superior.

Composer

Instala dependencias de `app-gateway` y genera autoload.

npm

Instala dependencias y ejecuta Vite/TypeScript en `app-surface`.

Instalación

El repo remoto final todavía puede cambiar. Por ahora deja (URL_DEL_REPOSITORIO) como placeholder en la documentación interna de onboarding.

Clonar proyecto 
git clone <URL_DEL_REPOSITORIO> web-platform-core
    cd web-platform-core
Instalar Gateway y Surface 
cd app-gateway
    composer install
    
    cd app-surface
    npm install

Ejecución local

Hay dos piezas: compilar assets de surface y servir gateway. En desarrollo usa `lite:build` para mantener Vite recompilando los assets publicados. Ese script ejecuta vite build --watch; no corre tsc antes de cada build. Para una validación completa de TypeScript usa npm run build.

El detalle del build vive en Vite, styles y assets, y la forma en que gateway los resuelve está en Assets Vite.

Watch surface 
cd app-surface
    npm run lite:build

Archivo .env

El `.env` vive en la raíz de la solución. Se crea desde `.env.template`. Controla modo runtime, rutas base, sesión, assets y overrides outbound.

Si una variable afecta assets, outbound o sesión, amplía el contexto en Vite y assets, API HTTP clients externos y headers de sesión.

Crear .env 
copy .env.template .env
Variable Qué controla Cómo decidir el valor
Runtime general
IS_PRODUCTION
Opcional Default: false
Modo general del runtime. Valor recomendado localmente: `false`. En `true` reutiliza cache DI, exige release válido y oculta detalle técnico.
DEEP_DEPLOYED
Opcional Default: false
Detalle técnico de errores hacia cliente. Solo aplica con `IS_PRODUCTION=false`. Puede configurarse en `true` para depuración local.
VERSION_DEPLOY
Obligatoria en producción Default: 0
Versión de release para assets y cache endurecido. Debe usarse un entero tipo `20260101`. En producción debe ser mayor que `0`.
SPEED_UP_BUILD
Opcional Default: false
Optimización del build Surface. Solo la lee Vite. En `true` desactiva minify/treeshake para iterar más rápido; no llega al runtime PHP ni a __APP_ENV__.
Rutas públicas y assets

Obligatoria para surface Default: ""
Directorio base de la solución. Sin slash inicial ni final cuando se use subcarpeta.

Opcional Default: app-gateway
Segmento del gateway. Normalmente `app-gateway`.

Opcional Default: public
Carpeta pública de assets. Normalmente `public`.

MENU_LAYOUT

APIs outbound de HTTP client externo
API_<PREFIX>_URI
Condicional Default: services.json / vacío
URL base de un servicio outbound. Prioriza este valor sobre `services.json`. Es obligatoria solo cuando el servicio requerido no trae `uri` válida en `services.json`; para `admision`, el prefijo es `API_ADMISION_`.
API_<PREFIX>_BEARER
Opcional Default: services.json / ""
Token bearer para un servicio outbound. Debe configurarse solo cuando el servicio requiere autenticación por bearer.
API_<PREFIX>_TIMEOUT_SECONDS
Opcional Default: services.json / 30.0
Timeout total de una llamada outbound. Debe ser numérico y mayor que `0`.
API_<PREFIX>_CONNECT_TIMEOUT_SECONDS
Opcional Default: services.json / 10.0
Timeout de conexión hacia el servicio. Debe ser numérico y mayor que `0`.
API_<PREFIX>_VERIFY_TLS
Opcional Default: services.json / false
Validación TLS del cliente outbound. Debe ser `true` o `false`; en producción normalmente conviene dejarlo en `true` si el servicio tiene TLS válido.
Equivalencia services.json `services.json` declara la base; `.env` solo sobrescribe por entorno.

Gateway carga primero app-gateway/services.json. Dentro de ese archivo, cada entrada bajo clients es un cliente outbound nombrado. Ese nombre es importante: el provider lo pide al core y el core construye las variables de entorno con la forma API_<PREFIX>_*, usando el nombre del servicio en mayúsculas. Así que las variables equivalentes empiezan por API_<PREFIX>_.

Base actual en services.json 
{
      "clients": {
        "<prefix>": {
          "uri": "https://ip:port"
        }
      }
    }
Variables equivalentes en .env 
API_<PREFIX>_URI="https://ip:port"
    API_<PREFIX>_BEARER=""
    API_<PREFIX>_TIMEOUT_SECONDS=30
    API_<PREFIX>_CONNECT_TIMEOUT_SECONDS=10
    API_<PREFIX>_VERIFY_TLS=false
Forma completa equivalente en services.json 
{
      "clients": {
        "<prefix>": {
          "uri": "https://ip:port",
          "bearer": "",
          "timeoutSeconds": 30,
          "connectTimeoutSeconds": 10,
          "verifyTls": false
        }
      }
    }
  • Base versionable services.json Guarda valores compartibles del cliente, como la URL local base o timeouts estándar.
  • Override de entorno .env Gana sobre `services.json` cuando la variable existe y no está vacía.
  • Texto vacío URI / BEARER Si la variable está vacía, el core conserva el valor leído desde `services.json`.
  • Validación fuerte TIMEOUT / TLS Los timeouts deben ser numéricos y mayores que `0`; TLS debe interpretarse como booleano.

Si ni `services.json` ni `.env` entregan una uri usable, Gateway falla claro al crear la definición del servicio. Los demás campos tienen defaults del core: bearer vacío, timeout total 30.0, timeout de conexión 10.0 y verifyTls=false.

Semanas completas de logs que se conservan. Debe ser mayor que 0; por defecto conserva la semana actual y las anteriores configuradas. También aplica a app-gateway/var/log/develop y app-gateway/var/log/production.

Sesión
SESSION_PATH
Opcional Default: sys_get_temp_dir()
Ruta física donde PHP guarda sesiones. Para usar el temporal de PHP, la variable debe eliminarse en vez de dejarse vacía.
SESSION_TIME
Opcional Default: 10
Minutos de sesión. Debe usarse un entero positivo. Gateway lo usa para calcular expiresAtUnix al crear o refrescar una tab. Surface no calcula este vencimiento: lo recibe en X-REMAINING.
SESSION_REFRESH_WINDOW
Opcional Default: 30
Ventana de refresh de sesión, en segundos. Gateway solo extiende la tab session cuando faltan esos segundos o menos para expirar. Conviene que el aviso de Surface ocurra dentro de esta ventana.
SESSION_EXPIRY_ALERT
Opcional Default: SESSION_REFRESH_WINDOW
Momento del warning de expiración que Surface convierte en modal. Vite lo expone en __APP_ENV__; debe ser menor o igual que SESSION_REFRESH_WINDOW. Si no se define, Surface usa la ventana de refresh como fallback.
SESSION_REFRESH_COOLDOWN
Opcional Default: 60
Enfriamiento entre refreshes, en segundos. Es un freno de escritura: Gateway solo lo mira después de comprobar que la tab está dentro de SESSION_REFRESH_WINDOW. Con SESSION_TIME=10 y ventana de 30 segundos, aporta poco en el flujo normal, pero protege contra requests repetidas, simultáneas o una ventana de refresh más amplia.
SESSION_CLEANUP_INTERVAL
Opcional Default: 600
Intervalo de limpieza de tabs expiradas. El bootstrap no recorre tabs expiradas en cada request. Cada sesión PHP ejecuta el barrido como máximo una vez por intervalo.
Tabs en sesión Cookie compartida, contexto por pestaña.
  • Header Surface X-TAB-SESSION Identifica la pestaña activa.
  • Mapa Gateway $_SESSION['tabs'] Guarda entradas separadas por tab.
  • Limpieza SESSION_CLEANUP_INTERVAL Controla cuándo se remueven tabs expiradas.
  • Refresh efectivo SESSION_REFRESH_WINDOW + COOLDOWN Debe estar cerca de vencer y fuera del cooldown.

Guía rápida, leída como regla exacta: con SESSION_TIME=10, el login de las 12:00:00 crea una tab session cuyo expiresAtUnix apunta a 12:10:00. Ese valor no se renueva en cada request autenticada. Gateway solo lo mueve cuando se cumplen dos puertas a la vez: faltan SESSION_REFRESH_WINDOW segundos o menos para vencer, y ya pasó más de SESSION_REFRESH_COOLDOWN segundos desde el último refresh real guardado en refreshedAtUnix.

En este ejemplo, una request a las 12:09:35 todavía llega antes de vencer: faltan 25 segundos para 12:10:00, así que está dentro de la ventana de 30 segundos. Además, el último refresh real fue el login de las 12:00:00; pasaron 575 segundos, más que el cooldown de 60. Por eso la request puede renovar la tab y el nuevo vencimiento queda en 12:19:35. La extensión se calcula como ahora + SESSION_TIME, no como vencimiento anterior + SESSION_TIME.

Si inmediatamente entra otra request a las 12:09:36, no hay otra extensión. Después del refresh anterior la tab ya vence a las 12:19:35, por lo que faltan casi 10 minutos y dejó de estar en la ventana final. Además, solo pasó 1 segundo desde refreshedAtUnix=12:09:35, así que el cooldown también sigue bloqueando una nueva escritura. La request puede responder correctamente y publicar un X-REMAINING actualizado, pero no debe mover otra vez expiresAtUnix.

Cuándo sí importa el cooldown Es una defensa contra renovaciones demasiado frecuentes, no el reloj principal de la sesión.

En la configuración típica de esta guía, SESSION_TIME=10, SESSION_REFRESH_WINDOW=30 y SESSION_REFRESH_COOLDOWN=60, el cooldown casi nunca decide solo. Después de renovar, la tab vuelve a quedar a casi diez minutos de vencer, así que sale inmediatamente de la ventana de 30 segundos. En ese caso, la ventana ya bloquea la mayoría de renovaciones repetidas y el cooldown queda como cinturón de seguridad.

  • Requests simultáneas fragments / fetch Si varios fragments llegan justo dentro de la ventana final, solo una request debería renovar y las demás deberían reutilizar el nuevo tiempo.
  • Ventana amplia SESSION_REFRESH_WINDOW=300 Si permites renovar cuando faltan cinco minutos, muchas requests normales caerán dentro de la ventana; el cooldown separa las escrituras reales.
  • Polling o autosave cada pocos segundos Una pantalla que consulta o guarda seguido no debería convertir cada request cercana al vencimiento en una escritura de sesión.
  • Sesiones cortas SESSION_TIME bajo Si la sesión dura poco y la ventana ocupa una parte grande de esa duración, el cooldown se vuelve más visible.

Lectura simple: SESSION_TIME decide cuánto dura la sesión; SESSION_REFRESH_WINDOW decide cuándo se puede pedir una nueva; y SESSION_REFRESH_COOLDOWN evita pedir una nueva demasiadas veces seguidas.

Escenario de prueba Explicación a detalle y paso a paso Resultado esperado
12:00:00, login con SESSION_TIME=10. Se emite metadata nueva: startedAtUnix, refreshedAtUnix y expiresAtUnix. refreshedAtUnix=12:00:00 y expiresAtUnix=12:10:00.
12:08:00, request autenticada. Faltan 120 segundos; todavía es mayor que SESSION_REFRESH_WINDOW=30. No hay refresh. La tab sigue venciendo a las 12:10:00.
12:09:29, borde antes de la ventana. Faltan 31 segundos, apenas fuera de la ventana final. No hay refresh. Sirve para probar el límite exacto de la ventana.
12:09:35, primera request dentro de la ventana. Faltan 25 segundos y pasaron 575 desde el último refresh real. Sí hay refresh. El nuevo expiresAtUnix queda en 12:19:35.
12:09:36, doble click, fetch repetido o fragment inmediato. Tras el refresh anterior faltan 599 segundos y solo pasó 1 segundo de cooldown. No hay nuevo refresh. La request puede ser válida, pero no debe escribir otra expiración.
12:10:35, exactamente 60 segundos después. El cooldown aún no pasa porque el código exige time() - refreshedAtUnix > 60, no >= 60. No hay refresh. Además, todavía faltan 540 segundos para 12:19:35.
12:10:36, cooldown ya superado. Pasaron más de 60 segundos, pero faltan 539 segundos para vencer. No hay refresh porque la tab no está cerca de expirar.
12:19:04, antes de la siguiente ventana. Faltan 31 segundos para 12:19:35. No hay refresh. Sigue estando un segundo fuera de la ventana permitida.
12:19:05, próxima ventana válida. Faltan 30 segundos y el cooldown quedó ampliamente superado. Sí hay refresh. El nuevo vencimiento sería 12:29:05.

La prueba mental queda así: fuera de ventana no se renueva; dentro de ventana pero en cooldown no se renueva; dentro de ventana y fuera de cooldown sí se renueva. Esa combinación evita escrituras repetidas de sesión por cada fetch, fragment o click duplicado.

Qué se instala y por qué importa

Una dependencia es una pieza externa que el proyecto decide usar en lugar de escribirla desde cero. Puede ser una librería para leer variables de entorno, un cliente HTTP para llamar APIs, un compilador de TypeScript, una librería visual o un paquete que solo le da información al editor. Instalar dependencias no significa que todas se ejecuten en producción ni que todas lleguen al navegador.

La pregunta útil es: ¿en qué momento participa? Algunas piezas corren mientras Gateway responde una request real. Otras solo existen cuando ejecutas un comando en consola. Otras compilan los archivos de Surface y desaparecen antes de que el usuario abra la página. Otras no ejecutan nada: solo describen tipos para que TypeScript avise si estás usando mal una dependencia existente.

Idea conceptual

Runtime

Lo que puede ejecutarse mientras la aplicación atiende una request o mientras el navegador usa una pantalla.

Build

Lo que transforma TypeScript, CSS y módulos en archivos finales que Gateway puede publicar.

Tooling

Herramientas para generar código, depurar, validar tipos, limpiar cache o asistir al desarrollo.

Tipos

Paquetes que no agregan comportamiento; solo ayudan a TypeScript a entender una dependencia existente.

En WPC hay dos mundos instalables. Gateway usa Composer porque es PHP; Surface usa npm porque compila TypeScript y assets de navegador. Ambos descargan paquetes, pero resuelven problemas distintos. Composer prepara el backend y sus comandos; npm prepara el frontend y el pipeline que emite archivos estáticos.

Nombre del archivo Explicación simple En WPC
composer.json Lista las dependencias directas y scripts del proyecto PHP. Vive en `app-gateway` y describe lo que Gateway necesita para arrancar, llamar servicios externos y ejecutar comandos.
package.json Lista dependencias, scripts npm y metadatos del frontend. Vive en `app-surface` y declara Vite, TypeScript, librerías UI, tipos y comandos como `npm run lite:build`.
vendor/ Carpeta donde Composer instala paquetes PHP. Gateway la usa para autoload, runtime PHP y comandos locales. No se edita a mano.
node_modules/ Carpeta donde npm instala paquetes JavaScript. Surface la usa para compilar. El servidor final no necesita esta carpeta si ya recibió los assets generados.

Flujo mental de instalación a ejecución

  1. Instalas Gateway: composer install lee `composer.json` y `composer.lock`, descarga paquetes PHP en `vendor/` y prepara el autoload.
  2. Instalas Surface: npm install lee `package.json` y `package-lock.json`, descarga paquetes en `node_modules/` y deja disponibles comandos como Vite, TypeScript y BrowserSync.
  3. Compilas assets: npm run lite:build convierten el código de Surface en archivos CSS/JS y manifest dentro de app-gateway/{PUBLIC_PATH}/ui-assets. Gateway no ejecuta TypeScript; solo publica el resultado.
  4. Atiendes una request: Gateway usa dependencias PHP de runtime para cargar `.env`, construir contenedor, resolver rutas, renderizar HTML, llamar APIs externas o emitir JSON. Surface se monta sobre ese HTML con los assets ya publicados.
  5. Generas o mantienes código: comandos como composer robo -- <command>, dumps de desarrollo y servidores auxiliares viven en dependencias de desarrollo. Son importantes para el equipo, pero no deberían ser requisito para responder cada request web.

Cómo leer los grupos de dependencias

Los nombres de los grupos parecen obvios, pero conviene leerlos como una decisión de disponibilidad. No dicen solo “qué paquete se instala”; dicen en qué escenarios el proyecto espera encontrar ese paquete.

Grupo de dependencias Lectura conceptual Qué pasa si falta
composer.json
require Dependencias PHP necesarias para que Gateway funcione en runtime: bootstrap, contenedor, HTTP outbound, entorno o auditoría. Puede fallar una request real, el bootstrap, un controller o una integración externa.
require-dev Dependencias PHP para comandos, generación, consola o diagnóstico durante desarrollo. Pueden fallar `composer robo -- <command>`, dumps o tareas locales, pero una request web normal no debería depender de ellas.
package.json
dependencies Librerías JavaScript/CSS que Surface puede usar en código del navegador, adapters UI o assets publicados. Puede fallar el bundle, una interacción UI, una utilidad de fecha o una alerta cargada por lazy import.
devDependencies Herramientas Node para compilar, validar tipos, leer env de build, servir localmente o describir cómo debe usarse una dependencia existente legacy. Puede fallar `npm run lite:build`, el typecheck o la experiencia del editor, aunque los assets ya generados puedan seguir sirviéndose.
Lectura de manifiestos Distingue lo directo, lo fijado y lo disponible por entorno.
  • Dependencias directas Son las declaradas por el proyecto en sus manifiestos.
  • Versiones exactas composer.lock / package-lock.json Fijan el árbol instalado, pero no definen funcionalidades, rutas, métodos ni contratos externos.
  • Composer require / require-dev Cambia si está disponible en runtime PHP o solo tooling.
  • npm dependencies / devDependencies Cambia si llega a build/runtime Surface o solo desarrollo.

Composer: Gateway y tooling PHP

`app-gateway/composer.json` define el proyecto PHP. El autoload PSR-4 expone `App\\` hacia `app-gateway/app/` y `Tools\\` hacia `tools/`.

Paquete o dependencia Para qué sirve Detalle operativo
require
vlucas/phpdotenv Carga variables desde el `.env` raíz. Gateway lo usa durante bootstrap HTTP y CLI para leer modo de ejecución, rutas públicas, sesión, assets y overrides outbound. Es runtime porque el sistema necesita conocer el entorno antes de construir contenedor, rutas o clientes.
symfony/dependency-injection Construye y compila el contenedor de servicios. Sostiene providers de `Core` y `Extension`, inyección de controllers, middleware, responses, clients outbound y servicios compartidos. No es una capa de negocio; es la infraestructura que evita instanciar dependencias a mano en cada request.
symfony/config Da soporte a carga de configuración y cache compilado. Acompaña al contenedor con `FileLocator`, `ConfigCache` y piezas de carga PHP. En producción permite fallar claro si el cache requerido no existe o no está alineado con el filesystem real.
guzzlehttp/guzzle Cliente HTTP concreto para integraciones outbound. Implementa la conversación técnica con APIs externas detrás de los contratos internos de HTTP. Los connectors no deben exponer Guzzle como regla de aplicación; lo consumen a través de infraestructura y devuelven resultados del proyecto.
whichbrowser/parser Parsea `User-Agent` para auditoría de sesión/navegador. Ayuda a registrar contexto técnico del navegador sin meter parsing manual en controllers. Es runtime porque el dato se obtiene durante requests reales.
require-dev
consolidation/robo Task runner de comandos `composer robo`. Ejecuta scaffolding, generación de contratos y tareas de mantenimiento. No participa en cada request web. En un servidor productivo normal puede omitirse con composer install --no-dev si no se ejecutan generadores allí.
symfony/var-dumper Inspección legible de variables durante desarrollo. Alimenta herramientas de debug. Sirve para diagnosticar estructuras complejas sin convertir dumps en contrato público ni dejarlos como salida normal de aplicación.
symfony/console Base CLI usada por Robo y comandos de soporte. La versión queda fijada para mantener compatible el runtime de consola con el bridge de deprecaciones usado por `composer robo`. Es tooling: si un flujo necesita estar disponible en runtime web, no debe depender de Console.

Scripts Composer

Comando literal en consola Cuándo usarlo

npm: Surface, build y librerías del navegador

`app-surface/package.json` está marcado como `private` para evitar publicación accidental y usa `type: module` porque Vite, la config y el código TypeScript trabajan como módulos ES. Las dependencias de producción describen librerías que pueden llegar al navegador o a assets publicados; las de desarrollo describen herramientas que hacen posible compilar, tipar y servir Surface.

Nombre de la dependencia Para qué sirve Detalle operativo
dependencies
bootstrap Base visual y JS de componentes Bootstrap. Los layouts SSR cargan Bootstrap compilado y los adapters de Surface leen `window.bootstrap` para modales, toasts y dropdowns. Se conserva como dependencia de runtime porque representa una librería UI del navegador, aunque no todos los módulos la importen directamente desde TypeScript.
bootstrap-icons Fuente y clases de iconografía Bootstrap. Los layouts y estilos de workspace pueden depender de esa familia de iconos. Es visual, no lógica de negocio; si una pantalla usa iconos, debe tratarlos como assets de navegador.
luxon Manejo de fechas en toolkit y adapters. `toolkit/shared/date.ts` y el adapter de `daterangepicker` usan `DateTime` para parsear, formatear y comparar fechas sin repartir conversiones manuales por cada integración.
sweetalert2 Alertas, confirmaciones, formularios y toasts UI. El adapter `toolkit/feedback/swal` lo carga de forma lazy con `import("sweetalert2")`. Eso lo mantiene como pieza de runtime, pero evita cargarlo antes de que una pantalla lo necesite.
devDependencies
@types/bootstrap Tipos TypeScript para la API de Bootstrap. Permite tipar constructores y métodos usados por adapters sin empaquetar código adicional. El paquete desaparece del runtime; solo informa al compilador.
@types/datatables.net Tipos para DataTables legacy. Surface puede inicializar wrappers sobre tablas ya renderizadas o plugins cargados por layout. Los tipos evitan `any` innecesario, pero no instalan el plugin en el navegador.
@types/daterangepicker Tipos para el plugin `daterangepicker`. Acompaña al adapter de fechas que valida la existencia del plugin jQuery antes de usarlo. El paquete solo describe cómo se usa la dependencia.
@types/jquery Tipos para `$` y plugins jQuery legacy. Vite marca `jquery` como externo en Rollup; eso significa que Surface espera el global cargado por el layout y no lo mete al bundle. Los tipos permiten compilar código que interactúa con ese global.
@types/luxon Tipos históricos para Luxon. Ayuda al compilador en integraciones que consumen `DateTime`. Aunque Luxon moderno ya publica tipos, mantener el paquete aquí no cambia el runtime; solo afecta validación TypeScript.
@types/moment Tipos para interoperar con plugins legacy basados en Moment. `daterangepicker` y ecosistemas heredados suelen exponer objetos Moment. El tipo evita perder contrato en adapters aunque la estrategia propia de Surface prefiera Luxon para lógica nueva.
@types/node Tipos de APIs Node usadas por config/build. `vite.config.ts` y `vite.config.constants.ts` usan rutas, records de entorno y tipos de build. Esto no llega al navegador; vive en el proceso Node que compila Surface.
@types/select2 Tipos para Select2. Permite tipar el adapter `toolkit/adapters/select2` y sus opciones sin convertir Select2 en dependencia empaquetada por Vite.
browser-sync Servidor/proxy de apoyo para desarrollo local. Lo invoca el script `npm run serve`. Es útil para recarga, proxy o pruebas locales, pero no forma parte del bundle ni del servidor PHP.
dotenv Lectura de variables durante tooling Node. Vite usa carga de entorno desde la raíz del workspace para construir `__APP_ENV__`, `outDir`, `assetBase`, sourcemaps y modo de build. No reemplaza a `vlucas/phpdotenv` en Gateway.
typescript Typecheck y compilación TypeScript. Herramienta para validar tipos y compilar TypeScript a JavaScript durante el desarrollo y build.
vite Bundler y dev/build tool de Surface. Lee `vite.config.ts`, aplica alias `@`, inyecta `__APP_ENV__`, genera manifest y publica assets en `app-gateway/{PUBLIC_PATH}/ui-assets`. Es esencial para construir, pero el servidor final consume los archivos ya emitidos.

Scripts npm

Comando literal en consola Qué es lo que ejecuta Uso esperado
npm run build tsc && vite build Validación completa: primero TypeScript, luego bundle, manifest y assets publicados.
npm run lite:build vite build --watch Watch rápido usado en onboarding: recompila assets al cambiar Surface sin ejecutar `tsc` en cada ciclo.
Despliegue El servidor final necesita runtime y assets, no todo el toolchain.
  • Servidor PHP Requiere dependencias Composer de runtime.
  • Surface Debe llegar con assets ya compilados.
  • Build en servidor devDependencies Necesarias solo si el build ocurre allí.
  • Assets publicados node_modules No se necesita en el servidor final si compilas antes.

Validación inicial

  • Los assets Vite cargan desde `ui-assets`.
  • El HTML del layout tiene `body#main-body-access` o `body#main-body-control`.

Cuando una validación falle, la revisión continúa en Ayuda o en los contratos de JSON envelope y Contratos HTML.
