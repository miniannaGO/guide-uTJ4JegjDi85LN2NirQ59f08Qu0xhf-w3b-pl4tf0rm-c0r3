Empezar

Preparación del entorno local: instalar dependencias, configurar .env, construir los archivos del navegador y comprobar que Gateway y Surface puedan ejecutarse juntos.

Requisitos

Esta sección no instala nada todavía: fija las herramientas mínimas que deben existir antes de tocar el repositorio. El proyecto se apoya en PHP para app-gateway y en TypeScript/Vite para app-surface.

Con esas piezas disponibles, la guía puede leerse en orden: primero Gateway como entrada HTTP y salida controlada, después Surface como activación progresiva del HTML entregado por Gateway.

Entorno local

Este panel separa el runtime, el gestor de dependencias PHP y el gestor frontend para identificar qué parte del entorno falta o está desactualizada.

  1. Gateway

    PHP 8.2 en adelante

    Runtime base de Gateway

  2. Dependencias

    Composer

    Instala paquetes PHP y prepara el autoload del Gateway.

  3. Surface

    npm

Instalación

Instalar el proyecto significa preparar dos áreas que trabajan juntas: Gateway necesita sus paquetes PHP y Surface necesita sus herramientas de TypeScript y Vite. El objetivo de este paso no es arrancar todavía la aplicación, sino dejar ambas áreas listas para que los comandos posteriores encuentren sus dependencias.

En términos técnicos, Composer crea el árbol de dependencias PHP y npm crea el árbol de dependencias frontend. Si una instalación falla, se debe resolver ese lado antes de configurar el .env.

Clonar proyecto 
/ruta/donde/crear-el-proyecto> git clone <URL_DEL_REPOSITORIO> web-platform-core
Instalar Gateway y Surface 
/raiz-del-proyecto/app-gateway> composer install
    
/raiz-del-proyecto/app-surface> npm install

Ejecución local

La primera ejecución comprueba una sola cosa: que Surface puede transformar su código TypeScript en archivos que Gateway pueda publicar. Por eso se inicia un proceso que queda atento a los cambios y vuelve a compilar cuando se modifica el frontend.

Ese proceso se conoce como watch. En desarrollo se usa lite:build para que Vite recompile los assets publicados cuando cambie el código TypeScript. Ese script ejecuta vite build --watch; no corre tsc antes de cada build. Para una validación completa de TypeScript se debe usar npm run build.

Esta prueba confirma que Surface puede producir archivos que Gateway resolverá al renderizar HTML. No explica todavía el build de Vite, la resolución de assets ni el runtime de montaje; solo valida que la base instalada puede ejecutar el primer ciclo local.

Watch surface 
/raiz-del-proyecto/app-surface> npm run lite:build

Archivo .env

El archivo .env permite cambiar cómo se ejecuta la solución en cada entorno sin modificar el código fuente. Allí se indican decisiones como la ubicación pública del proyecto, el modo local o productivo y los ajustes que dependen del servidor donde se despliega.

Vive en la raíz de la solución y se crea desde .env.template. Sus grupos controlan el modo de ejecución, rutas base, sesión, assets y overrides outbound.

Crear .env 
/raiz-del-proyecto copy .env.template .env

Mínimo para levantar localmente

Para el primer arranque no se necesita completar toda la plantilla. Después de copiar .env.template, basta con revisar las variables que ubican la aplicación en el servidor local y mantienen el runtime en modo desarrollo.

.env mínimo local 
IS_PRODUCTION=false
DEEP_DEPLOYED=true
BASE_URI="web-platform-core"

Si Gateway se sirve desde la raíz del host, se debe usar BASE_URI="". Las variables de sesión, logs y outbound pueden dejarse con sus valores por defecto hasta que se necesite ajustar ese comportamiento.

Runtime general

Estas variables deciden el comportamiento general del proceso que está ejecutando la aplicación. En la guía, ese proceso activo se denomina runtime. Aquí se define si el entorno es local o productivo, cuánto detalle puede mostrar ante un error y qué versión identifica el despliegue.

Variable Qué controla Cómo decidir el valor
IS_PRODUCTION
Opcional Default: false
Modo general del runtime. Valor recomendado localmente: false. En true reutiliza cache DI, exige release válido y oculta detalle técnico.
DEEP_DEPLOYED
Opcional Default: false
Detalle técnico de errores hacia cliente. Solo aplica con IS_PRODUCTION=false. Puede configurarse en true para depuración local.
VERSION_DEPLOY
Obligatoria en producción Default: 0
Versión del despliegue utilizada para renovar los assets almacenados en caché. Debe usarse un entero tipo 20260101. En producción debe ser mayor que 0.
SPEED_UP_BUILD
Opcional Default: false
Optimización del build Surface. Solo la lee Vite. En true desactiva minify/treeshake para iterar más rápido; no llega al runtime PHP ni a __APP_ENV__.

Rutas, assets y UI

Este grupo responde a una pregunta visible: ¿dónde encontrará el navegador la aplicación y los archivos que necesita? Las variables ubican el proyecto dentro del servidor, indican la ruta pública de CSS y scripts compilados, fijan la zona horaria y permiten establecer una preferencia visual. Esos archivos publicados se denominan assets.

Variable Qué controla Cómo decidir el valor
BASE_URI
Obligatoria para surface Default: ""
Directorio base de la solución. Sin slash inicial ni final cuando se use subcarpeta.
APP_BASE_PATH
Opcional Default: app-gateway
Segmento del gateway. Normalmente app-gateway.
PUBLIC_PATH
Opcional Default: public
Carpeta pública de assets. Normalmente public.
APP_TIMEZONE
Opcional Default: America/Lima
Zona horaria del bootstrap web y CLI. Por defecto America/Lima; cambia solo si el despliegue lo requiere.
MENU_LAYOUT
Opcional Default: wide
Preferencia de layout disponible para runtime/UI. wide para ancho completo o box para contenedor más acotado.
Ruta pública BASE_URI, APP_BASE_PATH y PUBLIC_PATH deben coincidir con la URL local.
Zona horaria APP_TIMEZONE fija fechas, logs y cálculos temporales desde el bootstrap.

Outbound

Cuando Gateway debe comunicarse con un sistema externo, la dirección, las credenciales o los tiempos de espera pueden cambiar entre entornos. La guía llama outbound a esas comunicaciones que salen de la aplicación. Este grupo permite ajustar por entorno la configuración base declarada en services.json sin modificar ese archivo versionado.

Variable Qué controla Cómo decidir el valor
API_<PREFIX>_URI
Condicional Default: services.json / vacío
URL base de un servicio outbound. Prioriza este valor sobre services.json. Es obligatoria solo cuando el servicio requerido no trae uri válida en services.json.
API_<PREFIX>_BEARER
Opcional Default: services.json / ""
Token bearer para un servicio outbound. Debe configurarse solo cuando el servicio requiere autenticación por bearer.
API_<PREFIX>_TIMEOUT_SECONDS
Opcional Default: services.json / 30.0
Timeout total de una llamada outbound. Debe ser numérico y mayor que 0.
API_<PREFIX>_CONNECT_TIMEOUT_SECONDS
Opcional Default: services.json / 10.0
Timeout de conexión hacia el servicio. Debe ser numérico y mayor que 0.
API_<PREFIX>_VERIFY_TLS
Opcional Default: services.json / false
Validación TLS del cliente outbound. Debe ser true o false; en producción normalmente conviene dejarlo en true si el servicio tiene TLS válido.
Equivalencia services.json services.json declara la base; .env solo sobrescribe por entorno.

Gateway carga primero app-gateway/services.json. Dentro de ese archivo, cada entrada bajo clients es un cliente outbound nombrado. Ese nombre es importante: el provider lo pide al core y el core construye las variables de entorno con la forma API_<PREFIX>_*, usando el nombre del servicio en mayúsculas. Así que las variables equivalentes empiezan por API_<PREFIX>_.

Base actual en services.json 
{
  "clients": {
    "<prefix>": {
      "uri": "https://ip:port"
    }
  }
}
Variables equivalentes en .env 
API_<PREFIX>_URI="https://ip:port"
API_<PREFIX>_BEARER=""
API_<PREFIX>_TIMEOUT_SECONDS=30
API_<PREFIX>_CONNECT_TIMEOUT_SECONDS=10
API_<PREFIX>_VERIFY_TLS=false
Forma completa equivalente en services.json 
{
  "clients": {
    "<prefix>": {
      "uri": "https://ip:port",
      "bearer": "",
      "timeoutSeconds": 30,
      "connectTimeoutSeconds": 10,
      "verifyTls": false
    }
  }
}
  • Base versionable services.json Guarda valores compartibles del cliente, como la URL local base o timeouts estándar.
  • Override de entorno .env Gana sobre services.json cuando la variable existe y no está vacía.
  • Texto vacío URI / BEARER Si la variable está vacía, el core conserva el valor leído desde services.json.
  • Validación fuerte TIMEOUT / TLS Los timeouts deben ser numéricos y mayores que 0; TLS debe interpretarse como booleano.

Si ni services.json ni .env entregan una uri usable, Gateway emite un fallo al crear la definición del servicio. Los demás campos tienen defaults del core: bearer vacío, timeout total 30.0, timeout de conexión 10.0 y verifyTls=false.

Logs

Los logs permiten reconstruir qué ocurrió cuando una petición falla, tarda demasiado o cruza varias dependencias. Esa capacidad de observar el sistema se denomina observabilidad. Estas variables deciden si Gateway registra cada petición, cuánto detalle conserva de las llamadas externas, cuándo descarga a disco la información de consola y durante cuántas semanas mantiene los archivos. La explicación de términos como telemetría, span, collector y retención vive en Observabilidad de Gateway.

Variable Valores Cómo configurarla
LOG_TELEMETRY_ENABLED
Opcional Default: true
Booleano. Acepta true, 1, on, yes, false, 0, off y no. Mantener en true para registrar observabilidad normal por request. Usar false solo cuando se quiera silenciar esa telemetría durante una ejecución local o un diagnóstico puntual.
LOG_UPSTREAM_SPANS
Opcional Default: auto
auto o booleano. auto lo activa en desarrollo y lo desactiva en producción. Mantener auto como valor normal. Cambiar a true para forzar detalle por llamada outbound, o a false para dejar solo el resumen upstream dentro de access/metrics.
LOG_COLLECTOR_FLUSH_EVERY
Opcional Default: 100
Entero positivo. El valor esperado para el collector es 100 cuando no se configura otra cosa. Solo afecta al collector usado con salida CLI. Un valor bajo hace flush con más frecuencia; un valor alto agrupa más líneas antes de persistir.
LOG_RETENTION_WEEKS
Opcional Default: 12
Entero mayor que 0. El default de runtime es 12. Define cuántas semanas completas se conservan al ejecutar composer run logs:prune. Con 1 se conserva solo la semana actual.

Sesión

La sesión conserva continuidad entre peticiones del mismo navegador. En este proyecto, una cookie identifica la sesión compartida y cada pestaña mantiene además su propio contexto. Estas variables deben leerse juntas porque deciden cuánto dura ese contexto, cuándo puede renovarse y cuándo se elimina después de expirar.

Variable Qué controla Cómo decidir el valor
SESSION_PATH
Opcional Default: sys_get_temp_dir()
Ruta física donde PHP guarda sesiones. Para usar el temporal de PHP, la variable debe eliminarse en vez de dejarse vacía.
SESSION_TIME
Opcional Default: 10
Minutos de sesión. Debe usarse un entero positivo. Gateway lo usa para calcular expiresAtUnix al crear o refrescar una tab. Surface no calcula este vencimiento: lo recibe en X-REMAINING.
SESSION_REFRESH_WINDOW
Opcional Default: 30
Ventana de refresh de sesión, en segundos. Gateway solo extiende la tab session cuando faltan esos segundos o menos para expirar. Debe ser mayor o igual que SESSION_EXPIRY_ALERT para que el aviso de Surface aparezca cuando Gateway ya puede renovar.
SESSION_EXPIRY_ALERT
Opcional Default: SESSION_REFRESH_WINDOW
Momento del warning de expiración que Surface convierte en modal. Vite lo expone en __APP_ENV__; debe ser menor o igual que SESSION_REFRESH_WINDOW. Si es mayor, Surface avisa antes de que Gateway permita refrescar; si es demasiado bajo, el usuario tendrá poco margen para actuar. Si no se define, Surface usa la ventana de refresh como fallback.
SESSION_REFRESH_COOLDOWN
Opcional Default: 60
Enfriamiento entre refreshes, en segundos. Es un freno de escritura: Gateway solo lo mira después de comprobar que la tab está dentro de SESSION_REFRESH_WINDOW. No necesita ser menor que la ventana; puede ser mayor. Sí debe quedar por debajo de la vida total de la tab (SESSION_TIME * 60) para no impedir el refresh antes de expirar.
SESSION_CLEANUP_INTERVAL
Opcional Default: 600
Intervalo de limpieza de tabs expiradas. El bootstrap no recorre tabs expiradas en cada request. Cada sesión PHP ejecuta el barrido como máximo una vez por intervalo.
  1. SESSION_TIME Define duración base.
  2. SESSION_REFRESH_WINDOW Abre la ventana final.
  3. SESSION_REFRESH_COOLDOWN Evita escrituras repetidas.
  4. SESSION_CLEANUP_INTERVAL Limpia tabs expiradas.

Esta tabla solo resume cómo configurar la sesión. El refresh real, cooldown, casos de prueba y almacenamiento por pestaña se explican en Gateway: refresh de sesión y pruebas de refresh. El transporte entre capas vive en Bridge: headers de sesión, y la experiencia visible del contador en Surface: sesión runtime.

Qué se instala y por qué importa

Una dependencia es una pieza externa que el proyecto decide usar en lugar de escribirla desde cero. Puede ser una librería para leer variables de entorno, un cliente HTTP para llamar APIs, un compilador de TypeScript, una librería visual o un paquete que solo le da información al editor. Instalar dependencias no significa que todas se ejecuten en producción ni que todas lleguen al navegador.

La pregunta útil es: ¿en qué momento participa? Algunas piezas corren mientras Gateway responde una request real. Otras solo existen durante la ejecución de un comando en consola. Otras compilan los archivos de Surface y desaparecen antes de que el usuario abra la página. Otras no ejecutan nada: solo describen tipos para que TypeScript advierta el uso incorrecto de una dependencia existente.

Idea conceptual

Lectura de paquetes

Cada grupo responde a un momento distinto del ciclo: ejecución, compilación, mantenimiento o soporte de tipos para el editor.

  1. Ejecución

    Runtime

    Lo que puede ejecutarse mientras la aplicación atiende una request o mientras el navegador usa una pantalla.

    Request / navegador
  2. Compilación

    Build

    Lo que transforma TypeScript, CSS y módulos en archivos finales que Gateway puede publicar.

    Vite / assets
  3. Mantenimiento

    Tooling

    Herramientas para generar código, depurar, validar tipos, limpiar cache o asistir al desarrollo.

    CLI / soporte
  4. Editor

    Tipos

    Paquetes que no agregan comportamiento; solo ayudan a TypeScript a entender una dependencia existente.

    TypeScript

En WPC hay dos mundos instalables. Gateway usa Composer porque es PHP; Surface usa npm porque compila TypeScript y assets de navegador. Ambos descargan paquetes, pero resuelven problemas distintos. Composer prepara el backend y sus comandos; npm prepara el frontend y el pipeline que emite archivos estáticos.

Elemento Explicación simple En WPC
composer.json Lista las dependencias directas y scripts del proyecto PHP. Vive en app-gateway y describe lo que Gateway necesita para arrancar, llamar servicios externos y ejecutar comandos.
package.json Lista dependencias, scripts npm y metadatos del frontend. Vive en app-surface y declara Vite, TypeScript, librerías UI, tipos y comandos como npm run lite:build.
vendor/ Carpeta donde Composer instala paquetes PHP. Gateway la usa para autoload, runtime PHP y comandos locales. No se edita a mano.
node_modules/ Carpeta donde npm instala paquetes frontend. Surface la usa para compilar. El servidor final no necesita esta carpeta si ya recibió los assets generados.

Secuencia de instalación a ejecución

Esta secuencia muestra qué prepara cada comando y cuándo se utiliza su resultado. La idea sencilla es que instalar pone herramientas a disposición, compilar produce archivos publicables y ejecutar usa ambos resultados sin mezclar sus responsabilidades.

  1. Instalación de Gateway: composer install lee composer.json y composer.lock, descarga paquetes PHP en vendor/ y prepara el autoload.
  2. Instalación de Surface: npm install lee package.json y package-lock.json, descarga paquetes en node_modules/ y deja disponibles comandos como Vite y TypeScript.
  3. Compilación de assets: npm run lite:build convierte el código de Surface en CSS, bundle de navegador y manifest dentro de app-gateway/{PUBLIC_PATH}/ui-assets. Gateway no ejecuta TypeScript; solo publica el resultado.
  4. Atención de una request: Gateway usa dependencias PHP de runtime para cargar .env, construir contenedor, resolver rutas, renderizar HTML, llamar APIs externas o emitir JSON. Surface se monta sobre ese HTML con los assets ya publicados.
  5. Generación o mantenimiento de código: comandos como composer robo -- <command>, dumps de desarrollo y servidores auxiliares viven en dependencias de desarrollo. Son importantes para el equipo, pero no deberían ser requisito para responder cada request web.

Cómo leer los grupos de dependencias

Los nombres de los grupos parecen obvios, pero conviene leerlos como una decisión de disponibilidad. No dicen solo “qué paquete se instala”; dicen en qué escenarios el proyecto espera encontrar ese paquete.

Grupo Lectura conceptual Qué pasa si falta
composer.json
require Dependencias PHP necesarias para que Gateway funcione en runtime: bootstrap, contenedor, HTTP outbound, entorno o auditoría. Puede fallar una request real, el bootstrap, un controller o una integración externa.
require-dev Dependencias PHP para comandos, generación, consola o diagnóstico durante desarrollo. Pueden fallar composer robo -- <command>, dumps o tareas locales, pero una request web normal no debería depender de ellas.
package.json
dependencies Librerías frontend que Surface puede usar en código del navegador, adapters UI o assets publicados. Puede fallar el bundle, una interacción UI, una utilidad de fecha o una alerta cargada por lazy import.
devDependencies Herramientas Node para compilar, validar tipos, leer env de build, servir localmente o describir cómo debe usarse una dependencia existente legacy. Puede fallar npm run lite:build, el typecheck o la experiencia del editor, aunque los assets ya generados puedan seguir sirviéndose.
Lectura de manifiestos Distingue lo directo, lo fijado y lo disponible por entorno.
  • Dependencias directas Son las declaradas por el proyecto en sus manifiestos.
  • Versiones exactas composer.lock / package-lock.json Fijan el árbol instalado, pero no definen funcionalidades, rutas, métodos ni contratos externos.
  • Composer require / require-dev Cambia si está disponible en runtime PHP o solo tooling.
  • npm dependencies / devDependencies Cambia si llega a build/runtime Surface o solo desarrollo.

Composer: Gateway y tooling PHP

Composer responde a una pregunta práctica: ¿qué necesita el lado PHP para funcionar y qué necesita únicamente para desarrollar o mantener el proyecto? Esa separación evita tratar una herramienta de consola como si fuera una dependencia obligatoria de cada petición web.

La respuesta técnica vive en app-gateway/composer.json. Además de declarar paquetes, su autoload PSR-4 relaciona App\\ con app-gateway/app/ y Tools\\ con tools/.

npm: Surface, build y librerías del navegador

npm reúne dos necesidades diferentes de Surface: librerías que pueden participar en la experiencia del navegador y herramientas que solo existen para compilar, validar o desarrollar. La forma de reconocerlas es preguntar si la pieza debe acompañar al código publicado o si termina su trabajo antes del despliegue.

Esa separación se declara en app-surface/package.json, que está marcado como private para evitar publicación accidental y usa type: module porque Vite, la config y el código TypeScript trabajan como módulos ES. Las dependencias de producción describen librerías que pueden llegar al navegador o a assets publicados; las de desarrollo describen herramientas que hacen posible compilar, tipar y servir Surface.

Scripts npm

Un script npm es un nombre corto para ejecutar una secuencia conocida sin recordar cada comando interno. Aquí la decisión es simple: lite:build prioriza rapidez durante el trabajo diario; build agrega la validación completa que se espera antes de cerrar un cambio.

Comando Qué es lo que ejecuta Uso esperado
npm run build tsc && vite build Validación completa: primero TypeScript, luego bundle, manifest y assets publicados.
npm run lite:build vite build --watch Watch rápido usado en onboarding: recompila assets al cambiar Surface sin ejecutar tsc en cada ciclo.
Despliegue El servidor final necesita runtime y assets, no todo el toolchain.
  • Servidor PHP Requiere dependencias Composer de runtime.
  • Surface Debe llegar con assets ya compilados.
  • Build en servidor devDependencies Necesarias solo si el build ocurre allí.
  • Assets publicados node_modules No se necesita en el servidor final si la compilación se realiza antes.

Validación inicial

Esta comprobación confirma que la instalación mínima conecta ambos lados de la solución: Surface produjo assets y Gateway puede incluirlos dentro de un layout reconocible. No demuestra todavía que una feature completa funcione; solo descarta fallos básicos de preparación antes de continuar con la arquitectura.

  • Los assets Vite cargan desde ui-assets.
  • El HTML del layout tiene body#main-body-access o body#main-body-control.
