Requisitos

Esta guía asume un entorno local de desarrollo. El proyecto actual usa PHP para `app-gateway` y TypeScript/Vite para `app-surface`.

Para entender el rol de cada contexto antes de instalar, consulta Contextos, App Gateway y App Surface.

PHP

PHP 8.2 o superior.

Composer

Instala dependencias de `app-gateway` y genera autoload.

npm

Instala dependencias y ejecuta Vite/TypeScript en `app-surface`.

Qué se instala y por qué importa

Una dependencia es una pieza externa que el proyecto decide usar en lugar de escribirla desde cero. Puede ser una librería para leer variables de entorno, un cliente HTTP para llamar APIs, un compilador de TypeScript, una librería visual o un paquete que solo le da información al editor. Instalar dependencias no significa que todas se ejecuten en producción ni que todas lleguen al navegador.

La pregunta útil es: ¿en qué momento participa? Algunas piezas corren mientras Gateway responde una request real. Otras solo existen cuando ejecutas un comando en consola. Otras compilan los archivos de Surface y desaparecen antes de que el usuario abra la página. Otras no ejecutan nada: solo describen tipos para que TypeScript avise si estás usando mal una API.

Idea conceptual

Runtime

Lo que puede ejecutarse mientras la aplicación atiende una request o mientras el navegador usa una pantalla.

Build

Lo que transforma TypeScript, CSS y módulos en archivos finales que Gateway puede publicar.

Tooling

Herramientas para generar código, depurar, validar tipos, limpiar cache o asistir al desarrollo.

Tipos

Paquetes que no agregan comportamiento; solo enseñan a TypeScript cómo se ve una API existente.

En WPC hay dos mundos instalables. Gateway usa Composer porque es PHP; Surface usa npm porque compila TypeScript y assets de navegador. Ambos descargan paquetes, pero resuelven problemas distintos. Composer prepara el backend y sus comandos; npm prepara el frontend y el pipeline que emite archivos estáticos.

Término Explicación simple En WPC
composer.json Lista las dependencias directas y scripts del proyecto PHP. Vive en `app-gateway` y describe lo que Gateway necesita para arrancar, llamar servicios externos y ejecutar comandos.
composer.lock Fija versiones exactas para que todos instalen lo mismo. Evita que dos máquinas tengan versiones distintas del contenedor, Guzzle, Dotenv o Robo aunque `composer.json` use rangos como `^7.4`.
package.json Lista dependencias, scripts npm y metadatos del frontend. Vive en `app-surface` y declara Vite, TypeScript, librerías UI, tipos y comandos como `npm run build`.
package-lock.json Fija el árbol exacto de paquetes descargados por npm. Hace reproducible el build de Surface y reduce sorpresas entre equipos, CI y máquinas locales.
vendor/ Carpeta donde Composer instala paquetes PHP. Gateway la usa para autoload, runtime PHP y comandos locales. No se edita a mano.
node_modules/ Carpeta donde npm instala paquetes JavaScript. Surface la usa para compilar. El servidor final no necesita esta carpeta si ya recibió los assets generados.

Flujo mental de instalación a ejecución

  1. Instalas Gateway: composer install lee `composer.json` y `composer.lock`, descarga paquetes PHP en `vendor/` y prepara el autoload. Desde ese momento Gateway puede encontrar clases de `App\\`, `Tools\\` y librerías externas.
  2. Instalas Surface: npm install lee `package.json` y `package-lock.json`, descarga paquetes en `node_modules/` y deja disponibles comandos como Vite, TypeScript y BrowserSync.
  3. Compilas assets: npm run lite:build o npm run build convierten el código de Surface en archivos CSS/JS y manifest dentro de app-gateway/{PUBLIC_PATH}/ui-assets. Gateway no ejecuta TypeScript; solo publica el resultado.
  4. Atiendes una request: Gateway usa dependencias PHP de runtime para cargar `.env`, construir contenedor, resolver rutas, renderizar HTML, llamar APIs externas o emitir JSON. Surface se monta sobre ese HTML con los assets ya publicados.
  5. Generas o mantienes código: comandos como composer robo, dumps de desarrollo y servidores auxiliares viven en dependencias de desarrollo. Son importantes para el equipo, pero no deberían ser requisito para responder cada request web.

Cómo leer los grupos de dependencias

Los nombres de los grupos parecen obvios, pero conviene leerlos como una decisión de disponibilidad. No dicen solo “qué paquete se instala”; dicen en qué escenarios el proyecto espera encontrar ese paquete.

Grupo Lectura conceptual Qué pasa si falta
require Dependencias PHP necesarias para que Gateway funcione en runtime: bootstrap, contenedor, HTTP outbound, entorno o auditoría. Puede fallar una request real, el bootstrap, un controller o una integración externa.
require-dev Dependencias PHP para comandos, generación, consola o diagnóstico durante desarrollo. Pueden fallar `composer robo`, dumps o tareas locales, pero una request web normal no debería depender de ellas.
dependencies Librerías JavaScript/CSS que Surface puede usar en código del navegador, adapters UI o assets publicados. Puede fallar el bundle, una interacción UI, una utilidad de fecha o una alerta cargada por lazy import.
devDependencies Herramientas Node para compilar, validar tipos, leer env de build, servir localmente o describir APIs legacy. Puede fallar `npm run build`, `npm run lite:build`, el typecheck o la experiencia del editor, aunque los assets ya generados puedan seguir sirviéndose.
Lectura de manifiestos Distingue lo directo, lo fijado y lo disponible por entorno.
  • Dependencias directas Son las declaradas por el proyecto en sus manifiestos.
  • Versiones exactas composer.lock / package-lock.json Fijan el árbol instalado, pero no son API pública.
  • Composer require / require-dev Cambia si está disponible en runtime PHP o solo tooling.
  • npm dependencies / devDependencies Cambia si llega a build/runtime Surface o solo desarrollo.

Composer: Gateway y tooling PHP

`app-gateway/composer.json` define el proyecto PHP. El autoload PSR-4 expone `App\\` hacia `app-gateway/app/` y `Tools\\` hacia `tools/`. Esa segunda entrada es deliberada: permite que comandos Robo de Gateway usen generadores compartidos sin copiar código dentro de `app-gateway`.

Paquete Grupo Para qué sirve Detalle operativo
vlucas/phpdotenv require Carga variables desde el `.env` raíz. Gateway lo usa durante bootstrap HTTP y CLI para leer modo de ejecución, rutas públicas, sesión, assets y overrides outbound. Es runtime porque el sistema necesita conocer el entorno antes de construir contenedor, rutas o clientes.
symfony/dependency-injection require Construye y compila el contenedor de servicios. Sostiene providers de `Core` y `Extension`, inyección de controllers, middleware, responses, clients outbound y servicios compartidos. No es una capa de negocio; es la infraestructura que evita instanciar dependencias a mano en cada request.
symfony/config require Da soporte a carga de configuración y cache compilado. Acompaña al contenedor con `FileLocator`, `ConfigCache` y piezas de carga PHP. En producción permite fallar claro si el cache requerido no existe o no está alineado con el filesystem real.
guzzlehttp/guzzle require Cliente HTTP concreto para integraciones outbound. Implementa la conversación técnica con APIs externas detrás de los contratos internos de HTTP. Los connectors no deben exponer Guzzle como regla de aplicación; lo consumen a través de infraestructura y devuelven resultados del proyecto.
whichbrowser/parser require Parsea `User-Agent` para auditoría de sesión/navegador. Ayuda a registrar contexto técnico del navegador sin meter parsing manual en controllers. Es runtime porque el dato se obtiene durante requests reales.
consolidation/robo require-dev Task runner de comandos `composer robo`. Ejecuta scaffolding, generación de contratos y tareas de mantenimiento. No participa en cada request web. En un servidor productivo normal puede omitirse con composer install --no-dev si no se ejecutan generadores allí.
symfony/var-dumper require-dev Inspección legible de variables durante desarrollo. Alimenta herramientas de debug. Sirve para diagnosticar estructuras complejas sin convertir dumps en contrato público ni dejarlos como salida normal de aplicación.
symfony/console require-dev Base CLI usada por Robo y comandos de soporte. La versión queda fijada para mantener compatible el runtime de consola con el bridge de deprecaciones usado por `composer robo`. Es tooling: si un flujo necesita estar disponible en runtime web, no debe depender de Console.

Scripts Composer

Los scripts no son dependencias, pero explican cómo se invocan piezas instaladas por Composer. Por eso conviene leerlos junto al manifiesto.

Script Qué ejecuta Cuándo usarlo
composer run build:prod php bin/gateway build:prod Prepara el gateway para producción después de compilar assets y validar configuración.
composer run cache:clear php bin/gateway cache:clear Limpia cache generado por Gateway cuando cambian configuración, providers o artefactos compilados.

npm: Surface, build y librerías del navegador

`app-surface/package.json` está marcado como `private` para evitar publicación accidental y usa `type: module` porque Vite, la config y el código TypeScript trabajan como módulos ES. Las dependencias de producción describen librerías que pueden llegar al navegador o a assets publicados; las de desarrollo describen herramientas que hacen posible compilar, tipar y servir Surface.

Paquete Grupo Para qué sirve Detalle operativo
bootstrap dependencies Base visual y JS de componentes Bootstrap. Los layouts SSR cargan Bootstrap compilado y los adapters de Surface leen `window.bootstrap` para modales, toasts y dropdowns. Se conserva como dependencia de runtime porque representa una librería UI del navegador, aunque no todos los módulos la importen directamente desde TypeScript.
bootstrap-icons dependencies Fuente y clases de iconografía Bootstrap. Los layouts y estilos de workspace pueden depender de esa familia de iconos. Es visual, no lógica de negocio; si una pantalla usa iconos, debe tratarlos como assets de navegador.
luxon dependencies Manejo de fechas en toolkit y adapters. `toolkit/shared/date.ts` y el adapter de `daterangepicker` usan `DateTime` para parsear, formatear y comparar fechas sin repartir conversiones manuales por cada integración.
sweetalert2 dependencies Alertas, confirmaciones, formularios y toasts UI. El adapter `toolkit/feedback/swal` lo carga de forma lazy con `import("sweetalert2")`. Eso lo mantiene como pieza de runtime, pero evita cargarlo antes de que una pantalla lo necesite.
@types/bootstrap devDependencies Tipos TypeScript para la API de Bootstrap. Permite tipar constructores y métodos usados por adapters sin empaquetar código adicional. El paquete desaparece del runtime; solo informa al compilador.
@types/datatables.net devDependencies Tipos para DataTables legacy. Surface puede inicializar wrappers sobre tablas ya renderizadas o plugins cargados por layout. Los tipos evitan `any` innecesario, pero no instalan el plugin en el navegador.
@types/daterangepicker devDependencies Tipos para el plugin `daterangepicker`. Acompaña al adapter de fechas que valida la existencia del plugin jQuery antes de usarlo. El paquete solo describe la forma de la API.
@types/jquery devDependencies Tipos para `$` y plugins jQuery legacy. Vite marca `jquery` como externo en Rollup; eso significa que Surface espera el global cargado por el layout y no lo mete al bundle. Los tipos permiten compilar código que interactúa con ese global.
@types/luxon devDependencies Tipos históricos para Luxon. Ayuda al compilador en integraciones que consumen `DateTime`. Aunque Luxon moderno ya publica tipos, mantener el paquete aquí no cambia el runtime; solo afecta validación TypeScript.
@types/moment devDependencies Tipos para interoperar con plugins legacy basados en Moment. `daterangepicker` y ecosistemas heredados suelen exponer objetos Moment. El tipo evita perder contrato en adapters aunque la estrategia propia de Surface prefiera Luxon para lógica nueva.
@types/node devDependencies Tipos de APIs Node usadas por config/build. `vite.config.ts` y `vite.config.constants.ts` usan rutas, records de entorno y tipos de build. Esto no llega al navegador; vive en el proceso Node que compila Surface.
@types/select2 devDependencies Tipos para Select2. Permite tipar el adapter `toolkit/adapters/select2` y sus opciones sin convertir Select2 en dependencia empaquetada por Vite.
browser-sync devDependencies Servidor/proxy de apoyo para desarrollo local. Lo invoca el script `npm run serve`. Es útil para recarga, proxy o pruebas locales, pero no forma parte del bundle ni del servidor PHP.
dotenv devDependencies Lectura de variables durante tooling Node. Vite usa carga de entorno desde la raíz del workspace para construir `__APP_ENV__`, `outDir`, `assetBase`, sourcemaps y modo de build. No reemplaza a `vlucas/phpdotenv` en Gateway.
sass devDependencies Compilación de estilos Sass cuando el build lo requiera. Pertenece al pipeline de assets. Si el CSS final ya fue emitido, el navegador no necesita Sass; solo recibe CSS.
typescript devDependencies Typecheck y compilación TypeScript. `npm run build` ejecuta `tsc` antes de `vite build`. Eso captura contratos rotos en `workspace`, `platform` y `toolkit` antes de publicar assets.
vite devDependencies Bundler y dev/build tool de Surface. Lee `vite.config.ts`, aplica alias `@`, inyecta `__APP_ENV__`, genera manifest y publica assets en `app-gateway/{PUBLIC_PATH}/ui-assets`. Es esencial para construir, pero el servidor final consume los archivos ya emitidos.

Scripts npm

Script Qué ejecuta Uso esperado
npm run dev vite Levanta el servidor de Vite. Útil para pruebas aisladas de frontend, no representa por completo el HTML SSR de Gateway.
npm run build tsc && vite build Validación completa: primero TypeScript, luego bundle, manifest y assets publicados.
npm run preview vite preview Sirve el build de Vite para inspección local. No reemplaza una prueba real contra Gateway cuando necesitas layout SSR, sesión o rutas PHP.
npm run serve browser-sync start --config bs-config.cjs Flujo auxiliar de desarrollo si existe configuración local de BrowserSync. No es requisito para runtime productivo.

Despliegue El servidor final necesita runtime y assets, no todo el toolchain.
  • Servidor PHP Requiere dependencias Composer de runtime.
  • Surface Debe llegar con assets ya compilados.
  • Build en servidor devDependencies Necesarias solo si el build ocurre allí.
  • Assets publicados node_modules No se necesita en el servidor final si compilas antes.

Archivo .env

El `.env` vive en la raíz de la solución. Se crea desde `.env.template`. Controla modo runtime, rutas base, sesión, assets y overrides outbound.

Si una variable afecta assets, outbound o sesión, amplía el contexto en Vite y assets, API HTTP clients externos y headers de sesión.

Crear .env 
copy .env.template .env
Variable Qué controla Cómo decidir el valor
Runtime general
IS_PRODUCTION
Opcional Default: false
Modo general del runtime. Valor recomendado localmente: `false`. En `true` reutiliza cache DI, exige release válido y oculta detalle técnico.
DEEP_DEPLOYED
Opcional Default: false
Detalle técnico de errores hacia cliente. Solo aplica con `IS_PRODUCTION=false`. Puede configurarse en `true` para depuración local.
VERSION_DEPLOY
Obligatoria en producción Default: 0
Versión de release para assets y cache endurecido. Debe usarse un entero tipo `20260101`. En producción debe ser mayor que `0`.
SPEED_UP_BUILD
Opcional Default: false
Optimización del build Surface. Solo la lee Vite. En `true` desactiva minify/treeshake para iterar más rápido; no llega al runtime PHP ni a __APP_ENV__.
Rutas públicas y assets
BASE_URI
Obligatoria para surface Default: ""
Directorio base de la solución. Sin slash inicial ni final cuando se use subcarpeta.
APP_BASE_PATH
Opcional Default: app-gateway
Segmento del gateway. Normalmente `app-gateway`.
PUBLIC_PATH
Opcional Default: public
Carpeta pública de assets. Normalmente `public`.
APP_TIMEZONE
Opcional Default: America/Lima
Zona horaria del bootstrap web y CLI. Por defecto `America/Lima`; cambia solo si el despliegue lo requiere.
UI / BFF
MENU_LAYOUT
Opcional Default: wide
Preferencia de layout disponible para runtime/UI. `wide` para ancho completo o `box` para contenedor más acotado.
Sesión
SESSION_PATH
Opcional Default: sys_get_temp_dir()
Ruta física donde PHP guarda sesiones. Para usar el temporal de PHP, la variable debe eliminarse en vez de dejarse vacía.
SESSION_TIME
Opcional Default: 10
Minutos de sesión. Debe usarse un entero positivo. Gateway lo usa para calcular expiresAtUnix al crear o refrescar una tab. Surface no calcula este vencimiento: lo recibe en X-REMAINING.
SESSION_REFRESH_WINDOW
Opcional Default: 30
Ventana de refresh de sesión, en segundos. Gateway solo extiende la tab session cuando faltan esos segundos o menos para expirar. Conviene que el aviso de Surface ocurra dentro de esta ventana.
SESSION_REFRESH_COOLDOWN
Opcional Default: 60
Enfriamiento entre refreshes, en segundos. Gateway lo evalúa después de comprobar que la tab está dentro de SESSION_REFRESH_WINDOW. Por ejemplo, si renovó a las 12:09:35 y entra otra request a las 12:09:36, no vuelve a escribir expiresAtUnix. Con 60, debe haber pasado más de un minuto; exactamente 60 segundos todavía no alcanza.
SESSION_CLEANUP_INTERVAL
Opcional Default: 600
Intervalo de limpieza de tabs expiradas. El bootstrap no recorre tabs expiradas en cada request. Cada sesión PHP ejecuta el barrido como máximo una vez por intervalo.
SESSION_CLEANUP_LAST_RUN_KEY
Opcional Default: _maintenance.tabsCleanupLastRunUnix
Clave interna para recordar la última limpieza. Normalmente no se cambia salvo migración o aislamiento de marca dentro de $_SESSION. Con el driver actual, la clave se guarda como $_SESSION['_maintenance']['tabsCleanupLastRunUnix'].
SESSION_EXPIRY_ALERT
Opcional Default: SESSION_REFRESH_WINDOW
Momento del warning de expiración que Surface convierte en modal. Vite lo expone en __APP_ENV__; debe ser menor o igual que SESSION_REFRESH_WINDOW. Si no se define, Surface usa la ventana de refresh como fallback.
Tabs en sesión Cookie compartida, contexto por pestaña.
  • Header Surface X-TAB-SESSION Identifica la pestaña activa.
  • Mapa Gateway $_SESSION['tabs'] Guarda entradas separadas por tab.
  • Limpieza SESSION_CLEANUP_INTERVAL Controla cuándo se remueven tabs expiradas.
  • Refresh efectivo SESSION_REFRESH_WINDOW + COOLDOWN Debe estar cerca de vencer y fuera del cooldown.

Guía rápida: login 12:00:00 con `SESSION_TIME=10` vence 12:10:00; una request 12:09:35 puede extender hasta 12:19:35, pero otra 12:09:36 no vuelve a extender si el cooldown todavía aplica.

Logs
Salida de logs Gateway escribe JSON Lines por entorno.
  • Requests web app-gateway/var/log/{env}/<semana>/stdout.jsonl `develop` o `production` según el entorno.
  • CLI stdout Puede persistirse con el collector.
  • Collector tools/Observability/log-collector/collect.php Guarda eventos emitidos desde consola.
  • Viewer tools/Observability/log-viewer Ruta de observabilidad permitida por `.htaccess`.
LOG_UPSTREAM_SPANS
Opcional Default: auto
Detalle por llamada outbound. auto mantiene detalle en desarrollo y evita un evento por upstream en producción. El resumen queda en access/metrics.
LOG_COLLECTOR_FLUSH_EVERY
Opcional Default: 100
Líneas acumuladas antes de hacer flush. No afecta a cada request web; solo regula el collector externo cuando se capturan procesos CLI que escriben en stdout.
LOG_RETENTION_WEEKS
Opcional Default: 12
Semanas completas de logs que se conservan. Debe ser mayor que 0; por defecto conserva la semana actual y las anteriores configuradas. También aplica a app-gateway/var/log/develop y app-gateway/var/log/production.
APIs outbound de HTTP client externo
API_<prefix>_URI
Condicional Default: services.json / vacío
URL base de un servicio outbound. Prioriza este valor sobre `services.json`. Es obligatoria solo cuando el servicio requerido no trae `uri` válida en `services.json`; para `external_api`, el prefijo es `API_EXTERNAL_API_`.
API_<prefix>_BEARER
Opcional Default: services.json / ""
Token bearer para un servicio outbound. Debe configurarse solo cuando el servicio requiere autenticación por bearer.
API_<prefix>_TIMEOUT_SECONDS
Opcional Default: services.json / 30.0
Timeout total de una llamada outbound. Debe ser numérico y mayor que `0`.
API_<prefix>_CONNECT_TIMEOUT_SECONDS
Opcional Default: services.json / 10.0
Timeout de conexión hacia el servicio. Debe ser numérico y mayor que `0`.
API_<prefix>_VERIFY_TLS
Opcional Default: services.json / false
Validación TLS del cliente outbound. Debe ser `true` o `false`; en producción normalmente conviene dejarlo en `true` si el servicio tiene TLS válido.

Ejecución local

Hay dos piezas: compilar assets de surface y servir gateway. En desarrollo usa `lite:build` para mantener Vite recompilando los assets publicados. Ese script ejecuta vite build --watch; no corre tsc antes de cada build. Para una validación completa de TypeScript usa npm run build.

El detalle del build vive en Vite, styles y assets, y la forma en que gateway los resuelve está en Assets Vite.

Watch surface 
cd app-surface
npm run lite:build

Validación inicial

  • Los assets Vite cargan desde `ui-assets`.
  • El HTML del layout tiene `body#main-body-access` o `body#main-body-control`.
  • Una página con `data-surface-page` muestra listeners activos.
  • Los endpoints JSON devuelven envelope con `success` booleano.
  • Los fragments devuelven HTML real, no JSON disfrazado.

Cuando una validación falle, la revisión continúa en Ayuda o en los contratos de JSON envelope y Contratos HTML.
